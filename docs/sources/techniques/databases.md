# Sources for `skills/algorithmic-intelligence/references/techniques/databases.md`

Where each claim in that file comes from, for maintainers and reviewers. Not part of the installed skill. PostgreSQL pages are under postgresql.org/docs/current/ (PostgreSQL 18 when checked, November 2026); section numbers can shift between versions, so pages are also named by file. Engine documentation describes implementation behavior unless it says the SQL standard requires it.

## Introduction

- The definition of a database's outcome (order, visibility, locking, atomicity, triggers) applies "Outcome, behavior, and contract" in `SKILL.md` and rule 5 to databases; no outside source.
- PostgreSQL, "Using EXPLAIN" (14.1, using-explain.html): "EXPLAIN actually executes the query," with side effects, and a `BEGIN` ... `ROLLBACK` example for writing statements. Plans depending on table size and statistics: "Statistics Used by the Planner" (14.2, planner-stats.html).

## Find where query time goes

- PostgreSQL, "pg_stat_statements" (F.32, pgstatstatements.html): statements with identical structure combined, constants replaced by parameter symbols; `calls`, `total_exec_time`, `mean_exec_time` columns.
- MySQL 8.4 Reference Manual, "Statement Summary Tables" (29.12.20.3, performance-schema-statement-summary-tables.html): `events_statements_summary_by_digest` summarizes per schema and digest; "The Slow Query Log" (7.4.5, slow-query-log.html): statements over `long_query_time`.
- Microsoft Learn, "Monitor Performance by Using the Query Store": the Query Store keeps several plans per query, and "plan forcing can resolve a query performance regression caused by a plan change in a very short period of time."
- PostgreSQL, "Using EXPLAIN" (14.1): "The thing that's usually most important to look for is whether the estimated row counts are reasonably close to reality"; `loops` is the number of executions of a node and actual values are per execution; `BUFFERS` shows pages hit, read, dirtied, and written (implied by `ANALYZE` from PostgreSQL 18). Looking at the lowest misestimated node first is practitioner reasoning (a misestimate propagates to every node above it), with no single published source; Leis et al. (below, "Inside engines") show errors compounding up a join tree.
- MySQL 8.0 Reference Manual, "EXPLAIN Statement," section "Obtaining Information with EXPLAIN ANALYZE": introduced in 8.0.18, runs the statement and reports actual time, rows, and loops per iterator.
- Microsoft Learn, "Display an Actual Execution Plan": an actual plan contains runtime information. SQLite, "EXPLAIN QUERY PLAN" (sqlite.org/eqp.html): a high-level description of the plan, with no timing.
- PostgreSQL, "PREPARE" (sql-prepare.html), Notes: with `plan_cache_mode` = `auto`, the first five executions use custom plans, and later ones use the generic plan if its cost is not much higher than the average custom plan's; `force_custom_plan` and `force_generic_plan` override. The docs say a custom plan can be much more efficient because the planner uses the parameter values; "skewed data" is this file's wording for when that happens.
- Microsoft Learn, "Query Processing Architecture Guide," section "Parameter sensitivity" ("also known as parameter sniffing"), and "Parameter Sensitive Plan optimization" (SQL Server 2022 and later): one cached plan for a parameterized query is not optimal for every value.
- Oracle Database 19c SQL Tuning Guide, "Improving Real-World Performance Through Cursor Sharing," sections "Bind Variable Peeking" and "Adaptive Cursor Sharing": the optimizer peeks at bind values only at hard parse, so the plan may not suit all values; adaptive cursor sharing lets one statement use several plans.
- PostgreSQL, "auto_explain" (F.3, auto-explain.html): logs plans of statements slower than `auto_explain.log_min_duration`. PostgreSQL, "Populating a Database" (14.4.8, "Run ANALYZE Afterwards"): statistics after a bulk load. Extended statistics: "CREATE STATISTICS" (sql-createstatistics.html). That a forced plan freezes a choice is reasoning, consistent with the Query Store page's treatment of forcing as a response to a regression.

## Query shapes

- PostgreSQL, "Window Functions" tutorial (3.5, tutorial-window.html; `row_number`, running `sum`), "Window Functions" reference (9.22, functions-window.html; `lag`, `lead`, `rank`), and "Window Function Calls" (4.2.8, sql-expressions.html): "The default framing option is RANGE UNBOUNDED PRECEDING ... With ORDER BY, this sets the frame to be all rows from the partition start up through the current row's last ORDER BY peer" (so tied rows get the same running sum). That `ROW_NUMBER` among ties is arbitrary follows from the unspecified order of peers.
- SQLite, "Window Functions" (sqlite.org/windowfunctions.html), History: added in 3.25.0 (2018-09-15). MySQL 8.0 Reference Manual, "What Is New in MySQL 8.0": window functions added in 8.0. The O(n²) → O(n log n) estimate is counting (a self-join on `<` compares pairs; a window needs one sort per partition).
- Set-based statements: PostgreSQL "UPDATE" (`FROM`), "INSERT" (`INSERT ... SELECT`), and "DELETE" (`USING`) reference pages. Their atomicity follows from a statement being atomic; per-row versus statement-level triggers: "CREATE TRIGGER" (below, "Behavior traps"). The round-trip saving is counting.
- PostgreSQL, "Subquery Expressions" (9.24, functions-subquery.html): "if there are no equal right-hand values and at least one right-hand row yields null, the result of the NOT IN construct will be null, not true"; `EXISTS` only tests whether any row is returned. That planners run `NOT EXISTS` as an anti-join: "Planner/Optimizer" (51.5) lists the join methods; the anti-join transformation itself is implementation behavior visible in plans (`Hash Anti Join`), not stated in the documentation.
- Semi-join versus `JOIN` + `DISTINCT`: PostgreSQL "SELECT," `DISTINCT` clause (removes all duplicate rows from the result, including rows duplicated in the outer table); the equivalence condition is reasoning.
- PostgreSQL, "SELECT," UNION Clause: "duplicate rows are eliminated unless ALL is specified"; "Combining Queries" (7.4, queries-union.html): UNION eliminates duplicates "in the same way as DISTINCT."
- Scalar subqueries: PostgreSQL, "Scalar Subqueries" (4.2.11, sql-expressions.html): a scalar subquery returning more than one row is an error, and one returning no rows yields NULL. `COUNT` of no rows is 0 and other aggregates return NULL: "Aggregate Functions" (9.21, functions-aggregate.html). "LATERAL Subqueries" (7.2.1.5, queries-table-expressions.html).
- PostgreSQL, "WITH Queries (Common Table Expressions)" (7.8, queries-with.html): a non-recursive, side-effect-free CTE (a `SELECT` with no volatile functions) referenced once is folded into the parent query by default; `MATERIALIZED` and `NOT MATERIALIZED`. PostgreSQL 12 Release Notes, Optimizer: "Previously, CTEs were never inlined and were always evaluated before the rest of the query."
- Parameter limits: PostgreSQL protocol "Message Formats" (54.7), Bind message: the parameter count is an Int16; libpq source `src/interfaces/libpq/libpq-fe.h` defines `PQ_QUERY_PARAM_MAX_LIMIT 65535` (implementation, not documentation). Microsoft Learn, "Maximum capacity specifications for SQL Server": 2,100 parameters per stored procedure. SQLite, "Implementation Limits For SQLite": `SQLITE_MAX_VARIABLE_NUMBER` defaults to 999 before 3.32.0 and 32766 after. PostgreSQL "Row and Array Comparisons" (9.25.3, `ANY` with an array). That each distinct `IN` list length is a distinct statement text (and so a separate entry in statement caches and in `pg_stat_statements`-style statistics) is reasoning from how those caches key statements; no single source.
- Keyset walk: the keyset row and its sources in `docs/sources/CORE-TECHNIQUES.md`; Markus Winand, *Use The Index, Luke*, "Paging Through Results" (use-the-index-luke.com/sql/partial-results/fetch-next-page; the "seek method"). Snapshot held by a cursor: "Long transactions" sources below.

## Indexes beyond the basics

- PostgreSQL, "CREATE INDEX" (sql-createindex.html): a standard build "locks out writes (but not reads)"; `CONCURRENTLY` takes longer, can leave an invalid index on failure, and cannot run in a transaction block. Microsoft Learn, "CREATE INDEX (Transact-SQL)," `ONLINE = ON` (not available in every edition). MySQL 8.4, "Online DDL Operations" (17.12.1): adding a secondary index permits concurrent reads and writes.
- Markus Winand, *Use The Index, Luke*, "Insert" (use-the-index-luke.com/sql/dml/insert): "The number of indexes is therefore a multiplier for the cost of an insert statement."
- PostgreSQL, "Index-Only Scans and Covering Indexes" (11.9, indexes-index-only-scans.html): `INCLUDE`; the visibility map bit is checked and the heap visited when it is not set; a win only when a significant fraction of pages are all-visible. "Routine Vacuuming," "Updating the Visibility Map" (24.1.4): vacuum maintains the map. PostgreSQL 11 Release Notes: covering indexes with `INCLUDE`. Microsoft Learn, "Create Indexes with Included Columns." Winand, "Index-Only Scan: Avoiding Table Access" (use-the-index-luke.com/sql/clustering/index-only-scan-covering-index). "Heap Fetches" is the `EXPLAIN ANALYZE` output field for index-only scans (implementation behavior).
- PostgreSQL, "Partial Indexes" (11.8, indexes-partial.html): usable only if the planner recognizes that the query's `WHERE` implies the index predicate, at planning time, so "parameterized query clauses do not work with a partial index." SQLite, "Partial Indexes" (sqlite.org/partialindex.html), section "Queries Using Partial Indexes." Microsoft Learn, "Create Filtered Indexes." The SQL Server limitation with parameterized queries is not in Microsoft's reference pages; it is shown in an archived Microsoft blog post, Tim Chapman, "The Pains of Filtered Indexes" (learn.microsoft.com/en-us/archive/blogs/timchapman/the-pains-of-filtered-indexes), a practitioner source. Winand, "Partial Indexes: Indexing Selected Rows" (use-the-index-luke.com/sql/where-clause/partial-and-filtered-indexes). Unique partial indexes enforcing uniqueness only among covered rows: PostgreSQL 11.8, Example 11.3.
- PostgreSQL, "Indexes on Expressions" (11.7, indexes-expressional.html): expressions are computed on every insert and non-HOT update; "CREATE INDEX": functions in index expressions must be `IMMUTABLE`. MySQL 8.0, "CREATE INDEX Statement," "Functional Key Parts" (8.0.13 and later). SQLite, "Indexes On Expressions" (sqlite.org/expridx.html). Oracle 19c Database Concepts, "Overview of Function-Based Indexes." Winand, "Functions" (use-the-index-luke.com/sql/where-clause/functions).
- Unused and redundant indexes: PostgreSQL "The Cumulative Statistics System" (27.2), `pg_stat_all_indexes.idx_scan`, and "Statistics Functions": `pg_stat_reset()`, and counters reset after a crash or recovery. MySQL 8.0 sys schema, "The schema_unused_indexes View" (meaningful only after a representative workload) and "The schema_redundant_indexes and x$schema_flattened_keys Views." Microsoft Learn, "sys.dm_db_index_usage_stats": counters are emptied whenever the engine starts. MySQL 8.0, "Invisible Indexes" (test removing an index without a destructive change; not for primary keys). Oracle 19c Administrator's Guide, "Managing Indexes," "Understand When to Use Unusable or Invisible Indexes." PostgreSQL "Constraints," "Foreign Keys" (5.5.5): deleting from the referenced table scans the referencing table, and the referencing columns are not indexed automatically. That counters are per server (replicas count their own queries) follows from the counters being local statistics; implementation behavior.
- PostgreSQL, "Heap-Only Tuples (HOT)" (66.7, storage-hot.html): HOT requires that the update modifies no column referenced by the table's indexes, summarizing indexes (BRIN) excepted, and that the page has free space. That indexing a frequently updated column therefore costs index entries on each update is inference from that page.

## Writes and transactions

- PostgreSQL, "Populating a Database" (14.4): disable autocommit, use `COPY`, remove indexes and foreign keys and recreate them, run `ANALYZE` afterwards. MySQL 8.4, "Optimizing INSERT Statements": multiple-row `VALUES` lists are many times faster than single-row inserts; `LOAD DATA` is usually 20 times faster than `INSERT`. SQLite FAQ, question 19: 50,000 or more inserts per second but only a few dozen transactions per second; wrap inserts in `BEGIN` ... `COMMIT`.
- JDBC: Java SE 21 API, `java.sql.Statement.executeBatch()`: on failure a `BatchUpdateException` is thrown, and the driver may or may not continue. pgJDBC documentation, "Initializing the Driver," `reWriteBatchedInserts`. MySQL Connector/J Developer Guide, "Performance Extensions," `rewriteBatchedStatements`.
- Hibernate ORM 6.6 User Guide, "Using IDENTITY columns": Hibernate cannot batch inserts for entities using `IDENTITY`; "JDBC batching": `hibernate.jdbc.batch_size`.
- Batched commits, split transactions, and their visibility and atomicity effects: reasoning from transaction atomicity (PostgreSQL tutorial, "Transactions," 3.4) and rule 5; the crash-loss window follows from uncommitted work being rolled back. Martin Kleppmann, *Designing Data-Intensive Applications* (2017), Chapter 11, for idempotent replay.
- PostgreSQL, "INSERT," ON CONFLICT Clause: "ON CONFLICT DO UPDATE guarantees an atomic INSERT or UPDATE outcome ... even under high concurrency"; arbiters are unique indexes or constraints. SQLite, "UPSERT" (sqlite.org/lang_upsert.html): added in 3.24.0. MySQL 8.0, "INSERT ... ON DUPLICATE KEY UPDATE Statement": affected rows 1 for an insert, 2 for an update, 0 when unchanged; avoid on tables with multiple unique indexes. Microsoft Learn, "MERGE (Transact-SQL)," "Concurrency considerations for MERGE": `HOLDLOCK` prevents unique key violations in some scenarios where keys are both inserted and updated. Lost updates in read-modify-write: Berenson et al. (below), anomaly P4.
- Long transactions: PostgreSQL "Client Connection Defaults" (19.11), `idle_in_transaction_session_timeout`: an open transaction prevents vacuuming away recently dead tuples and can contribute to bloat; "Routine Vacuuming" (24.1). The version-column check is the standard optimistic concurrency pattern (Kleppmann, Chapter 7, "Preventing Lost Updates," compare-and-set; section checked against secondary summaries of the book, not the printed text).
- Hot rows: PostgreSQL, "Sequence Manipulation Functions" (9.17): `nextval` values are not reclaimed when a transaction aborts, so sequences have gaps and cannot be gapless. Spreading a counter over several rows is a standard pattern with no single primary source; its read cost is counting.
- Deadlocks: PostgreSQL, "Explicit Locking," "Deadlocks" (13.3.4): deadlocks are detected and one transaction aborted; the best defense is acquiring locks in a consistent order. Microsoft Learn, "Deadlocks Guide," "Minimize deadlocks": access objects in the same order, keep transactions short. Retries repeating outside effects: reasoning ("Optimistic and speculative execution" in `BEHAVIOR-TRAPS.md`).
- `SKIP LOCKED`: PostgreSQL, "SELECT," The Locking Clause: "Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table." MySQL 8.0, "Locking Reads": the same caution. Loss of strict FIFO order follows from workers skipping rows others hold.
- Isolation: PostgreSQL, "Transaction Isolation" (13.2): Read Committed default; Repeatable Read and Serializable applications must retry serialization failures; Table 13.1 of anomalies. Hal Berenson, Phil Bernstein, Jim Gray, Jim Melton, Elizabeth O'Neil, and Patrick O'Neil, "A Critique of ANSI SQL Isolation Levels," SIGMOD 1995: lost update (P4), read skew and write skew (A5A, A5B), and write skew under snapshot isolation (§4.2). Microsoft Learn, "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)": with `READ_COMMITTED_SNAPSHOT` on, statements read a snapshot as of statement start (instead of waiting for writers). MySQL 8.0, "Transaction Isolation Levels": InnoDB defaults to `REPEATABLE READ`.

## Schema and data layout

- PostgreSQL, "Table Partitioning" (5.12, ddl-partitioning.html): benefits when the table would exceed physical memory; partition pruning at planning and execution time (5.12.4); too many partitions raise planning time and memory (5.12.6); unique and primary keys must include all partition key columns (5.12.2.3, Limitations). PostgreSQL "TRUNCATE" and "ALTER TABLE ... DETACH PARTITION": dropping or detaching a partition is not a row-level `DELETE`, so no `DELETE` triggers fire (inference from "CREATE TRIGGER": row-level triggers fire on the rows an `INSERT`, `UPDATE`, or `DELETE` affects). Rows moving between partitions on key update: "UPDATE," Notes.
- PostgreSQL, "Generated Columns" (5.4): a stored generated column is computed when written (PostgreSQL 18 defaults to virtual columns, computed when read). "REFRESH MATERIALIZED VIEW": `CONCURRENTLY` requires a unique index; "Materialized Views" (39.3): the data is not always current. Incremental maintenance: `docs/sources/techniques/data-at-scale.md`.
- RFC 9562, "Universally Unique IDentifiers (UUIDs)," 2024: Section 2, Motivation, item 1 (UUIDv4 has "poor database-index locality," inserts at random locations, "dramatic" effects on B-trees); §5.7 (UUIDv7 time-ordered from a Unix timestamp); §6.11. That UUIDv7 reveals creation time follows from §5.7 (the timestamp is in the value).
- Text versus native types: comparison and conversion rules in PostgreSQL "Data Types" (Chapter 8) and "Type Conversion" (Chapter 10); the examples are reasoning, with no single source.

## Connections and round trips

- PostgreSQL, "How Connections Are Established" (51.2): a backend process per connection. HikariCP wiki, "About Pool Sizing" (github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing): pool size near `(core_count × 2) + effective_spindle_count`; small pools outperform large ones (a practitioner source quoting a formula from the PostgreSQL project).
- PgBouncer, "Features" (pgbouncer.org/features.html): transaction pooling breaks session features (`SET`/`RESET`, `LISTEN`, `WITH HOLD` cursors, SQL-level `PREPARE`, session advisory locks); protocol-level prepared statements need `max_prepared_statements` (added in 1.21.0, per the changelog).
- PostgreSQL, "Pipeline Mode" (32.5, libpq-pipeline-mode.html): sending queries without waiting for results; most useful at high network latency; after an error the server skips commands until the next sync point. PostgreSQL 14 Release Notes: pipeline mode added to libpq. JDBC `executeBatch` (above).
- Django documentation, "QuerySet API reference": `select_related` uses an SQL join for single-valued relationships; `prefetch_related` does a separate lookup per relationship; `bulk_create`, `bulk_update`, and `update()` do not call `save()` or send `pre_save`/`post_save` signals. "Database access optimization" (topics/db/optimization/).
- Hibernate ORM User Guide, "Fetching" (dynamic fetching via queries and entity graphs; batch and subselect fetching) and "join fetch for association fetching": fetching several collections in parallel gives a Cartesian product.
- Rails Guides, "Active Record Query Interface," "Eager Loading Associations" (`includes`, `preload`, `eager_load`). Rails API, `ActiveRecord::Relation`: `insert_all` and `update_all` do not trigger callbacks or validations.

## Inside engines

- P. Griffiths Selinger, M. M. Astrahan, D. D. Chamberlin, R. A. Lorie, and T. G. Price, "Access Path Selection in a Relational Database Management System," SIGMOD 1979: cost from catalog statistics; nested loops and merging scans; "interesting orders" (§4–5).
- Goetz Graefe, "Query Evaluation Techniques for Large Databases," *ACM Computing Surveys* 25(2), 1993: §5.1–5.5 (nested-loops including index nested loops, merge join, hash join, comparison) and §2.2 and §5.3 (hash table overflow and partitioning to disk). PostgreSQL, "Planner/Optimizer" (51.5): nested loop, merge, and hash joins. Hash joins on equality only and the complexity figures are standard results (Graefe §5).
- Viktor Leis, Andrey Gubichev, Atanas Mirchev, Peter Boncz, Alfons Kemper, and Thomas Neumann, "How Good Are Query Optimizers, Really?" *PVLDB* 9(3), 2015: errors grow with joins and are systematically underestimates (§3.2); cost-model errors dwarfed by cardinality errors (§1, §5); non-index nested-loop joins on underestimates cause most timeouts, removed by disabling them (§4.1).
- Mike Stonebraker, Daniel J. Abadi, Adam Batkin, et al., "C-Store: A Column-oriented DBMS," VLDB 2005. Daniel J. Abadi, Samuel R. Madden, and Nabil Hachem, "Column-Stores vs. Row-Stores: How Different Are They Really?" SIGMOD 2008: column stores win on read-mostly analytics; emulating them in a row store performs poorly; gains come from compression, late materialization, block iteration, and the invisible join (§5–6).
- Peter Boncz, Marcin Zukowski, and Niels Nes, "MonetDB/X100: Hyper-Pipelining Query Execution," CIDR 2005: tuple-at-a-time interpretation overhead (§1, §3); vectors of about 1,000 cache-resident values (§4). Thomas Neumann, "Efficiently Compiling Efficient Query Plans for Modern Hardware," *PVLDB* 4(9), 2011 (bibliographic data checked; the content claim, compiling queries to tight loops, is the paper's title subject).
- Group commit: David J. DeWitt, Randy H. Katz, Frank Olken, Leonard D. Shapiro, Michael R. Stonebraker, and David A. Wood, "Implementation Techniques for Main Memory Database Systems," SIGMOD 1984, §5.2 (the "commit group": several commit records share one log write; the paper calls the idea database folklore, so this is its first description in print, not its invention). PostgreSQL, "Write Ahead Log" settings (19.5), `commit_delay`; "Asynchronous Commit" (28.4): the most recent transactions may be lost in a crash, without corruption. MySQL 8.0, "Replication and Binary Logging Options and Variables," `binlog_group_commit_sync_delay`; "InnoDB Startup Options and System Variables," `innodb_flush_log_at_trx_commit`: settings 0 and 2 can lose about one second of transactions in a crash (once-per-second flushing not guaranteed).
- Buffer replacement: Elizabeth J. O'Neil, Patrick E. O'Neil, and Gerhard Weikum, "The LRU-K Page Replacement Algorithm for Database Disk Buffering," SIGMOD 1993 (LRU cannot tell frequent from infrequent references, §1.2; scans swamping LRU, §1.1). Theodore Johnson and Dennis Shasha, "2Q: A Low Overhead High Performance Buffer Management Replacement Algorithm," VLDB 1994 (constant-time, as good as LRU/2, scan resistant). F. J. Corbató, "A Paging Experiment with the Multics System," in *In Honor of Philip M. Morse*, MIT Press, 1969 (the circular-list use-bit algorithm later called CLOCK). PostgreSQL source, `src/backend/storage/buffer/README`: clock sweep with usage counts, and "Buffer Ring Replacement Strategy" for large sequential scans, VACUUM, and bulk writes. MySQL 8.4, "Making the Buffer Pool Scan Resistant" (17.8.3.3): midpoint insertion, `innodb_old_blocks_pct`, `innodb_old_blocks_time`. That CLOCK avoids reordering a list on every hit follows from the algorithm (a hit only sets a bit).
- Viktor Leis, Alfons Kemper, and Thomas Neumann, "The Adaptive Radix Tree: ARTful Indexing for Main-Memory Databases," ICDE 2013: node types of 4, 16, 48, and 256 children; path compression and lazy expansion; height depends on key length, not the number of keys; binary-comparable keys (§IV); faster than main-memory B-tree variants and comparable to hash tables, while keeping order for range scans (§V–VI).

## Behavior traps

- Order: PostgreSQL "SELECT" ("If ORDER BY is not given, the rows are returned in whatever order the system finds fastest to produce") and "Sorting Rows" (7.5: the order "will depend on the scan and join plan types and the order on disk, but it must not be relied on"); "Version and Platform Compatibility" (19.13.1), `synchronize_seqscans`: unpredictable changes in row order for queries without `ORDER BY`. SQLite, "SELECT," ORDER BY clause: order undefined without it; "Pragma statements," `reverse_unordered_selects`.
- NULLs: PostgreSQL 9.24 (above) for `NOT IN`; "Comparison Functions and Operators" (9.2) for `= NULL`; "Aggregate Functions" (9.21) for `COUNT(column)` and `SUM` of no rows. NULL order: PostgreSQL "Sorting Rows" (7.5: nulls sort as larger than any non-null value); MySQL 8.4, "Working with NULL Values" (first for `ASC`); SQLite "SELECT" (NULLs smaller than any other value); Microsoft Learn, "ORDER BY Clause (Transact-SQL)" (NULLs are the lowest values).
- Collation: MySQL 8.0, "Server Character Set and Collation" (default `utf8mb4_0900_ai_ci`) and "Unicode Character Sets" (accent- and case-insensitive). PostgreSQL "Collation Support" (23.2, nondeterministic collations) and "Operator Classes and Operator Families" (11.10, `text_pattern_ops` for `LIKE` outside the C locale).
- Isolation and visibility: sources under "Writes and transactions" above.
- Triggers: PostgreSQL "CREATE TRIGGER": row-level triggers fire once per row, statement-level once per statement even for zero rows; "TRUNCATE": fires no `ON DELETE` triggers. Microsoft Learn, "Create DML Triggers to Handle Multiple Rows of Data": one trigger invocation for a statement affecting many rows. "No promised order" of row-trigger firing within a statement follows from the unspecified row order of the statement; no explicit source. PostgreSQL "CREATE TABLE," Compatibility, "Non-Deferred Uniqueness Constraints": non-deferrable unique constraints are checked immediately per row, unlike the standard's end of statement (the `pos + 1` example is this file's).
- Timeouts and locks: PostgreSQL "Client Connection Defaults" (19.11), `statement_timeout` and `lock_timeout`. Microsoft Learn, "Transaction Locking and Row Versioning Guide," "Lock escalation thresholds": a statement acquiring at least 5,000 locks on one table or index. That a waiting lock request blocks later conflicting requests behind it follows from PostgreSQL's lock queue ("Explicit Locking," 13.3, table-level lock conflicts); stated there implicitly, and a well-known practitioner point for migrations.
- Replica lag: PostgreSQL "Hot Standby" (26.4): a measurable delay between primary and standby, changes visible once the commit record is replayed, and query conflicts can cancel standby queries (26.4.2).
