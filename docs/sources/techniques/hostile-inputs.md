# Sources for `skills/algorithmic-intelligence/references/techniques/hostile-inputs.md`

Where each claim in that file comes from, for maintainers and reviewers. Not part of the installed skill.

- Moritz Hardt and David P. Woodruff, "How Robust Are Linear Sketches to Adaptive Inputs?", STOC 2013.
- Omri Ben-Eliezer, Rajesh Jayaram, David P. Woodruff, and Eylon Yogev, "A Framework for Adversarially Robust Streaming Algorithms," PODS 2020; Avinatan Hassidim, Haim Kaplan, Yishay Mansour, Yossi Matias, and Uri Stemmer, "Adversarially Robust Streaming Algorithms via Differential Privacy," NeurIPS 2020.
- Sara Ahmadian and Edith Cohen, "Unmasking Vulnerabilities: Cardinality Sketches under Adaptive Inputs," ICML 2024; Edith Cohen, Jelani Nelson, Tamás Sarlós, Mihir Singhal, and Uri Stemmer, "One Attack to Rule Them All: Tight Quadratic Bounds for Adaptive Queries on Cardinality Sketches," arXiv preprint, 2024 (a later conference publication is reported but was not verified; the skill file cites the preprint).
- Scott A. Crosby and Dan S. Wallach, "Denial of Service via Algorithmic Complexity Attacks," USENIX Security 2003.
- M. Douglas McIlroy, "A Killer Adversary for Quicksort," *Software: Practice and Experience* 29(4), 1999; David R. Musser, "Introspective Sorting and Selection Algorithms," *Software: Practice and Experience* 27(8), 1997.
- Jean-Philippe Aumasson and Daniel J. Bernstein, "SipHash: A Fast Short-Input PRF," INDOCRYPT 2012.
- Paul C. Kocher, "Timing Attacks on Implementations of Diffie-Hellman, RSA, DSS, and Other Systems," CRYPTO 1996.
- Oscar Reparaz, Josep Balasch, and Ingrid Verbauwhede, "Dude, Is My Code Constant Time?", DATE 2017.
- Caroline Lemieux et al., "PerfFuzz: Automatically Generating Pathological Inputs," ISSTA 2018; Theofilos Petsios et al., "SlowFuzz: Automated Domain-Independent Detection of Algorithmic Complexity Vulnerabilities," CCS 2017.
- Reinhard Wilhelm et al., "The Worst-Case Execution-Time Problem," *ACM Transactions on Embedded Computing Systems* 7(3), 2008.
- Unicode Technical Report #36, "Unicode Security Considerations," and Unicode Technical Standard #39, "Unicode Security Mechanisms": normalization, case folding, confusables, and non-ASCII digits in parsers.
- Juliano Rizzo and Thai Duong, "The CRIME Attack," Ekoparty 2012; Yoel Gluck, Neal Harris, and Angelo Prado, "BREACH: Reviving the CRIME Attack," Black Hat USA 2013.
- JavaScript hash seeding: V8 seeds string hashes (the `--hash-seed` flag and `src/numbers/hash-seed` in the V8 source), while integer-like keys are not hashed with the seed; Node.js startup snapshots once fixed the seed until it was rehashed at startup (the `--rehash-snapshot` V8 option). See also `docs/sources/languages/JAVASCRIPT-TYPESCRIPT.md`.

Cryptography performance:

- Shay Gueron, "Intel Advanced Encryption Standard (AES) New Instructions Set," Intel white paper, revision 3.0 (2010): hardware AES and carry-less multiplication for GCM, and their freedom from table-based cache timing; Arm, *Arm Architecture Reference Manual for A-profile*, Cryptographic Extension (AES, SHA instructions). Vendor documentation.
- Daniel J. Bernstein, "Cache-Timing Attacks on AES" (2005); Dag Arne Osvik, Adi Shamir, and Eran Tromer, "Cache Attacks and Countermeasures: The Case of AES," CT-RSA 2006: table-based AES leaks keys through cache timing.
- RFC 8446, "The Transport Layer Security (TLS) Protocol Version 1.3": section 2.2 (resumption and pre-shared keys), 2.3 and 8 ("0-RTT and Anti-Replay": early data is not protected against replay); RFC 5077, "TLS Session Resumption without Server-Side State" (session tickets, ticket-key protection and rotation).
- NIST SP 800-38D, "Recommendation for Block Cipher Modes of Operation: Galois/Counter Mode (GCM) and GMAC" (2007), section 8 (uniqueness requirement on IVs and the limits on invocations per key); Antoine Joux, "Authentication Failures in NIST Version of GCM," comment to NIST (2006): nonce reuse reveals the authentication key; Hanno Böck, Aaron Zauner, Sean Devlin, Juraj Somorovsky, and Philipp Jovanovic, "Nonce-Disrespecting Adversaries: Practical Forgery Attacks on GCM in TLS," USENIX WOOT 2016; RFC 8439, "ChaCha20 and Poly1305 for IETF Protocols," section 4 (security considerations: a nonce must never repeat under the same key).
- RFC 8439, section 1: ChaCha20 is "considerably faster than AES in software-only implementations," about three times as fast on platforms without AES hardware.
- Daniel J. Bernstein, Niels Duif, Tanja Lange, Peter Schwabe, and Bo-Yin Yang, "High-Speed High-Security Signatures," CHES 2011, and ed25519.cr.yp.to: batch verification of 64 signatures in under 134,000 cycles per signature against about 273,000 for a single verification, on the processors measured there; signing about 87,500 cycles. RSA-2048 signing costs millions of cycles on comparable processors (eBACS benchmarks, bench.cr.yp.to, "ebats" signature results). Measurements of specific implementations.
- Konstantinos Chalkias, François Garillot, and Valeria Nikolaenko, "Taming the Many EdDSAs," Security Standardisation Research (SSR) 2020, IACR ePrint 2020/1244: batch and single Ed25519 verification disagree on some signatures, and libraries differ; Zcash Improvement Proposal 215, "Explicitly Defining and Modifying Ed25519 Validation Rules" (zips.z.cash/zip-0215): validation rules under which batch and single verification agree.
- OWASP Password Storage Cheat Sheet (cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html): current work-factor guidance for Argon2id, scrypt, bcrypt, and PBKDF2, and upgrading hashes at the next login; RFC 9106, "Argon2 Memory-Hard Function for Password Hashing and Proof-of-Work Applications"; NIST SP 800-132, "Recommendation for Password-Based Key Derivation" (iteration count as the cost to an attacker); NIST SP 800-63B, section 5.1.1.2 (memorized secret verifiers, salted with a costly key-derivation function).
- Niels Ferguson, Bruce Schneier, and Tadayoshi Kohno, *Cryptography Engineering* (2010): verify authentication before decrypting or acting on data, and use established primitives and constructions rather than designing new ones; RFC 2104, "HMAC," section 1 (the HMAC construction instead of a bare keyed hash, whose weaknesses such as length extension it avoids); NIST SP 800-38D, appendix C (minimum tag lengths for GCM).
