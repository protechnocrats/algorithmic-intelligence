# Sources for `skills/algorithmic-intelligence/references/techniques/accelerators.md`

Where each claim in that file comes from, for maintainers and reviewers. Not part of the installed skill. The "When offload pays" and "Data-parallel algorithms and structures" entries moved here from `docs/sources/techniques/hardware-and-concurrency.md` with their sections.

## When offload pays

Also the source of the floating-point, reduced-precision, and availability items in "Behavior traps", and of the determinism paragraph in "Measuring and verifying on a device" (moved from the former deterministic-kernels row).


- Samuel Williams, Andrew Waterman, and David Patterson, "Roofline: An Insightful Visual Performance Model for Multicore Architectures," *Communications of the ACM* 52(4), 2009: arithmetic intensity decides whether a kernel is bound by memory bandwidth or compute.
- Chris Gregg and Kim Hazelwood, "Where Is the Data? Why You Cannot Debate CPU vs. GPU Performance Without the Answer," ISPASS 2011: transfer time over the host-device link can dominate and must be counted in comparisons.
- Victor W. Lee et al., "Debunking the 100X GPU vs. CPU Myth: An Evaluation of Throughput Computing on CPU and GPU," ISCA 2010: against optimized CPU code, throughput kernels ran about 2.5 times faster on the GPU on average, not 100 times; the basis for "several times faster" in the offload row.
- NVIDIA, *CUDA C++ Best Practices Guide* (docs.nvidia.com/cuda/cuda-c-best-practices-guide/), cited by section name (numbers as of the current edition, which may shift): "What Runs on a CUDA-Enabled Device?" (3.2; bullet: data should be kept on the device as long as possible); "Data Transfer Between Host and Device" (10.1; minimize transfers "even if it means running some kernels on the device that do not show performance gains"; peak device memory bandwidth "898 GB/s on the NVIDIA Tesla V100" against "16 GB/s on the PCIe x16 Gen3"); "Pinned Memory" (10.1.1; "Pinned memory should not be overused. Excessive use can reduce overall system performance"); "Asynchronous and Overlapping Transfers with Computation" (10.1.2; streams); "Coalesced Access to Global Memory" (10.2.1); "Occupancy" (11.1; "Higher occupancy does not always equate to higher performance"); "Branching and Divergence" (13.1). Vendor documentation of implementation behavior.
- NVIDIA, *CUDA Programming Guide*, sections "CUDA Graphs" (launch sequences captured once and replayed) and "Floating-Point Computation" (subsections "Fused Multiply-Add (FMA)" and "CUDA and IEEE-754 Compliance"); Nathan Whitehead and Alex Fit-Florea, "Precision & Performance: Floating Point and IEEE 754 Compliance for NVIDIA GPUs," NVIDIA white paper (2011): fused multiply-add contraction and differing results between CPU and GPU.
- PyTorch documentation, "Reproducibility" notes (docs.pytorch.org/docs/stable/notes/randomness.html): results "may not be reproducible between CPU and GPU executions," nor across releases or platforms; `torch.use_deterministic_algorithms` raises an error for operations without a deterministic implementation; some backward passes use nondeterministic atomic operations. Implementation behavior of one framework, cited as an example.
- PyTorch documentation, "CUDA semantics," section "TensorFloat-32 (TF32) on Ampere (and later) devices": the matmul TF32 flag defaulted to true in 1.7 through 1.11 and false from 1.12, while the cuDNN convolution flag defaults to true; newer releases add `fp32_precision` settings. Implementation behavior, cited as an example of defaults that differ between operations and releases.
- Paulius Micikevicius et al., "Mixed Precision Training," ICLR 2018: half-precision storage with single-precision accumulation and loss scaling.

## Data-parallel algorithms and structures

- Wen-mei W. Hwu, David B. Kirk, and Izzat El Hajj, *Programming Massively Parallel Processors: A Hands-on Approach*, 4th ed. (Morgan Kaufmann, 2022): warp execution and control divergence, tiling with shared memory for matrix multiplication and stencils (halo cells), privatized histograms, reduction and scan, stream compaction, merge, sorting, sparse formats, and graph traversal chapters.
- Guy E. Blelloch, "Prefix Sums and Their Applications," CMU-CS-90-190 (1990): scan, segmented scan, and compaction by scan; Shubhabrata Sengupta, Mark Harris, Yao Zhang, and John D. Owens, "Scan Primitives for GPU Computing," Graphics Hardware 2007 (segmented scan, compaction on GPUs); Duane Merrill and Michael Garland, "Single-pass Parallel Prefix Scan with Decoupled Look-back," NVIDIA Technical Report NVR-2016-002 (2016); Mark Harris, "Optimizing Parallel Reduction in CUDA," NVIDIA developer presentation (2007).
- NVIDIA CCCL documentation: CUB `DeviceRadixSort` (nvidia.github.io/cccl/unstable/cub/api/structcub_1_1DeviceRadixSort.html: the sort is stable, floating-point keys are bit-transformed, and −0.0 and +0.0 are treated as equivalent); CUB `DeviceReduce` and "Determinism" (nvidia.github.io/cccl/unstable/cub/determinism.html: not-guaranteed, run-to-run, and GPU-to-GPU determinism levels for floating-point reductions); NVIDIA developer blog, "Controlling Floating-Point Determinism in NVIDIA CCCL" (March 2026; the three levels, with `run_to_run` the default for reductions). Implementation behavior of one library, cited as an example.
- Duane Merrill and Andrew Grimshaw, "High Performance and Scalable Radix Sorting: A Case Study of Implementing Dynamic Parallelism for GPU Computing," *Parallel Processing Letters* 21(2), 2011; Nadathur Satish, Mark Harris, and Michael Garland, "Designing Efficient Sorting Algorithms for Manycore GPUs," IPDPS 2009 (radix sort and merge sort on GPUs).
- Oded Green, Robert McColl, and David A. Bader, "GPU Merge Path: A GPU Merging Algorithm," ICS 2012; Saher Odeh, Oded Green, Zahi Mwassi, Oz Shmueli, and Yitzhak Birk, "Merge Path: Parallel Merging Made Simple," IPDPS Workshops 2012 (cross-diagonal partitioning into equal pieces).
- Sort-based against hash-based grouping and joins on GPUs: Tim Kaldewey, Guy Lohman, René Mueller, and Peter Volk, "GPU Join Processing Revisited," DaMoN 2012; Panagiotis Sioulas, Periklis Chrysogelos, Manos Karpathiotakis, Raja Appuswamy, and Anastasia Ailamaki, "Hardware-Conscious Hash-Joins on GPUs," ICDE 2019 (the measured winner depends on data size and key distribution, hence "measure both").
- Duane Merrill, Michael Garland, and Andrew Grimshaw, "Scalable GPU Graph Traversal," PPoPP 2012 (frontier-based BFS with scan-based expansion and load balancing by degree); Scott Beamer, Krste Asanović, and David Patterson, "Direction-Optimizing Breadth-First Search," SC 2012; Yangzihao Wang et al., "Gunrock: A High-Performance Graph Processing Library on the GPU," PPoPP 2016 (binning work by degree); Duane Merrill and Michael Garland, "Merge-Based Parallel Sparse Matrix-Vector Multiplication," SC 2016 (merge-path load balancing over row boundaries and nonzeros).
- G. M. Morton, "A Computer Oriented Geodetic Data Base and a New Technique in File Sequencing," IBM technical report (1966); Simon Green, "Particle Simulation using CUDA," NVIDIA white paper (2010) (uniform grid built by sorting particles by cell, cell start and end offsets); Christian Lauterbach, Michael Garland, Shubhabrata Sengupta, David Luebke, and Dinesh Manocha, "Fast BVH Construction on GPUs," *Computer Graphics Forum* 28(2) (Eurographics 2009) (linear BVH from Morton codes, lower quality than surface-area-heuristic builds); Tero Karras, "Maximizing Parallelism in the Construction of BVHs, Octrees, and k-d Trees," High-Performance Graphics 2012 (all internal nodes built in parallel from common-prefix lengths; duplicate codes disambiguated by index).
- Vasily Volkov and James W. Demmel, "Benchmarking GPUs to Tune Dense Linear Algebra," SC 2008; NVIDIA cuBLAS documentation, "Results reproducibility" (algorithm choice and reproducibility across architectures and settings); NVIDIA cuDNN documentation on deterministic algorithm selection. Implementation behavior.
- Dan A. Alcantara et al., "Real-Time Parallel Hashing on the GPU," *ACM Transactions on Graphics* 28(5) (SIGGRAPH Asia 2009) (cuckoo hashing built in bulk with atomics, rebuild on failure); Saman Ashkiani, Martin Farach-Colton, and John D. Owens, "A Dynamic Hash Table for the GPU," IPDPS 2018 (concurrent inserts and deletes, slower than static tables); Muhammad A. Awad, Saman Ashkiani, Serban D. Porumbescu, Martín Farach-Colton, and John D. Owens, "Analyzing and Implementing GPU Hash Tables," SIAM Symposium on Algorithmic Principles of Computer Systems (APOCS) 2023 (open addressing, bucketed probing, load factor effects); NVIDIA cuCollections documentation (`static_map` built in bulk). Iteration order depending on scheduling follows from concurrent insertion with compare-and-swap.
- Flattened breadth-first tree layouts: Paul-Virak Khuong and Pat Morin, "Array Layouts for Comparison-Based Searching," *ACM Journal of Experimental Algorithmics* 22, 2017 (the Eytzinger layout; also cited in `docs/sources/techniques/hardware-and-concurrency.md`); Toby Sharp, "Implementing Decision Trees and Forests on a GPU," ECCV 2008 (trees stored as arrays with index arithmetic, traversed per thread).
- Warp vote and population-count operations (`__ballot_sync`, `__popc`): NVIDIA *CUDA Programming Guide*, "C/C++ Language Extensions," "Warp Functions," "Warp Vote Functions"; NVIDIA *CUDA Math API*, "Integer Intrinsics" (`__popc`); atomic bitwise operations (`atomicOr`, `atomicAnd`): "C/C++ Language Extensions," "Atomic Functions." Vendor documentation.

## Kernel-level techniques

- Warp-level primitives: NVIDIA *CUDA Programming Guide*, "C/C++ Language Extensions," "Warp Functions," subsections "Warp Shuffle Functions," "Warp Vote Functions," and "Warp __sync Intrinsic Constraints" (the `_sync` forms take a mask of participating threads); Yuan Lin and Vinod Grover, "Using CUDA Warp-Level Primitives," NVIDIA developer blog (January 2018): since Volta's independent thread scheduling, threads of a warp can diverge and reconverge independently, so implicit warp-synchronous code is unsafe and the explicit-mask forms are required; Andy Adinets, "CUDA Pro Tip: Optimized Filtering with Warp-Aggregated Atomics," NVIDIA developer blog (2014): one atomic per warp by a leader thread, offsets from ballot and population count. AMD's 64-wide wavefronts: AMD HIP documentation, "HIP C++ language extensions," `warpSize` note ("AMD devices return 64 for gfx9 and 32 for gfx10 and above"; it "should not be assumed to be a specific value in portable HIP applications") and "Warp cross-lane functions." Vendor documentation.
- Bank conflicts: NVIDIA *CUDA C++ Best Practices Guide*, "Shared Memory and Memory Banks" (10.2.3.1) ("if multiple addresses of a memory request map to the same memory bank, the accesses are serialized"); Mark Harris, "An Efficient Matrix Transpose in CUDA C/C++," NVIDIA developer blog (2013): padding the shared tile by one column removes the conflicts of column reads; NVIDIA CUTLASS, CuTe `Swizzle` functor (`include/cute/swizzle.hpp`: address bits XORed with higher bits) for XOR swizzling. That padding raises shared memory per block and can lower occupancy follows from the Best Practices Guide, "Effects of Shared Memory" (11.4; shared memory "can act as a constraint on occupancy").
- Register blocking and thread coarsening: Vasily Volkov, "Better Performance at Lower Occupancy," GTC 2010 (more outputs per thread, held in registers, beat higher occupancy); Volkov and Demmel (cited above); Hwu, Kirk, and El Hajj (cited above), 4th ed., "Thread coarsening" in chapter 6, "Performance considerations" (coarsening reduces redundant work and loads but can underuse the device and raise register pressure).
- Double buffering: NVIDIA *CUDA Programming Guide*, "Asynchronous Data Copies" (`memcpy_async`, multi-stage copies on compute capability 8.0 and later; subsection "Using the Tensor Memory Accelerator (TMA)") and "Pipelines" (`cuda::pipeline`); NVIDIA CUTLASS documentation, "Efficient GEMM in CUDA," section "Pipelining" (software pipelining by double buffering shared-memory tiles). NVIDIA *Compute Sanitizer* documentation (racecheck for shared-memory hazards, synccheck for invalid barrier use) for the race checker in the section lead-in.
- Persistent kernels: Kshitij Gupta, Jeff A. Stuart, and John D. Owens, "A Study of Persistent Threads Style GPU Programming for GPGPU Workloads," InPar 2012 (launch only enough blocks to fill the device, loop over a work queue; relies on all blocks being resident); Timo Aila and Samuli Laine, "Understanding the Efficiency of Ray Traversal on GPUs," HPG 2009 (persistent threads fetching from a global work pool); NVIDIA *CUDA Programming Guide*, "Cooperative Groups" (synchronizing the entire grid "requires using the cudaLaunchCooperativeKernel runtime launch API," which launches all blocks or fails).
- Matrix units: NVIDIA *CUDA Programming Guide*, "C/C++ Language Extensions," "Warp Matrix Functions" (`wmma`, supported fragment shapes and element types); Massimiliano Fasi, Nicholas J. Higham, Mantas Mikaitis, and Srikara Pranesh, "Numerical Behavior of NVIDIA Tensor Cores," *PeerJ Computer Science* 7:e330, 2021 (inner products are not IEEE-compliant: rounding and normalization of the accumulation differ by architecture); Stefano Markidis, Steven Wei Der Chien, Erwin Laure, Ivy Bo Peng, and Jeffrey S. Vetter, "NVIDIA Tensor Core Programmability, Performance & Precision," IPDPS Workshops 2018 (throughput against general-purpose cores, and the precision loss of half-precision inputs). The throughput statement is relative, not a fixed ratio, since it varies by generation.
- Sorting networks: Kenneth E. Batcher, "Sorting Networks and Their Applications," AFIPS Spring Joint Computer Conference 1968 (bitonic and odd-even merge networks, O(n log² n) comparators); Donald E. Knuth, *The Art of Computer Programming*, Vol. 3, 2nd ed. (1998), §5.3.4 "Networks for Sorting"; Peter Kipfer and Rüdiger Westermann, "Improved GPU Sorting," *GPU Gems 2*, chapter 46 (2005) (data-independent compare sequences suit GPUs). Instability follows from compare-exchange swapping equal keys across distant positions.
- Counter-based generators: John K. Salmon, Mark A. Moraes, Ron O. Dror, and David E. Shaw, "Parallel Random Numbers: As Easy as 1, 2, 3," SC 2011 (Philox and Threefry: output is a keyed bijection of a counter, so streams need no shared state and pass the TestU01 BigCrush battery); NVIDIA cuRAND documentation (Philox4_32_10 generator, offsets by subsequence). That a different generator changes seed-based expected values is the definition of a different sequence.
- Collectives: Pitch Patarasuk and Xin Yuan, "Bandwidth Optimal All-reduce Algorithms for Clusters of Workstations," *Journal of Parallel and Distributed Computing* 69(2), 2009 (ring all-reduce is bandwidth-optimal: each process sends 2(p − 1)/p of the data); Rajeev Thakur, Rolf Rabenseifner, and William Gropp, "Optimization of Collective Communication Operations in MPICH," *International Journal of High Performance Computing Applications* 19(1), 2005 (algorithm chosen by message size and process count); NVIDIA NCCL documentation, "Environment Variables," `NCCL_ALGO` (Ring, Tree, CollNet, NVLS, PAT, and others; NCCL chooses when unset), "Collective Operations" (collectives "have to be called for each rank," otherwise "undefined behavior, including hangs"), and "Creating a Communicator," "Using multiple NCCL communicators concurrently" (operations need a consistent order across devices, "otherwise deadlocks could ensue"). Results differing with the algorithm follow from floating-point non-associativity (Higham, *Accuracy and Stability of Numerical Algorithms*, 2nd ed., 2002, chapter 4).
- Memory pools and prefetching: NVIDIA *CUDA Programming Guide*, "Stream-Ordered Memory Allocator" (`cudaMallocAsync`, memory pools, the release threshold, reuse across streams after event dependencies); Vivek Kini and Jake Hemstad, "Using the NVIDIA CUDA Stream-Ordered Memory Allocator, Part 1," NVIDIA developer blog (July 2021) (`cudaMalloc` and `cudaFree` can synchronize the device); PyTorch documentation, "CUDA semantics," "Memory management" ("PyTorch uses a caching memory allocator to speed up memory allocations. This allows fast memory deallocation without device synchronizations"); Nikolay Sakharnykh, "Maximizing Unified Memory Performance in CUDA," NVIDIA developer blog (November 2017) (fault-driven migration against `cudaMemPrefetchAsync`). Vendor and framework documentation.

## Measuring and verifying on a device

- Asynchronous calls and timing: NVIDIA *CUDA C++ Best Practices Guide*, "Using CPU Timers" (9.1.1; "many CUDA API functions are asynchronous"; synchronize before starting and stopping a CPU timer) and "Using CUDA GPU Timers" (9.1.2) (events timed on the device clock); PyTorch documentation, "CUDA semantics," "Asynchronous execution" ("time measurements without synchronizations are not accurate"; `torch.cuda.synchronize()` or `torch.cuda.Event`; errors reported asynchronously, `CUDA_LAUNCH_BLOCKING=1`); JAX documentation, "Asynchronous dispatch" (only dispatch is timed without `block_until_ready()`; printing or converting to a NumPy array waits for the result).
- Benchmarks that leave out transfers: Chris Gregg and Kim Hazelwood, "Where is the Data? Why You Cannot Debate CPU vs. GPU Performance Without the Answer," IEEE ISPASS 2011 (published GPU speedups often omit the time to move data between host and device; including it changes the comparison substantially and can reverse it for some kernels); Lee et al., ISCA 2010 (cited above), for speedup claims shrinking against fair, complete measurements; the CUDA Best Practices Guide timer sections above for the missing synchronization. "Several times over" is an inference from these sources, not a measured constant.
- First-call cost: JAX documentation, "Benchmarking JAX code" ("the first time you run JAX code, it will be slower because it is being compiled," including built-in functions). Library autotuning on first call: cuDNN benchmark mode in PyTorch, `torch.backends.cudnn.benchmark` ("torch.backends" API reference; "Reproducibility" notes, "CUDA convolution benchmarking": cuDNN benchmarks several convolution algorithms for each new size, and may pick different ones on later runs). Implementation behavior, cited as examples.
- Device state: NVIDIA *Nsight Compute* Profiling Guide, "Workload Durations" (Nsight Compute "locks SM clocks by default" and "flushes all GPU caches by default between replay passes"; Nsight Systems does neither; lock clocks with `nvidia-smi` and pass `--clock-control none` to compare); NVIDIA *Nsight Systems* documentation for the timeline profiler; AMD ROCm profiler documentation (rocprof); Intel VTune Profiler documentation (GPU offload analysis).
- Hidden synchronization: PyTorch documentation, "CUDA semantics" (copies between CPU and GPU synchronize; `.item()` synchronizes the CPU with the GPU, listed among operations prohibited during graph capture) and the `torch.cuda.set_sync_debug_mode` API reference ("warn" or "error" on synchronizing operations; "an experimental feature, and not all synchronizing operations will trigger warning or error"); JAX "Asynchronous dispatch" (above).
- Tolerance from the operation: Higham, *Accuracy and Stability of Numerical Algorithms* (cited above), chapter 4 "Summation" (recursive summation error bounded by γ₍ₙ₋₁₎ Σ|xᵢ| with γₖ = ku/(1 − ku) ≈ ku); unit roundoff of reduced-precision formats from IEEE 754-2019 (binary16) and the bfloat16 and TF32 format definitions in the PyTorch and CUDA documentation cited above.
- Determinism: the PyTorch "Reproducibility" notes, CUB "Determinism," cuBLAS "Results reproducibility," and cuDNN deterministic-algorithm entries cited under the earlier sections; Whitehead and Fit-Florea (cited above) for fused multiply-add contraction controlled by compiler flags (`-fmad=false`).
