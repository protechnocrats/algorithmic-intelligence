# Workflow

Follow these phases in order in report and apply mode. Report mode stops after Phase 4. Apply mode continues with Phases 5 and 6 in `APPLYING.md`. Write mode follows `WRITING-NEW-CODE.md` instead. "Rule details" at the end of this file holds the full text of the mandatory rules that `SKILL.md` states briefly; it applies in every phase.

## Phase 1: Setup

1. If you have not yet, state the mode in one line ("First, state the mode" in `SKILL.md`). Detect the project's languages and runtime versions from build and source files, and read the matching `languages/` files (for example `languages/PYTHON.md`) before reading the code. For a language without one, load the saved profile at `.algorithmic-intelligence/languages/<LANGUAGE>.md` in the project's root if it exists, or build one as `languages/GENERIC.md` describes. If the profile is new or changed, ask whether to save it there ("Saving the profile" in `GENERIC.md`), together with the commit question in step 4.
2. Identify the test framework, how tests are run, and whether a property-based testing library or a verification tool (bounded model checker, concurrency checker, proof tool; see the language file) is already present. Do not add one without asking.
3. Identify available profilers and benchmark tooling. If there are none, plan a simple in-test timing harness (`BENCHMARKING.md`) rather than adding a dependency.
4. Check version control. In apply mode, recommend a dedicated branch and confirm the working tree is clean, or that the developer accepts mixing changes. Then settle commits ("Commits are opt-in" in `SKILL.md`): if neither the conversation nor the project's instructions authorize or forbid them, ask once now whether to commit each optimization separately, and keep the answer for the rest of the task.
5. Run the existing test suite. Record pass and fail counts and the names of failing tests. If any fail before you change code, follow rule 12: report mode continues, with the failing tests at the top of the report and noted against the candidates they could affect; apply mode stops before changing code until the developer decides. Never use a failing test as evidence: do not profile through it, and do not treat its expected values as the code's contract. If there is no suite, or it cannot run in this environment (missing toolchain or hardware, a kernel or firmware that must boot, an unavailable service), say so and continue: report mode is unaffected, and in apply mode the differential tests you write become the only automated check; run them as a standalone program if no test framework exists. If even they cannot run, every change is unverified (rule 5).

## Phase 2: Survey

**Confirm the scope first.** Write down what the developer asked you to cover: the whole repository, a module, a directory, a file, a function, or a slow operation they named. Survey that scope. Outside it, read code only as far as needed to establish a candidate's cost and callers (step 4, "Cost along the call chain"): follow calls out of the scope, but do not survey unrelated modules or the source of third-party dependencies. If the scope is too large to inspect completely in this session, start with the evidence below (profiles, the developer's complaints, hot paths) and keep a list of the parts you did not inspect. The report must include that list ("Scope" in `REPORTING.md`), so the developer never mistakes an unreviewed area for one with no problems.

Find candidates, preferring evidence to guessing:

- **Profiles and complaints come first:** profiler output, slow-trace logs, or a specific complaint from the developer. When the code can run with realistic input (the test suite, a benchmark, a local environment) and no profile exists, profile it before choosing candidates and record where the time goes. In report mode, profile only through what already exists (the test suite, existing benchmarks, an entry point the project provides) or with scratch files outside the project, and leave the working tree exactly as it was. If the code cannot run, say why, and label every candidate's bottleneck evidence estimated.
- **Then scan for structural signals:** nested loops over the same or related collections (including triple-nested loops), recursion that branches more than once per call, enumeration of subsets or permutations, linear searches inside loops (`contains`, `indexOf`, `find`, `includes`), repeated sorting, removal from the front of arrays, string building in loops, recursion without memoization over overlapping subproblems, database or network calls inside loops, work repeated on every UI frame, game frame, or recomposition, filters that visit every neighbor of every pixel, element-by-element loops over arrays or tensors, polling that rescans a whole dataset to find changes, aggregates recomputed from base data on every read, and requests that wait longer in queues, pools, or locks than they take to process.
- **Use the "Hidden costs" section** of each loaded language file.

For each candidate, establish before analyzing it:

1. **Its contract.** Read the function and the functions it calls. Write what it requires, what it returns (including order, ties, and duplicates), and what it changes, throws, or calls. Every later check is held to this specification.
2. **Who uses it, and how it is reached.** Search all callers, including reflection, dependency injection, serialization, and UI bindings where relevant, and note public API exposure. Then follow the callers upward until you reach an **entry point**: code that the program, a framework, or an outside party starts. Entry points include `main` functions and command-line commands; request handlers and routes; event, message, and queue listeners; scheduled and background jobs; UI event handlers and lifecycle callbacks; tests; and the public or exported API of a library (whose callers are outside the repository).

   **Reachability.** Write down which of these you found:
   - **Reached from an entry point:** name it. Its frequency (per request, per frame, nightly) multiplies the cost in step 4.
   - **Reached only from tests:** say that no production entry point was found.
   - **No entry point found:** the chain ends at a function, class, or module that nothing appears to call, often one registered with a dependency-injection container. Do not conclude it is unused: code reached indirectly does not show up in a search for direct calls. Search for dependency-injection registrations and bindings (annotations such as `@Inject`, `@Component`, `@Service`, `@Bean`, `@Provides`, and module and container configuration in code, XML, YAML, or JSON); classpath or package scanning; service loaders and plugin registries (`META-INF/services`, entry points in package metadata); routing tables and handler maps; event subscriptions; scheduler and job configuration; reflection and lookup by name (class or method names as strings, `getattr`, dynamic imports); and build or deployment configuration that selects implementations. If one of these reaches the code, treat it as reached from that entry point. If none does, record the reachability as unknown, with the list of places you searched.

   Code with unknown reachability keeps its item. Its cost along the call chain is unknown, not zero: rank it below items on proven hot paths (Phase 4), never list it as "not worth changing" for that reason, never delete it, and ask the developer whether the code is used.
3. **How often and how large.** Estimate realistic `n` (and every other size variable) and call frequency from callers, data sources, UI limits, pagination, and tests. Write the assumption down.
4. **Cost along the call chain.** Multiply the function's cost by how many times its callers invoke it per operation: loops in callers, per-item callbacks, per-frame or per-request calls. A function that is optimal for one call can be the inner loop of a cubic computation. Then analyze the caller as the candidate: the fix often belongs there (for example, build an index once, then look up), and the function may stay unchanged.
5. **Hot or cold.** Main thread, per frame, per request, per item, startup, or rare background work.
6. **Which resource limits it.** CPU, memory, I/O, network, a lock, or a queue. For services and systems, check each resource's utilization, saturation (work waiting for it), and errors: the USE method. A faster algorithm in the waiting code does not fix time spent waiting; see `techniques/queues-and-latency.md` and `techniques/hardware-and-concurrency.md`.
7. **Exposure.** Does an untrusted party control any input (requests, files, network data, user-supplied patterns or keys), does the code handle secrets (keys, tokens, passwords, private data), or must it meet a hard deadline? If any applies, judge it by its worst case, not its expected case, and load `techniques/hostile-inputs.md`. If the code uses a randomized structure (a sketch, a filter, a randomized cache, a keyed hash table) and the untrusted party can see outputs that depend on its random choices, the adversary is adaptive: follow "Adaptive adversaries" in that file.

Drop candidates where `n` is provably tiny and the path is cold ("Rule 8" in "Rule details" defines both), but list them in the report as "not worth changing" so the developer sees they were considered. A path with unknown reachability (step 2) is not cold: keep those candidates.

## Phase 3: Analyze

For each remaining candidate, record:

1. **Problem statement.** Restate the function as an abstract problem ("count pairs with sum k," "find the latest event per user," "check membership against a fixed list"). Abstract statements match known techniques.
2. **Current complexity.** Time and space in every size variable, labeled worst, average, or amortized, counting every call and all implicit work as "Count every call at its real cost" under rule 6 in `SKILL.md` requires; then the total along the call chain from Phase 2. In the item's "Cost now" field, name the calls that make up the dominant term, each with its cost and the source of that cost.
3. **Lower bound.** The best complexity any correct algorithm could achieve, with the reason and its basis (proven, conditional, conjectured, workload-dependent, or unknown); see "Lower bounds" in `ALGORITHM-ARSENAL.md`. If none can be established, write "unknown," say why, and give the strongest bound you can support. Never invent one (rule 6).
4. **Candidates.** Routed by `ALGORITHM-ARSENAL.md`, from every matching signal in the tables of `CORE-TECHNIQUES.md` (and `ADVANCED-TECHNIQUES.md` when the core techniques do not reach the lower bound or the domain calls for it), in proportion to difficulty (rule 6). Straightforward: the strongest candidate and a brief reason alternatives are unnecessary. Nontrivial: at least three plausible approaches, including at least one combination when the problem has more than one dimension (ordering plus lookup, range plus count, and so on). For each: time, space (preprocessing separately from per-query cost), the assumptions it needs and the evidence from the code that they hold, standard library or dependency, and behavior risks. If no table row matches the abstract problem, or the best match stays above the lower bound for no stated reason, work through `DISCOVERY.md` before choosing and add what it produces to the candidates.
5. **Choice and why not better.** The best approach and why. If it does not reach the lower bound, explain the gap with the reasons at the end of "Lower bounds" in `ALGORITHM-ARSENAL.md` (an unapproved dependency, preprocessing the call pattern cannot amortize, an assumption the code does not satisfy, or constant factors that lose at realistic sizes), and name the `DISCOVERY.md` moves tried when no table row reached it.
6. **Prediction.** Written now, before anything is measured: the expected speedup at realistic sizes, the expected growth exponent of both versions, and the end-to-end effect (the share of the whole operation's time this code takes, and so the most the change can save; rule 8).
7. **Space check.** Only once time is optimal: can the chosen approach use less memory without changing its time complexity? Confirm every new cache or index is bounded. Then multiply by the number of copies that can exist at once (one per process, worker, thread, connection, request, or tenant), and report the total, not one copy (rule 1).
8. **Behavior risks.** Walk `BEHAVIOR-TRAPS.md` and list every trap the change could hit.
9. **Verification plan.** The highest verification level the change can reach cheaply ("Verification levels" in `DIFFERENTIAL-TESTING.md`), the tool if one is needed, and which observable behavior no level can cover here (real database ordering, timing, platform rendering).
10. **Known behavior changes.** Any observable behavior the approach changes, even for the better ("Behavior-changing techniques" in `ALGORITHM-ARSENAL.md` lists the usual ones). Before listing one, look for a version that keeps the behavior ("Look for a version that keeps the behavior" under rule 5 in "Rule details"); if one exists, it is the item, and the faster version is the option for review. Behavior changes go under the report's "Behavior changes for review" and are never applied without explicit approval (rule 5).
11. **Bugs noticed.** Anything that looks wrong in the original. Record it for the bug log; do not fix it. Note whether the code will be optimized (rule 4): if not, it stays exactly as is; if so, whether the chosen approach keeps the bug or removes it as a side effect.

## Phase 4: Report

Once every candidate has been analyzed, write the report defined in `REPORTING.md` in one pass ("Where reports go" in `REPORTING.md`). Rank items by expected real-world impact: hot path and large `n` first, then complexity gap, then risk. Items with unknown reachability (Phase 2, step 2) rank below items reached from an entry point with known frequency and above items not worth changing; ask the developer whether their code is used, since the answer can move them to the top or remove the need to change them.

In report mode, stop here and present the report. Ask which items to apply and raise any dependency requests. Ask separately about each item under "Behavior changes for review": a general answer such as "apply all" covers only items whose equivalence is verified (rule 5).

## Rule details

The full text of the mandatory rules in `SKILL.md` where it says more than the short version there. Rule numbers match `SKILL.md`. Apply these in every phase; the phases above refer to them by name.

**Rule 1, memory.** Extra memory must not cost time through GC pressure, cache misses, or out-of-memory crashes. Count every copy: a 100 MB cache in each of 100 worker processes is 10 GB. Hard memory budgets include embedded targets, kernels, mobile, and per-request or per-process limits.

**Rule 2, trading time for memory.** Replacing an O(1) hash map with an O(log n) sorted array to save memory is the kind of change rule 2 forbids. When the code exceeds a hard memory budget, techniques that trade time for memory include external sorting, recomputation (such as gradient checkpointing), and streaming.

**Rule 3, verification.** The details are in `DIFFERENTIAL-TESTING.md` ("Verification levels," "Check the check," and "Reporting verification").

**Rule 4, bugs.**
- **If the buggy code cannot be optimized** (it is already optimal, or no optimization can be verified to keep behavior unchanged), leave it exactly as it is.
- **If it can be optimized,** apply the optimization through the normal workflow, keeping the bug. If the best optimization (rule 6) removes the bug as a side effect, keep the fix: confirm with differential tests that outputs differ only on inputs that trigger the bug, record it in the bug log as fixed as a side effect, and mark the code with `BEHAVIOR-CHANGE`. It counts as a side effect only when both hold: the bug is demonstrated by a concrete failing input that the original actually fails on in a test you ran (a suspected or theoretical bug does not qualify), and the change is the one you would make for speed alone if the bug did not exist. Before calling a bug fixed as a side effect, name that failing input and the command that showed the original failing; if you cannot, it does not qualify. A changed condition, check, or error path (for example, how a key is looked up) is not needed for speed, so it is never a side effect. Any change made, shaped, or extended to address a bug, including refactoring shared state or adding guards, is a behavior change for review under rule 5.
- **Bug or contract?** If it is unclear whether old behavior is a bug or an intended contract (for example, an exception thrown on purpose that callers may catch), it is not a bug: any change to it is a behavior change under rule 5. A crash from exhausting a resource (stack overflow, out of memory) on input the code accepts is never a contract, since no caller can rely on the size at which it happens: it is a bug, and removing it as a side effect follows rule 4.

**Rule 5, behavior changes.** Two cases need the developer's decision before anything is applied:
- **Unverified equivalence:** no verification reached shows that behavior is unchanged (some observable behavior is covered by no test, check, or tool at any level).
- **Known behavior change:** the optimization alters any observable behavior other than a bug removed as a side effect under rule 4, including changes that look like improvements (failing faster, a different order, approximate instead of exact results, no longer throwing an exception callers may rely on). This includes inputs that "should not happen" but that the code accepts (cyclic, malformed, out of range, hostile): if the original fails one way (an error) and the new code fails another (a hang, a crash, a different value), that is a behavior change. Telling the developer in a note does not approve it.

List each one under "Behavior changes for review" with the exact behavior before and after, and what is unverified. Apply it only after the developer explicitly approves that item, then mark it in the code and the report: `NEEDS-TESTING` for unverified equivalence, `BEHAVIOR-CHANGE` for a known change (`REPORTING.md`).

- **Changes to calls into other systems are verifiable.** Batching, deduplicating, or caching calls to a database, service, or other collaborator changes the calls on purpose, so the calls are not compared one for one. Verify everything else against a fake that implements the collaborator's documented contract ("Changes to calls into other systems" in `DIFFERENTIAL-TESTING.md`). Only behavior the documentation does not settle stays unverified.
- **Approval names the item.** A general instruction ("apply all," "apply everything you recommend," "go ahead," "do it") approves only items whose equivalence is verified, even when the report mentioned the risk of the others. An item in either case above needs the developer's explicit approval of that item, given after it is listed with its exact behavior before and after.
- **Removing work.** Deleting or skipping work the code currently does is an optimization item like any other: report it, get it approved, and verify it with differential tests. It is equivalent only when you have shown, not assumed, that (a) nothing uses its result: every caller was searched, and the code is not public or exported, since outside callers cannot be searched; and (b) the work has no other effect: no writes, logs, exceptions, collaborator calls, random-number draws, locks, shared state, or timing, ordering, or hardware purpose (constant-time code, delays, memory fences, volatile or device-register reads, warm-up). Otherwise the item is unverified equivalence or a known behavior change. Never delete code that does not run (unused functions, classes, branches) as an optimization: it costs no time.
- **A risk that can change results is a behavior change.** If any input the code accepts can produce a different observable result (for example, an index that goes stale when a caller edits an entry's key after adding it), the item is a known behavior change or unverified equivalence, listed under "Behavior changes for review," not a footnote under "risks."
- **Look for a version that keeps the behavior.** When an item's fastest version changes behavior, search for a version that keeps all observable behavior and removes most of the cost. List the item under "Behavior changes for review" only if none exists, and then name in the item each way you tried and why it fails. Ways that often work:
  - **Redo the expensive work only when its input changed.** Keep the cheap observable step and skip the costly one when its input is the same: for example, still read a configuration file on every call, so every edit is seen on the next call, but parse it again only when its contents differ from the last parse. Compare the input itself, or a version number the code maintains, not a proxy such as a modification time that can miss a change.
  - **Hand out copies.** When callers may modify a value that is now cached or shared, return a fresh copy, as the original did by creating a new value on every call.
  - **Take the fast path, and fall back to the original where it cannot match.** When the fast version differs only in some cases (a batch call that fails as a whole where the loop failed one item at a time, a structure that cannot handle some key types or values), use it where it matches and run the original code for the rest. For example, send in batches and, when a batch fails, resend its items one at a time (or split it in halves), so the items sent, the items rejected, and their order come out as before. Count the fallback's cost at a realistic failure rate.
  - **Keep the state a single operation can see.** When something outside the operation (another process, thread, user, or service) can change data while the operation runs, the original sees that change at a point that depends only on timing. A version that reads the data once at the start of the operation, and sees every change on the next operation, produces only results the original could also produce. That is not a behavior change, provided the operation itself does not change that data (otherwise it must still see its own changes) and the code's documentation and comments promise nothing about when an outside change becomes visible. State this reasoning in the item.

  A version found this way is an ordinary item: verify it and apply it under a general approval. Report the faster version that changes behavior next to it, as an option for review.
- **Declined is not the end of the item.** When the developer declines a behavior change, apply the version that keeps the behavior if one exists (once verified, it needs no further approval), and record it in the item's decision. Leave the code unchanged only when no such version exists.

**Rule 6, complexity.** Whatever the starting complexity (factorial, exponential, polynomial of any degree, or a product of several size variables), look for its lower bound: do not look only for quadratic code, and count the cost along the whole call chain (Phase 2, step 4). Many problems have no known lower bound, or none the code can establish, especially when cost depends on databases, networks, distributed systems, hardware, or data distributions: report the bound as unknown with the reason, and give the strongest bound you can support (for example, "at least one pass over the input"). A bound below the input size (O(log n), O(1)) is possible only when the work is amortized over repeated queries, the input is already structured (such as sorted or indexed), or a correct answer does not depend on every element (for example, finding any local peak). Use `ADVANCED-TECHNIQUES.md` when the core techniques do not reach the lower bound or the problem is in a specialized domain; it is an index, so load only the `techniques/` files it routes to. When counting calls, a key function runs n times when the sort computes keys once, and once per comparison when it is wrapped in a comparator; wrapping values in objects and hashing string keys (proportional to length) count too; a doubling experiment (`BENCHMARKING.md`) settles a cost no document does. Analysis never stops early: always identify and report the best achievable approach and the lower bound. Applying is evidence-driven: recommend applying a change only when measurements or a stated workload estimate show it pays off, do not add a specialized structure only for a better asymptotic bound, and stop applying once the bottleneck is resolved or the remaining cost is at the lower bound, recording what remains.

**Rule 8, measurement.** Big-O describes growth, not speed at a given size. "Provably tiny" means a bound visible in the code or data (a fixed enum, a constant-size table, a validated limit), not a guess about typical use; "not hot" means the code does not run per item, per request, per frame, or inside another loop. A 10× speedup of code that takes 2% of the operation saves under 2%; say so plainly.
