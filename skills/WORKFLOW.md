# Workflow

Follow these phases in order in report and apply mode. Report mode stops after Phase 4. Write mode does not use this file; it follows `WRITING-NEW-CODE.md`.

## Phase 1: Setup

1. Detect languages and versions as described in `SKILL.md`, then load the matching `languages/` files. For a language without a companion file, look for a saved profile at `.algorithmic-intelligence/languages/<LANGUAGE>.md` in the project's root directory and load it if it exists; otherwise build one, as `languages/GENERIC.md` describes. Either way, if the profile needs to be created or updated, ask whether to save it there (the question and its purpose are in `GENERIC.md`, "Saving the profile"), together with the commit question in step 4.
2. Identify the test framework, how tests are run, and whether a property-based testing library or a verification tool (bounded model checker, concurrency checker, proof tool; see the language file) is already present. Do not add one without asking.
3. Identify available profilers and benchmark tooling. If none exists, plan a simple in-test timing harness (see `BENCHMARKING.md`) rather than adding a dependency.
4. Check version control state. In apply mode, recommend a dedicated branch and confirm the working tree is clean, or that the developer accepts mixing changes. Then settle commits: commits are opt-in ("Commits are opt-in" in `SKILL.md`). If neither the conversation nor the project's instructions authorize or forbid them, ask once now whether to commit each optimization separately, and remember the answer for the rest of the task.
5. Run the existing test suite. Record pass and fail counts and the names of the failing tests. If anything fails before you change code (rule 12):
   - **Report mode:** continue. Put the failing tests at the top of the report, do not use failing tests as evidence (do not profile through them, and do not treat their expected values as the code's contract), and note which candidates the failures could affect.
   - **Apply mode:** report the failures and stop before changing any code, until the developer decides how to proceed.

   If there is no suite, or it cannot run here, follow rule 12.

## Phase 2: Survey

**Confirm the scope first.** Write down what the developer asked you to cover: the whole repository, a module, a directory, a file, a function, or a slow operation they named. Survey that scope. Outside it, read code only as far as needed to establish a candidate's cost and callers (step 4, "Cost along the call chain"): follow calls out of the scope, but do not start surveying unrelated modules or the source of third-party dependencies. If the scope is too large to inspect completely in this session, start with the evidence below (profiles, the developer's complaints, hot paths), and keep a list of the parts you did not inspect. The report must include that list ("Scope" in `REPORTING.md`), so the developer never mistakes an unreviewed area for one with no problems.

Find candidates. Prefer evidence over guessing:

- Profiler output, slow-trace logs, or a specific complaint from the developer come first. When the code can run with realistic input (the test suite, a benchmark, a local environment) and no profile exists, run a profiler before choosing candidates and record where the time goes. In report mode, profile only through what already exists (the test suite, existing benchmarks, an entry point the project provides) or with scratch files outside the project, and leave the working tree exactly as it was. If it cannot run, say why, and treat every candidate's bottleneck evidence as estimated.
- Then scan for structural signals: nested loops over the same or related collections (including triple-nested loops), recursion that branches more than once per call, enumeration of subsets or permutations, linear searches inside loops (`contains`, `indexOf`, `find`, `includes`), repeated sorting, removal from the front of arrays, string building in loops, recursion without memoization over overlapping subproblems, database or network calls inside loops, work repeated on every UI frame, game frame, or recomposition, filters that visit every neighbor of every pixel, element-by-element loops over arrays or tensors, polling that rescans a whole dataset to find changes, aggregates recomputed from base data on every read, and requests that spend longer waiting in queues, pools, or locks than being processed.
- Use the "hidden costs" section of each loaded language file.

For each candidate, establish before analyzing it:

1. **Its contract.** Read the function and the functions it calls. Write what it requires, what it returns (including order, ties, and duplicates), and what it changes, throws, or calls. This is the specification every later check is held to.
2. **Who uses it, and how it is reached.** Search all callers, including reflection, dependency injection, serialization, and UI bindings where relevant. Note public API exposure. Then follow the callers upward, caller by caller, until you reach an **entry point**: code that the program, a framework, or an outside party starts. Entry points include `main` functions and command-line commands; request handlers and routes; event, message, and queue listeners; scheduled and background jobs; UI event handlers and lifecycle callbacks; tests; and public or exported APIs of a library (whose callers are outside the repository).

   **Reachability.** Write down which of these you found:
   - **Reached from an entry point:** name it. Its frequency (per request, per frame, nightly) is what multiplies the cost in step 4.
   - **Reached only from tests:** say that no production entry point was found.
   - **No entry point found:** the chain ends at a function, class, or module that nothing appears to call, often one registered with a dependency-injection container. Do not conclude it is unused. Code reached indirectly does not show up in a search for direct calls. Search for: dependency-injection registrations and bindings (annotations such as `@Inject`, `@Component`, `@Service`, `@Bean`, `@Provides`, module and container configuration in code, XML, YAML, or JSON); classpath or package scanning; service loaders and plugin registries (`META-INF/services`, entry points in package metadata); routing tables and handler maps; event subscriptions; scheduler and job configuration; reflection and lookup by name (class names or method names as strings, `getattr`, dynamic imports); and build or deployment configuration that selects implementations. If one of these reaches the code, treat it as reached from that entry point. If none does, record the reachability as unknown, with the list of places you searched.

   Code with unknown reachability keeps its item. Its cost along the call chain is unknown, not zero: rank it below items on proven hot paths (Phase 4), never list it as "not worth changing" for that reason, never delete it, and ask the developer whether the code is used.
3. **How often and how large.** Estimate realistic `n` (and every other size variable) and call frequency from callers, data sources, UI limits, pagination, and tests. Write the assumption down.
4. **Cost along the call chain.** Multiply the function's cost by how many times its callers invoke it per operation: loops in callers, per-item callbacks, per-frame or per-request calls. A function that is optimal for a single call can be the inner loop of a cubic computation. When it is, analyze the caller as the candidate; the fix often belongs there (for example, build an index once, then look up) rather than in the function, which may stay unchanged.
5. **Hot or cold.** Main thread, per-frame, per-request, per-item, startup, or rare background work.
6. **Which resource limits it.** CPU, memory, I/O, network, a lock, or a queue. For services and systems, check each resource's utilization, saturation (work waiting for it), and errors: the USE method. Time spent waiting is not fixed by a faster algorithm in the waiting code; see `techniques/queues-and-latency.md` and `techniques/hardware-and-concurrency.md`.
7. **Exposure.** Does an untrusted party control any input (requests, files, network data, user-supplied patterns or keys), does the code handle secrets (keys, tokens, passwords, private data), or must it meet a hard deadline? If any applies, judge it by its worst case rather than its expected case, and load `techniques/hostile-inputs.md`. When the code uses a randomized structure (a sketch, a filter, a randomized cache, a keyed hash table) and the untrusted party can see outputs that depend on its random choices, the adversary is adaptive: follow "Adaptive adversaries" in that file.

Drop candidates where `n` is provably tiny and the path is cold (rule 8 defines both), but list them in the report as "not worth changing" so the developer sees they were considered. A path with unknown reachability (step 2) is not cold: keep those candidates.

## Phase 3: Analyze

For each remaining candidate, record:

1. **Problem statement.** Restate the function as an abstract problem ("count pairs with sum k," "find the latest event per user," "check membership against a fixed list"). Abstract statements match known techniques.
2. **Current complexity.** Time and space, in every size variable, labeled worst, average, or amortized. Include hidden costs from library calls and from the project functions it calls, and the total cost along the call chain from Phase 2.
3. **Lower bound.** The best complexity any correct algorithm could achieve, with the reason and its basis (proven, conditional, conjectured, workload-dependent, or unknown). See "Lower bounds" in `ALGORITHM-ARSENAL.md`. If no bound can be established, write "unknown," say why, and give the strongest bound you can support. Never invent one (rule 6).
4. **Candidates.** Routed by `ALGORITHM-ARSENAL.md`, from every matching signal in the tables of `CORE-TECHNIQUES.md` (and `ADVANCED-TECHNIQUES.md` when the core techniques do not reach the lower bound or the problem domain calls for it), in proportion to difficulty (rule 6). Straightforward: the strongest candidate plus a brief reason alternatives are unnecessary. Nontrivial: at least three plausible approaches, including at least one combination when the problem has more than one dimension (ordering plus lookup, range plus count, and so on). For each: time, space (preprocessing separately from per-query cost), the assumptions it needs and the evidence from the code that they hold, standard library or dependency, behavior risks. If no table row matches the abstract problem, or the best match stays above the lower bound for no stated reason, work through `DISCOVERY.md` before choosing, and add what it produces to the candidates.
5. **Choice and why not better.** The best approach and why. If it does not reach the lower bound, explain why the gap remains, using the reasons at the end of "Lower bounds" in `ALGORITHM-ARSENAL.md` (an unapproved dependency, preprocessing the call pattern cannot amortize, an assumption the code does not satisfy, or constant factors that lose at realistic sizes), and which `DISCOVERY.md` moves were tried when no table row reached it.
6. **Prediction.** The expected speedup at realistic sizes and the expected growth exponent of both versions, written down now, before anything is measured. Also predict the end-to-end effect: the share of the whole operation's time this code takes, and therefore the most the change can save (rule 8).
7. **Space check.** Only after time is optimal: can the chosen approach use less memory without changing its time complexity? Confirm every new cache or index is bounded. Then multiply: how many copies of this structure can exist at the same time (one per process, worker, thread, connection, request, or tenant)? Report the total across all of them, not one copy (rule 1).
8. **Behavior risks.** Walk `BEHAVIOR-TRAPS.md` and list every trap the change could hit.
9. **Verification plan.** The highest verification level the change can reach cheaply ("Verification levels" in `DIFFERENTIAL-TESTING.md`), the tool if one is needed, and which observable behavior no level can cover here (real database ordering, timing, platform rendering).
10. **Known behavior changes.** Any observable behavior the approach changes, even for the better ("Behavior-changing techniques" in `ALGORITHM-ARSENAL.md` lists the usual ones). These go in the report's "Behavior changes for review" section and are never applied without explicit approval (rule 5).
11. **Bugs noticed.** Anything that looks wrong in the original. Record it for the bug log; do not fix it. Note whether the code will be optimized (rule 4): if not, it stays exactly as is; if so, note whether the chosen approach keeps the bug or removes it as a side effect.

## Phase 4: Report

Write the report defined in `REPORTING.md` in one pass, once every candidate has been analyzed ("Where reports go" in `REPORTING.md`). Rank items by expected real-world impact: hot path and large `n` first, then complexity gap, then risk. Items whose reachability is unknown (Phase 2, step 2) rank below items reached from an entry point with known frequency, and above items not worth changing; ask the developer whether their code is used, since the answer can move them to the top or remove the need to change them.

In report mode, stop here and present the report. Ask which items to apply and raise any dependency requests. Ask separately about each item under "Behavior changes for review": a general answer such as "apply all" covers only items whose equivalence is verified (rule 5).

## Phase 5: Apply

For each approved item, one at a time:

1. **Characterize the original.** Write differential tests per `DIFFERENTIAL-TESTING.md`, with the original implementation copied verbatim as the reference, and turn the contract into executable checks ("The contract as executable properties"). Run them against the unchanged code first. They must pass, which shows the harness is wired correctly. Then check the check: the tests must pass with the original on both sides, and catch planted differences ("Check the check" in `DIFFERENTIAL-TESTING.md`). Keep one differential-test file and one benchmark program for the whole apply phase and add each item to them ("Work in few, large steps" in `SKILL.md`).
2. **Change the code.** Make the smallest change that implements the chosen approach. Keep the signature and contract. Add a short comment where the technique is not obvious.
3. **Verify.** Run the differential tests and contract checks, then the full existing suite, then any bounded or exhaustive check from the verification plan. Re-walk the behavior traps for this change and confirm each is covered by a test or ruled out by analysis. Record the level reached.
4. **Benchmark.** Measure time and memory for the original and the new version at realistic `n`, at a larger `n`, and on worst-case inputs where relevant, following `BENCHMARKING.md`. Also state the end-to-end effect: what share of the whole operation's time the changed code took before the change, and the resulting end-to-end saving, measured where possible ("Component and end-to-end" in `BENCHMARKING.md`). Record the numbers as measured, with the measured growth exponent, and compare them with the prediction from Phase 3. If they disagree, find out why before keeping the change: a wrong prediction means a cost the analysis missed. If the new version is not faster at realistic sizes, do not keep it unless the developer agrees for scaling reasons; a change that is not kept goes under "Tried and rejected" in the report. If benchmarking cannot be run, say so and report the expected gain as estimated only.
5. **Handle unverified parts and behavior changes.** If any behavior cannot be verified, or the change alters behavior in any way, stop work on this item: restore its original code, do not commit it, add it to "Behavior changes for review," and continue with the next item. Ask about every such item at the end (rule 5). An earlier "apply all" is not approval for it. If the developer approves that item, apply it and add the `NEEDS-TESTING` or `BEHAVIOR-CHANGE` marker from `REPORTING.md`.
6. **Re-run after the final edit.** If anything changed after the last test run (review fixes, comments, formatting), run the differential tests and the full suite again. Results from an earlier version of the code do not count.
7. **Commit, only if authorized.** If the developer authorized commits (Phase 1, step 4), make one commit per optimization, with a message that states the before and after complexity, the benchmark result, the verification level, and the tests added. Do not mix bug fixes, formatting, or unrelated refactors into the commit. If commits are not authorized, do not commit: record in the report the exact files and functions this item changed, so the developer can review, commit, or revert it on its own.

If a differential test fails, the optimization is wrong. Fix the optimization, never the test. If the failure reveals that the original behavior is itself a bug, record it in the bug log and follow rule 4: if the best optimization removes the bug as a side effect, confirm that outputs differ only on the bug-triggering inputs and document it; otherwise keep matching the original.

## Phase 6: Close out

Write `APPLY-RESULTS.md` once, in one pass ("Apply results format" in `REPORTING.md`), and leave `OPTIMIZATION-REPORT.md` exactly as the analysis wrote it: what was applied, skipped, or rejected; final benchmark numbers against the predictions; changes tried and rejected while applying; bugs found while applying; and the full lists of `NEEDS-TESTING` and `BEHAVIOR-CHANGE` items. State plainly which items were verified and at which level (with the evidence), which were accepted by the developer with unverified behavior, and which knowingly change behavior. Call an item proven only at verification level 4. Offer to keep each item's benchmark as a regression guard ("Offer a regression guard" in `BENCHMARKING.md`), and list the ones the developer kept.
