# Workflow

The phases for report and apply mode. Report mode stops after Phase 4; apply mode continues with Phases 5 and 6 in `APPLYING.md`; write mode follows `WRITING-NEW-CODE.md`. "Rule details" at the end is the one place for the full form of the mandatory rules in `SKILL.md`.

**Contents:** Phase 1: Setup · Phase 2: Survey · Phase 3: Analyze · Phase 4: Report · Rule details

**Checklist.**

```
- [ ] Phase 1: language files read; test baseline recorded; commits settled (apply mode)
- [ ] Phase 2, per candidate: contract, callers and entry point, sizes, cost along the call chain, hot or cold, limiting resource, exposure
- [ ] Phase 3: DATA-STRUCTURES.md, with the audit of each hot-path collection; ALGORITHM-ARSENAL.md and the CORE-TECHNIQUES.md sections it routes to; lower bound; candidates; BEHAVIOR-TRAPS.md; DIFFERENTIAL-TESTING.md, with the tests planned per item
- [ ] Phase 4: report per REPORTING.md (apply mode: then APPLYING.md)
- [ ] Final summary lines ("Every final summary" in SKILL.md)
```

## Phase 1: Setup

1. **Languages.** Detect the languages and runtime versions as `languages/INDEX.md` says and read each language file before reading that code. Embedded query languages, shell, build files, and templates have no profile; their costs come from the technique files. For a language without a file, `languages/GENERIC.md` says how to load or build a profile; ask about saving it together with the commit question in step 4. Note the direct dependencies in the manifest of the module in scope: what they provide is available without a new dependency.
2. **Test and verification tools.** Find the test framework, how tests run, how the tests nearest the code in scope are written ("Which tests to write" in `DIFFERENTIAL-TESTING.md`), and whether a property-based testing library or a verification tool (bounded model checker, concurrency checker, proof tool) is already present. Adding one is a dependency (rule 7).
3. **Profilers and benchmark tooling.** Without any, plan a simple timing harness (`BENCHMARKING.md`) rather than a new dependency.
4. **Version control.** In apply mode, recommend a dedicated branch and a clean working tree, or confirm the developer accepts mixing changes. If commits are neither authorized nor declined ("Commits are opt-in" in `SKILL.md`), ask once now and keep the answer for the task.
5. **Baseline test run** (rule 12). Read the command and what it triggers first ("Before running a command" in `SKILL.md`); if it is unsafe, call the test runner directly. Installing the project's own dependencies from its lockfile is not "installing software": do it after reading the install hooks, skipping any that does something unsafe; if it cannot be done (no network), what needs it cannot run.
   The suite is the tests of the packages that hold the code in scope and their dependents, run the same way before and after every change (or the subset the developer names), non-interactively and with a time limit. Leave out tests that reach real databases, services, or the network, and list them under "Commands not run". Take the result from the exit status and a machine-readable report rather than printed text. A suite that collects nothing or skips most tests is not evidence; report it as a hazard. Without a runnable suite, say so: in apply mode the differential tests become the only automated check, and if even they cannot run, every change is unverified (rule 5).

## Phase 2: Survey

**Translate the request** ("Translate the request" under "Starting" in `SKILL.md`) and record it under "Request as understood" (`REPORTING.md`). A symptom with no code named sets the scope: the code reached from the entry point it describes.

**Scope.** Write down what the developer asked to cover and survey that; outside it, read only as far as needed to establish a candidate's cost and callers. Generated code is reported against its generator or template, never edited; vendored code is a dependency, report only. When the scope is too large for one session, start from the evidence below and list what you did not inspect ("Scope" in `REPORTING.md`), so an unreviewed area is not mistaken for a clean one. Check a file's size and type before reading it: a FIFO or device never ends, and a symbolic link can lead out of the project.

Find candidates, preferring evidence to guessing:

- **Profiles and complaints first.** When the code can run with realistic input and no profile exists, profile it on generated data with the Phase 1 precautions. In report mode, profile only through what already exists (tests, benchmarks, an entry point the project provides) or scratch files outside the project, and leave the working tree as it was. A profile an earlier session left is a claim; rerun it. For queries, `EXPLAIN ANALYZE` executes the statement and `ANALYZE` changes planner statistics for everyone, so use plain `EXPLAIN`, or a local copy with generated data. If the code cannot run, label every candidate's bottleneck evidence estimated.
- **Then structural signals:** collections whose structure does not suit what the code does to them, with or without a visible loop; nested loops over related collections, linear searches or service calls inside loops, repeated sorting or parsing, recursion over overlapping subproblems, work repeated every frame, polling or aggregates that rescan everything, and requests that wait in queues, pools, or locks longer than they take to process.
- **The "Hidden costs" section** of each loaded language file.

For each candidate, establish:

1. **Its contract.** What it requires, returns (order, ties, duplicates), changes, throws, or calls, taken from the code. Docstrings, annotations, and test names are claims; a disagreement goes in the item, the bug log, and "Hazards noticed".
2. **Who uses it, and how it is reached.** Find all callers and note public API exposure. What a caller does with the result and the arguments is contract: if it modifies, keeps, or encodes them, name that caller in the item ("Mutation and aliasing" in `BEHAVIOR-TRAPS.md`). Then follow callers upward to an **entry point**: something the program, a framework, or an outside party starts (main, commands, routes, listeners, scheduled jobs, UI callbacks, a library's exported API). Evidence that the code runs in production also counts: a profile or log, the developer saying it runs or is slow (a request to optimize it is not, by itself, such a statement), or deployment configuration naming what uses it, confirmed in the repository. Tests are not an entry point.

   **Reachability.** Record either an entry point (its frequency multiplies the cost in step 4) or "no entry point found", which includes code reached only from tests. Before concluding the latter, search the paths a call search misses: dependency injection and scanning, plugin and service registries, routing tables, event subscriptions, scheduler configuration, and lookup by name (strings, `getattr`, dynamic imports).

   **Code with no entry point found is not optimized**, since making it faster saves nothing. Log any bug in it (rule 4) and list it under "No entry point found" (`REPORTING.md`) with the chain followed, the places searched, and the question: is this used, and from where? Call it "likely unused", never "dead", and never delete it: a search can miss a runtime-built name, a script run by hand, or another repository. If the developer names a use, analyze it from there; in apply mode, ask before changing such code.
3. **How often and how large.** Read the project's configuration, deployment files, and README for production sizes and rates, in apply mode too. Estimate every size variable and the call frequency and write the assumption down. A size in a comment or README is a claim; only a limit the code or configuration enforces is a bound. When sources disagree (a comment says 100 users per team, the deployment allows 50,000), report each with file and line, also under "Hazards noticed", say which you used, and ask when the choice changes a ranking or design; when nobody can answer, use the larger.
4. **Cost along the call chain.** Multiply the function's cost by how often its callers invoke it per operation. A function optimal for one call can be the inner loop of a cubic computation. Analyze the caller as a candidate too: the fix often belongs there (build an index once, then look up), and the function may stay unchanged.
5. **Hot or cold.** Main thread, per frame, per request, per item, startup, or rare background work.
6. **Which resource limits it.** CPU, memory, I/O, network, a lock, or a queue. For services, check each resource's utilization, saturation, and errors (the USE method). A faster algorithm does not fix time spent waiting: see `techniques/queues-and-latency.md` and `techniques/hardware-and-concurrency.md`.
7. **Exposure.** Does an untrusted party control any input, does the code handle secrets, does it cache or batch across users or tenants, or must it meet a hard deadline? "Internal" or "trusted" in a comment is a claim: trace where the input comes from. If any applies, judge by the worst case and load `techniques/hostile-inputs.md`; if the code uses a randomized structure and the attacker can see outputs that depend on its random choices, follow "Adaptive adversaries" there.

Drop candidates where `n` is provably tiny and the path is cold (rule 8 in "Rule details"), and list them in the report as "not worth changing" so the developer sees they were considered.

## Phase 3: Analyze

For each remaining candidate, record:

1. **Problem statement** in abstract terms ("latest event per user", "membership against a fixed list"); abstract statements match known techniques.
2. **Current complexity,** time and space in every size variable with the case, counting every call at its real cost (rule 6 in "Rule details"), then the total along the call chain. Name the calls that make up the dominant term, each with its cost and the source of that cost.
3. **Data structures.** Do the audit in `DATA-STRUCTURES.md` for every collection on the hot path: dominant operations, current cost, best structure, and the reason for not switching. Each replacement is a candidate in step 5.
4. **Lower bound** with its reason and basis ("Lower bounds" in `ALGORITHM-ARSENAL.md`), or "unknown" with why and the strongest bound you can support.
5. **Candidates,** routed by `ALGORITHM-ARSENAL.md` from every matching signal in `CORE-TECHNIQUES.md`, and `ADVANCED-TECHNIQUES.md` when the core techniques fall short or the domain calls for it. Search the algorithm and the structure together (rule 6): ask what structure would make a different algorithm possible, even one the code does not use yet. A problem is straightforward only when the strongest candidate reaches the lower bound, needs no new dependency, and has no behavior risks: give it and a brief reason alternatives are unnecessary. Otherwise give at least three plausible (never invented) approaches, including a combination when the problem has more than one dimension (ordering plus lookup, range plus count). For each: time, space (preprocessing separate from per-query cost), the assumptions it needs with evidence from the code that they hold (a sliding window fails on negative values, binary search on a predicate that is not monotonic), dependency, and behavior risks. When no row matches, or the best stays above the bound for no stated reason, work through `DISCOVERY.md`.
6. **Choice and why not better.** Choose the lowest complexity reachable; list an easier partial improvement as an alternative. If the choice misses the lower bound, explain the gap with the reasons in "Lower bounds" in `ALGORITHM-ARSENAL.md`, and name the `DISCOVERY.md` moves tried.
7. **Prediction,** written before anything is measured: speedup at realistic sizes, the growth exponent of both versions, and the share of the whole operation this code takes, which caps the end-to-end saving.
8. **Space check,** once time is optimal: less memory at the same time complexity, and every new cache or index bounded and totaled across copies (rule 1).
9. **Behavior risks** from `BEHAVIOR-TRAPS.md`.
10. **Verification plan.** The tests this item will get, per "Which tests to write" in `DIFFERENTIAL-TESTING.md`: the entry point its pin tests drive and which collaborators stay real; any extraction a buried hot path needs; the seeded comparison's reference (a verbatim copy, or which fallback from "When the original cannot be copied"), what is compared, and the edge and generated inputs; each assumption pinned; and the planted difference they must catch. Then the highest level reachable cheaply ("Verification levels") and what no level can cover here (real database ordering, timing, platform rendering). Report mode writes no tests; this plan is what the developer approves.
11. **Known behavior changes,** including better-looking ones and weakened security properties ("Security is behavior" under rule 5). First look for a version that keeps the behavior ("Look for a version that keeps the behavior" under rule 5); if one exists, it is the item and the faster one is an option for review.
12. **Bugs noticed** in the original and in any other code read along the way, logged and not fixed. Note whether the code will be optimized and, if so, whether the chosen approach keeps the bug (rule 4).

## Phase 4: Report

Write the report in `REPORTING.md`'s format once every candidate is analyzed. Rank by expected real-world impact: hot path and large `n` first, then complexity gap, then risk. Code with no entry point found gets its own section, not an item.

In report mode, stop here: present the report, ask which items to apply, raise dependency requests, and ask separately about each behavior change for review ("Approval names the item" under rule 5). In a non-interactive run nothing is applied.

When the developer asks for a plan, each item in it carries its data structure audit and planned tests, as the report does. When the developer approves items, however worded, the run becomes apply mode: open `APPLYING.md` and continue at Phase 5, whose first step comes before any edit ("Differential tests come before the edit" in `SKILL.md`).

## Rule details

The full form of the mandatory rules in `SKILL.md` where it says more than the short version. Numbers match `SKILL.md`.

**Rule 1, memory.** Extra memory must not cost time through GC pressure, cache misses, or out-of-memory crashes. A structure is bounded by an explicit limit or by input the program already holds. Estimate the total in bytes (entries × bytes per entry × copies) and compare it with the memory limit in the project's configuration, or say none was found: a 100 MB cache in each of 100 workers is 10 GB. Under a hard memory budget (embedded, kernel, mobile, per-request or per-process limits), an approach that exceeds it is not a candidate, however fast.

**Rule 2, trading time for memory.** Replacing an O(1) hash map with an O(log n) sorted array to save memory is what rule 2 forbids. When code exceeds a hard memory budget, the time-for-memory trades to propose are external sorting, recomputation (such as gradient checkpointing), and streaming.

**Rule 3, verification.** See "Verification levels", "Check the check", and "Reporting verification" in `DIFFERENTIAL-TESTING.md`.

**Rule 4, bugs.** An optimization keeps the bugs of the code it replaces. Choosing, adjusting, or extending an approach to address a bug (adding guards, refactoring shared state) makes it a behavior change for review under rule 5.
- **Bug or contract?** When it is unclear whether old behavior is a bug or intended (an exception thrown on purpose that callers may catch), treat it as contract. A crash from exhausting a resource (stack overflow, out of memory) on input the code accepts is never contract, since no caller can rely on the size at which it happens.
- **Removed as a side effect.** When the best optimization (rule 6) happens to remove a bug, the fix may stay only if all three hold: (a) the original crashes, hangs, exhausts a resource, or throws an exception it does not raise on purpose, or an existing test or the project's documentation states the expected result and the original violates it; (b) you ran a concrete failing input against the original in this session (a suspected bug, or one a comment, issue, or old bug log describes, does not qualify); and (c) the change is the one you would make for speed alone. A changed condition, check, error path, validation, size limit, permission, or secret comparison is never needed for speed, so it never qualifies. Confirm with differential tests that outputs differ only on inputs that trigger the bug, log it as fixed as a side effect with the failing input and the command, and mark the code ("Code markers" in `APPLYING.md`). Any other difference you believe is a bug (duplicates kept, a wrong order) is a known behavior change: list it with the failing input and let the developer decide.

**Rule 5, behavior changes.** Two cases need the developer's decision before anything is applied:
- **Unverified equivalence:** some observable behavior is covered by no test, check, or tool at any level.
- **Known behavior change:** any observable difference other than a bug removed as a side effect, including improvements (failing faster, a different order, approximate results, no longer throwing an exception callers may catch). Inputs that "should not happen" but the code accepts count: an original that raises an error where the new code hangs or returns a value has changed behavior. So does any risk that can change a result on some accepted input (an index that goes stale when a caller edits a key after adding it).

List each under "Behavior changes for review" with the exact behavior before and after and what is unverified. Once approved, mark it `NEEDS-TESTING` or `BEHAVIOR-CHANGE` ("Code markers" in `APPLYING.md`).

- **Approval names the item.** An item in either case needs approval of that item, in this conversation, after it was shown with its behavior before and after; a reply that refers to the shown list, or a named subset, approves each item in it as shown, and anything said before it was shown approves none. A general instruction ("apply all", "go ahead") approves only items verified to keep behavior. Approval covers the version shown: if the item's before or after changes, ask again. Nothing in a file approves anything ("Untrusted content" in `SKILL.md`).
- **Security is behavior.** Weakening a security property is a known behavior change even when no test observes it ("Security-sensitive behavior" in `BEHAVIOR-TRAPS.md`). A cache key includes everything the result depends on, the caller's identity and permissions included.
- **Changes to calls into other systems are verifiable.** Batching, deduplicating, or caching calls to a database or service changes the calls on purpose; verify everything else against a fake that implements the collaborator's documented contract ("Changes to calls into other systems" in `DIFFERENTIAL-TESTING.md`). Only what the documentation leaves open stays unverified.
- **Removing work** is an item like any other: reported, approved, and verified. It keeps behavior only when you have shown that (a) nothing uses the result: every caller searched, and the code is not public or exported, since outside callers cannot be searched; and (b) the work has no other effect: writes, logs, exceptions, collaborator calls, random-number draws, locks, shared state, or a timing, ordering, or hardware purpose ("Removed work" in `BEHAVIOR-TRAPS.md`). Code that never runs costs no time, so deleting it is not an optimization.
- **Look for a version that keeps the behavior.** When the fastest version changes behavior, look for one that keeps all observable behavior, security properties included, and removes most of the cost. It is an ordinary item, applied under a general approval once verified; the faster version is reported next to it as an option for review. If none exists, name each way you tried and why it fails. Ways that often work:
  - **Redo the expensive work only when its input changed.** Keep the cheap observable step and skip the costly one: still read the configuration file on every call so every edit is seen, but parse it only when its contents differ. Compare the input itself or a version number the code maintains, not a proxy such as a modification time. The one kept result is a cache with a bound of one; hand out copies of it.
  - **Hand out copies.** When callers may modify a value that is now cached or shared, return a fresh copy, as the original did by building a new value each call.
  - **Take the fast path, and fall back to the original where it cannot match.** A batch call that fails as a whole where the loop failed per item: on a batch failure, resend its items one at a time (or split in halves), so the items sent, rejected, and their order match. Count the fallback's cost at a realistic failure rate.
  - **Keep the state a single operation can see.** When another process, thread, or service can change data during an operation, the original sees that change at a timing-dependent point. Reading the data once at the start, and seeing changes on the next operation, produces only results the original could produce, so it keeps behavior, provided the operation does not change that data itself and nothing documented promises when outside changes become visible. It is a behavior change when a read inside the operation is how it notices a stop, cancel, timeout, lease, lock, readiness, or quota signal, or when the operation runs long enough (a job, a batch) that changes during it are expected to be seen. State this reasoning in the item.
- **Declined is not the end of the item.** When the developer declines a behavior change, apply the version that keeps the behavior if one exists (once verified, it needs no further approval) and record it in the item's decision.

**Rule 6, complexity.** Search for the lower bound whatever the starting complexity (exponential, a high-degree polynomial, a product of size variables), not only for quadratic code. Never state a bound more certainly than its reason supports; many problems, especially those dominated by databases, networks, hardware, or data distributions, have none the code can establish, and an unknown bound does not end the search. A bound below the input size is possible only when work is amortized over repeated queries, the input is already structured (sorted, indexed), or a correct answer does not depend on every element.
- **Count every call at its real cost.** A function's cost includes everything it calls (built-ins, standard and third-party libraries, frameworks, project functions), times how often each runs. Operations that copy, slice, convert, reverse, sort, search, or hash a collection or string usually cost time proportional to its size. Count implicit work: building one structure from another, building a string piece by piece, a comparator called O(n log n) times (a key function runs n times when the sort caches keys, once per comparison when wrapped in a comparator), hashing string keys (proportional to length), and lazy sequences evaluated more than once. Short or built-in does not mean O(1), and a language file's "Hidden costs" lists common traps, not every operation. Take each cost from documentation, the language file, or a doubling experiment (`BENCHMARKING.md`); when none settles it, write it as unknown and label the total estimated.
- **Analysis and applying differ.** Analysis always reports the best achievable approach and the lower bound. Applying is driven by evidence: a change needs a measurement or a stated workload estimate showing it pays off at the sizes this code sees. When it does, apply the lowest complexity reachable, not a partial improvement because it is the easier edit. Stop at the lower bound, or once the operation no longer matters at real sizes, recording what remains.

**Rule 8, measurement.** Big-O describes growth, not speed at a given size.
- **"Provably tiny"** means a bound visible in the code or data (a fixed enum, a constant-size table, a limit validated on every path), not typical use or a comment. **"Not hot"** means it does not run per item, request, or frame, or inside another loop. Such code is reported without being changed.
- **"Measured"** numbers appear in the output of a benchmark, profiler, or test run in this session, or are computed from such numbers with the arithmetic shown (0.71 s for 200 calls is 3.6 ms per call). A number a command merely displays from a file or log is a claim. Before finishing, check each measured number against the output it came from.
- **End to end.** A faster function is not a faster program: a 10× speedup of code that takes 2% of the operation saves under 2%. Code is not faster for being shorter, newer, or in a better complexity class without a measurement or a stated workload estimate.
