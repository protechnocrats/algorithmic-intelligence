# Queues, Latency, and Throughput

The shared rules and table conventions in `ADVANCED-TECHNIQUES.md` apply.

For code that serves requests or moves work between stages (schedulers, network stacks, connection and thread pools, brokers, services, event loops). Every function can be optimal while response time is poor, because work waits in queues. Measure waiting time separately from service time before changing either.

## Laws to apply first

- **Little's Law.** L = λ · W holds for any stable system and any distributions. Use it to cross-check measurements and to size pools and buffers: λ · W is the average occupancy, so a pool of exactly that size queues under any burst; size for the measured peak.
- **Utilization drives waiting.** For M/M/1, W = 1 / (μ − λ): going from 80% to 95% busy quadruples the average time in the system, so a small cut in service time near saturation removes much of the waiting. Treat this as the shape of the curve, not a prediction.
- **Pooling.** One shared queue for c servers waits less than c separate queues at the same load, because no server idles while work waits elsewhere.
- **Tail latency under fan-out.** A request waiting on N parallel sub-requests is as slow as the slowest: if each is slow 1% of the time, a fan-out of 100 is slow about 63% of the time (1 − 0.99¹⁰⁰). Measure and optimize the parts' high percentiles, not their averages.
- **Measure without coordinated omission.** A load generator that waits for each reply before sending the next hides queueing delay. Measure latency from each request's scheduled send time, at a fixed arrival rate. Point load generators only at a local or dedicated test instance, with a time limit ("Before running a command" in `SKILL.md`).

## Techniques

Most techniques here change behavior under load (which requests wait, are rejected, or complete first) even when each request's result is unchanged: rule 5 applies. Existing queue bounds, pool sizes, rate limits, and timeouts are also defenses; raising or removing one for speed removes the defense (`techniques/hostile-inputs.md`).

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Queues grow without bound under bursts, memory climbs, and latency rises for everything | Bounded queues with backpressure (block or slow the producer) or admission control (reject early) | Behavior change: callers now wait or are rejected; the rejection signal is part of the contract; queues created per client or key are bounded in number too | Bounded memory and bounded waiting; overload becomes visible instead of cascading |
| One slow item delays everything behind it in a single queue or connection (head-of-line blocking) | Separate queues per class or destination, multiplexed streams, or out-of-order completion with request IDs | Ordering guarantees callers rely on are kept, or the change is reviewed | Fast work no longer waits behind slow work |
| Many independent queues or servers, some idle while others have backlogs | One shared queue, work stealing, or routing to the least loaded of two randomly chosen servers ("power of two choices") | Work items are interchangeable between servers; affinity (caches, sessions, locality) is preserved where it matters | Lower and more even waiting time; two random choices cut the maximum load from O(log n / log log n) to O(log log n) |
| Short and long tasks mixed in one first-in, first-out queue | Shortest-job-first or shortest-remaining-time scheduling, size-based queues, or priorities | Behavior change in completion order; long tasks need a starvation bound (aging); job sizes come from the server's own estimate, not a client's claim | Lower average waiting time; first-in, first-out keeps the variance of waiting time lower, not the average |
| Overloaded queue where old requests are already past their deadlines | Drop requests whose deadline has passed; under overload, serve newest first (adaptive LIFO) or apply CoDel-style queue management | Behavior change: some requests fail fast instead of succeeding late; deadlines known | Capacity is spent on requests that can still succeed |
| One task, call, or thread started per input item with no limit (a loop of unawaited calls, `Promise.all` or a goroutine per item, a thread per request) | Bounded concurrency: a semaphore or a fixed worker pool sized from the downstream limits | Result order, error behavior (first error versus all errors), and cancellation match the original; the bound counts copies across concurrent requests (rule 1) | Memory and downstream load bounded however large the input |
| Per-item overhead dominates (system calls, network round trips, disk syncs, lock acquisitions) | Batching: combine items up to a size or a time limit (group commit, Nagle-style coalescing, vectored I/O) | The added delay is acceptable (a behavior change for latency-sensitive callers); failures handled per item as before; items from different users or tenants keep their own authorization, and each result and error returns to its caller by identifier, not by position | Per-item overhead divided by the batch size; latency rises by up to the batch window |
| A few slow replies dominate the tail latency of reads that can be served by several replicas | Hedged requests: send a second request if the first has not answered by about the 95th-percentile latency, use the first reply, cancel the other | Requests are safe to duplicate, checked from the code (a read that records a view, charges, or increments a counter is not); extra load capped (typically a few percent), and hedging stops under overload | Tail latency cut sharply for little extra load |
| Retries after failures arrive in synchronized waves and overload a recovering service | Exponential backoff with jitter, retry budgets, circuit breakers | Behavior change in timing and in when callers see errors; retry only idempotent operations or ones carrying an idempotency key the server honors, since a timed-out call may have succeeded; retry at one layer, because layered retries multiply (three at each of three layers is 27 attempts) | Load stays below capacity during recovery |
| A fixed rate limit or pool size that is wrong as conditions change (congestion, autoscaling, I/O depth) | Feedback control: additive increase and multiplicative decrease (AIMD, as in TCP congestion control), latency-based limits (Vegas-style or gradient limiters), token buckets for sustained rate with bursts | The control loop is stable (gains and sampling interval tested under load steps); a per-client limit is keyed by an identity the server established, not a client-set header such as `X-Forwarded-For`, or a new key per request bypasses it; live buckets are bounded in number; behavior change in admitted rate | Throughput tracks available capacity without manual tuning |
| Threads blocked on I/O while CPU sits idle, or a thread per connection exhausting memory | Event-driven I/O (`epoll`, `kqueue`, `io_uring`, I/O completion ports) or asynchronous tasks with a bounded number of worker threads | Threading and ordering are part of the contract (rule 11); blocking calls are kept off the event loop | Concurrency limited by memory per connection instead of threads; fewer context switches |
