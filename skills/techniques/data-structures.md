# Specialized Data Structures, Hash Tables, and Caches

The shared rules and table conventions in `ADVANCED-TECHNIQUES.md` apply to every table here.

## Hash table design

When the project implements its own hash table, or a profile shows time inside one, its design matters as much as the choice to use one. Changing the hash function, probing scheme, or capacity changes iteration order wherever callers iterate the table. Any hash- or order-based structure also needs keys that do not change while stored: a key whose fields used by its hash, equality, or comparator are mutated after insertion is silently lost.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Chained hash table with one heap-allocated node per entry, hot in profiles | Open addressing in one flat array: linear probing, Robin Hood hashing, or group probing with SIMD metadata (Swiss tables) | Load factor kept below the scheme's limit (roughly 0.7 to 0.9); deletion uses tombstones or backward-shift deletion; nothing holds a pointer to an entry across inserts, since entries move on resize | Same O(1) expected; far fewer cache misses and allocations |
| Long probe sequences, many collisions, or slow lookups only for some key sets | Better hash function with full mixing (keys with low-entropy bits, such as aligned pointers or sequential IDs, cluster under weak hashes); Robin Hood hashing to bound probe-length variance | The new hash is deterministic where the original was, or randomized only where order was never observable | Longest probe sequence shrinks; worst-case lookups closer to expected |
| Keys come from untrusted input | Keyed hash with a secret per-process seed (for example, SipHash), or a balanced tree for a guaranteed bound | Changing the hash function changes iteration order | Hash flooding no longer degrades operations to O(n) each |
| Growth rehashes the whole table at once, and the pause matters (latency-sensitive or real-time code) | Incremental rehashing: keep the old and new tables and move a few buckets per operation | Lookups check both tables during migration | Worst-case single operation O(n) → O(1) extra per operation; same amortized cost |
| Integer keys hashed with a modulo by a prime, or with weak mixing, in a power-of-two table | Multiplicative (Fibonacci) hashing: multiply by 2^w / φ (for 64 bits, `0x9E3779B97F4A7C15`) and keep the top bits; Linux's `hash_long` does the same with a related golden-ratio constant | Changes iteration order; not for untrusted keys (see the keyed-hash row) | A multiply and a shift instead of a division; sequential keys spread evenly |
| Hash table with fixed-size buckets (hardware tables, cache-line buckets) where the fullest bucket overflows | d-left hashing: split the table into d parts, place each key in the least loaded of its d candidate buckets, breaking ties to the left | Lookups check d buckets; changes placement and iteration order | Maximum bucket load drops from about log n / log log n to about log log n / d, so buckets can be small and fixed-size |
| Lookups must be fast in the worst case, not just on average (packet processing, real-time, hardware tables) | Cuckoo hashing: each key lives in one of two (or d) candidate slots; inserts move occupants to their alternative slot | Load factor under the scheme's limit (about 50% with two single-slot tables, about 95% with buckets of four); insert failures handled by rehashing or a small stash; with untrusted keys, hash functions keyed with a per-process secret, or an attacker can force repeated insert failures | Lookups check at most two buckets (d with d hash functions, plus the stash if one is used), O(1) worst case; inserts O(1) expected amortized |
| Key comparisons are expensive (long strings, composite keys) | Store each key's full hash beside it, and compare hashes before keys | The hash is consistent with key equality (equal keys always hash equal); a hash match is always confirmed by comparing keys | Most failed comparisons avoided |
| Many equal strings or values stored or compared repeatedly (symbols, tags, field names, repeated column values) | Interning: keep one canonical copy per distinct value and compare by reference | Values come from a closed set, or the pool is bounded or scoped (per load, per request), since a global pool fed by input is a memory leak an attacker can drive; reference comparison only between interned values; the pool is safe for concurrent use | Memory per duplicate removed; equality O(length) → O(1) |
| Table built once, then only read, with keys known at build time | Perfect hashing or a static sorted array (see "Structures for repeated queries" in `CORE-TECHNIQUES.md`) | Key set never changes after building | O(1) worst-case lookups |

## Caching and eviction

Hit rate decides whether a cache pays off, and the eviction policy decides the hit rate. Measure hit rate, eviction overhead, and memory per entry on a representative access trace before choosing a policy. A policy change alters which requests miss, which is a behavior change wherever a miss is observable (latency contracts, side effects or I/O on a miss, staleness, statistics exposed to callers). Before adding or changing a cache, check from the code:

- **Key and scope:** the key holds every input the result depends on, including user, tenant, permissions, locale, and configuration ("Hidden inputs" and "Caching traps" in `BEHAVIOR-TRAPS.md`). Normalizing or truncating a key merges entries that must stay apart.
- **Invalidation:** every writer of the underlying data, including other processes, invalidates or is detected. A cached "not found" (negative caching) hides a record created later unless creation invalidates it, and attacker-chosen missing keys can fill the cache with it: bound or skip negative entries.
- **Shared mutable values:** a cached object returned to callers who mutate it changes the cache for everyone; return copies or immutable values if the original did.
- **Concurrent misses:** many requests missing on one key all run the expensive load (a stampede). Let one load per key run and the rest wait with a timeout, never while holding another key's lock: a slow attacker-chosen key would hold every waiter, and a loader that loads another key can deadlock. Cache errors or partial results only if the original did.
- **Security decisions:** for caching sessions, permissions, or token checks, see "Optimizations that weaken a defense" in `techniques/hostile-inputs.md`.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Recency-driven workload with exact LRU required | Hash map + doubly linked list | The checks above and a size bound; the list is guarded when several threads access the cache | O(1) per access |
| LRU bookkeeping on every hit is too expensive (lock contention, very high access rates, page caches) | CLOCK (second chance) or generalized CLOCK; multi-generational LRU | Approximate LRU order is acceptable; eviction order changes | O(1) per access with no list reordering on hits; eviction is O(1) amortized |
| Sequential scans flush hot entries out of an LRU cache | Scan-resistant policies: segmented LRU, 2Q, LRU-K, ARC | Check the license and patent status of the chosen policy's implementation before adopting it | Higher hit rate on mixed scan and reuse workloads |
| Skewed frequencies, with many items used only once | LFU with O(1) frequency buckets; TinyLFU admission (a count-min sketch decides whether a new item may replace the eviction victim), as in W-TinyLFU | The sketch is approximate, but only affects which items stay cached, never the values returned | Higher hit rate on skewed workloads; O(1) per access |
| Entries expire by time, found by scanning all entries | Expiry ordered by a heap, or a timing wheel (see "Specialized data structures") | Expiry precision matches the original | O(n) scan → O(log n) per entry, or O(1) with a timing wheel |

## Specialized data structures

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Predecessor and successor queries over a bounded integer universe u, at very high volume | Van Emde Boas tree, or a hierarchical bitset (y-fast trie for sparse sets) | Integer keys in [0, u); memory O(u) for van Emde Boas, less for hierarchical bitsets, O(n) for a y-fast trie | O(log n) → O(log log u) for van Emde Boas (worst case) and y-fast tries (expected amortized); O(log u / log w) for a hierarchical bitset with w-bit words |
| Sorted map needed but not in the standard library | Treap, skip list, or another balanced tree | The comparator is a consistent total order (no NaN keys, no comparison on mutable fields) and agrees with the equality the original used, since a sorted map treats keys that compare equal as one key; iteration order and handling of equal keys match the original; with untrusted keys, the random priorities or levels come from a source the attacker cannot predict, or use a deterministic balanced tree | O(n) → O(log n) expected |
| A structure that is fast to query but can only be built from scratch (a static sorted array, k-d tree, or suffix array), now receiving inserts | Bentley-Saxe logarithmic method: keep static structures of sizes 1, 2, 4, …, merge them like a binary counter on insert, and query each one | The query is decomposable (its answer combines across parts: membership, counting, nearest neighbor); deletes need tombstones or periodic rebuilds | Rebuild per insert, O(B(n)) → O((B(n) / n) · log n) amortized for build time B(n); queries cost about log n times more. LSM trees use the same idea |
| Sorted map with highly skewed or local access (a few keys accessed repeatedly, or accesses near the previous one) | Splay tree: each access moves the key to the root | Single-threaded or locked, since every lookup restructures the tree; a single operation can take O(n), so not on deadline paths or where an attacker chooses the access sequence | O(log n) amortized, and much less for skewed access (working-set property) |
| Priority queue where decrease-key dominates (Dijkstra or Prim on dense graphs) | Pairing heap or Fibonacci heap; or a binary heap with lazy insertion (push a new entry, skip stale ones when popped) | The binary heap with lazy insertion is usually fastest in practice despite the weaker bound; measure | Fibonacci heap: decrease-key O(1) amortized, so Dijkstra is O(E + V log V) |
| Keeping old versions by copying a whole collection on every update (immutable state, reducers, undo history, snapshots, multi-version reads) | Persistent data structures with structural sharing: path copying in balanced trees, hash array mapped tries (HAMT) for maps and sets, RRB vectors for sequences | Callers never mutate a shared version; reference equality still means "unchanged" for every version (frameworks that compare references, such as React, rely on it); iteration order of the persistent map matches the original's | O(n) per update → O(log n) (effectively O(log₃₂ n) for HAMT), with unchanged parts shared between versions |
| Counting, enumerating, or optimizing over huge families of configurations defined by constraints (product configurators, feature models, reachability in model checking) | Reduced ordered binary decision diagrams (BDDs), or zero-suppressed decision diagrams (ZDDs) for sparse families of sets | The size depends heavily on variable order and can be exponential: measure it on real constraints; a BDD library is a dependency (rule 7) | Counting solutions in time linear in the diagram's size, instead of enumerating them |
| Longest-prefix match against many address prefixes, checked one by one (routing tables, IP allow and deny lists) | Compressed binary trie (Patricia trie, level-compressed trie as in the Linux routing table), or a multibit trie | Ties and overlapping prefixes resolve exactly as in the original | O(prefixes) per lookup → O(address bits), or fewer memory accesses with multibit strides |
| Packets or requests classified against many multi-field rules checked in order (firewalls, access-control lists) | Decision-tree classifiers (HiCuts, HyperCuts), tuple space search, or bit-vector intersection per field | First-match priority reproduced exactly; memory of the built structure is bounded and measured | O(rules) per packet → close to constant in practice; worst cases depend on the rule set |
| Overlap queries over many intervals | Interval tree, or a segment tree over compressed coordinates | Endpoint semantics match the original (closed or half-open; whether touching intervals overlap); result order matches if observable | O(n) per query → O(log n + k) |
| Cheap pre-check before an expensive exact lookup | Bloom filter | Used only as a pre-filter before the exact check; with attacker-chosen items, hashes keyed with a secret, or crafted false positives force the expensive lookup every time | Avoids most expensive lookups |
| Bloom filter that computes k independent hash functions per item, and hashing dominates its cost | Double hashing (Kirsch-Mitzenmacher): derive the k positions as h₁(x) + i · h₂(x) from two hashes | Same false-positive rate asymptotically; positions change, so a stored or shared filter must be rebuilt (a format change) | k hash computations → 2 per item |
| Pre-check filter that must also support deletes, with filter memory not the constraint | Counting Bloom filter: small counters (about 4 bits) instead of bits | Counters saturate rather than wrap, or the filter rejects further inserts: sixteen attacker-chosen inserts wrap a 4-bit counter to zero, a later delete gives a false negative, and the exact check is skipped for a present key; delete only inserted items | Deletes supported at about four times the memory; a cuckoo filter (next row) is usually smaller |
| Cheap pre-check before an exact lookup, where items are also removed | Cuckoo filter | Used only as a pre-filter; delete only inserted items; inserts can fail when the filter is nearly full: handle that by resizing or falling back to the exact check | Same benefit as a Bloom filter, plus deletion; less space than a Bloom filter at low false-positive rates |
| Timers or timeouts scheduled and cancelled far more often than they fire (network stacks, kernels, connection pools) | Hierarchical timing wheel | Firing times rounded to the wheel's granularity match the original | O(log n) heap insert and cancel → O(1) |
| Approximate counts, frequencies, or distinct counts over huge streams | Count-min sketch, HyperLogLog | The developer accepts approximate results, and nothing that decides access, money, limits, or deduplication rests on the estimate alone (shared rules in `ADVANCED-TECHNIQUES.md`); exposed estimates can be steered ("Adaptive adversaries" in `techniques/hostile-inputs.md`) | O(n) memory → O(1) or O(log n) memory, with fast updates |
