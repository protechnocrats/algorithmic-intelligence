# Build Systems and Pipelines

The shared rules and table conventions in `ADVANCED-TECHNIQUES.md` apply to every table here.

**Contents:** Find where the time goes · Skip work whose inputs did not change · Caching across runs and machines · Do less work · Data pipelines · Behavior traps

Builds, CI jobs, code generation, test runs, and data pipelines repeat on every change, so work they redo when little has changed is paid on every run by everyone (rule 10). The goal is a run whose cost is proportional to what changed, with outputs identical to a clean full run.

## Find where the time goes

A build is a graph of steps, and the slow part is rarely where it is assumed. Time each step with the tool's own profiler or trace before changing anything: Bazel writes a JSON trace profile with a critical-path row (viewable in `chrome://tracing`), Gradle has `--profile` and build scans that split configuration from task execution, and any script-driven pipeline can log a start and end time per step. Report three numbers separately, because they have different causes and fixes:

- **Full build**: from a clean checkout and empty caches. Dominated by real work and parallelism.
- **No-op rebuild**: run again with nothing changed. Anything above near-zero is work done regardless of inputs (configuration, steps that always run, steps whose outputs are rewritten every time). A correct incremental build does nothing here.
- **Typical change**: edit one commonly changed file and rebuild. This is what developers wait for.

Measure at the data size production and CI see (rule 8). A step that copies, regenerates, or rescans data costs in proportion to that data: it looked cheap on a small fixture, a warm file cache, or a copy-on-write file system (Btrfs, XFS, APFS, where a copy shares blocks until written, and recent `cp` does this by default), and it is not cheap on a CI runner with a cold cache and an ordinary disk. Estimate such steps from bytes copied or rows processed at production size, label the estimate, and do not keep plainly unneeded work because it measured fast here.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| "The build is slow" with no breakdown | Profile per step with the build tool's trace; split full, no-op, and typical-change times | The run measured is the one people wait for (CI or local, same flags) | Names the few steps that hold most of the time |
| Many steps run in parallel but the build is still slow | Read the critical path (the longest chain of dependent steps) from the trace; shorten or split the steps on it | Steps off the critical path are not the target: making them faster does not shorten the build | Wall time bounded below by the critical path, not total work |
| A no-op rebuild takes noticeable time | Find which steps ran or which configuration was re-evaluated; the tool's "why did this run" output (an execution log, an explain mode) names the changed input | The rebuild really had no changed inputs | No-op time → near zero |

## Skip work whose inputs did not change

An incremental build is correct when it runs each step at most once and only if the step transitively depends on an input that changed since the last build (minimality in Mokhov, Mitchell, and Peyton Jones, "Build Systems à la Carte"), and its outputs equal a clean build's. Both halves depend on knowing every input of every step. A missing input makes the build skip a step it should have run, and ships stale output; an input that changes on every run (a timestamp, an absolute path, a random seed) makes it run a step it could have skipped.

How the tool decides "changed" matters:

- **Modification times** (Make, Ninja by default) compare a file's time with its outputs'. They are cheap but fooled in both directions: `touch` or a checkout rewrites times without changing content (rebuilds for nothing); restoring files from archives, packages, or backups gives old times to new content, clocks differ between machines or on network file systems, two writes in one second look identical on coarse-grained file systems, and times can go backwards (steps skipped that should run). Git deliberately sets the current time on every file a checkout changes so mtime-based tools stay correct, so switching to a branch and back rebuilds everything those files feed even though their content is the same as before.
- **Content hashes** (Bazel, Gradle, Nix, ccache, Docker `COPY`) compare a fingerprint of the content with the one recorded at the last build. A changed time with unchanged content does not trigger work, and content changed with an old time is still seen. Tools often use file size and time as a shortcut to skip rehashing, so they inherit the mtime problem when both are unchanged.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A script or pipeline reruns every step on every run | Express the steps as a dependency graph in a build tool (or a small runner that records input hashes per step) and run only steps whose inputs changed, in topological order | Every input of every step is declared (files read, tool and its version, flags, environment variables read, generated files consumed); dependencies discovered at build time (headers included, files listed in a manifest) are recorded through the tool's dependency-file or dynamic-dependency support | Runs cost O(steps affected by the change) instead of O(all steps) |
| Rebuilds triggered after checkouts, branch switches, or restores although content is unchanged; or changes missed after restoring files | Decide "changed" by content hash, recorded per step, instead of modification time | Hashing cost is small next to the step (hash large inputs once and record the result, or use the size-and-time shortcut); the recorded hashes are stored with the outputs and deleted with them | Spurious rebuilds and missed rebuilds caused by times both go away |
| A small change (a comment, a private function body) rebuilds everything downstream | Early cutoff: when a rebuilt step's output is byte-identical to the previous one, stop propagating; dependents are not rerun (supported by Shake, Bazel, Ninja's `restat`, and hash-based tools; not by plain Make) | The step's output is deterministic, so an unchanged input set gives identical bytes (see "Non-hermetic steps" under "Behavior traps") | Rebuild stops at the first unchanged output instead of reaching every dependent |
| A step (code generator, copy, config writer) rewrites its outputs every run even when their content is the same | Write to a temporary file, compare with the existing output, and replace it only if different (keep the old time when equal) | Consumers read only the content, not the time; the comparison reads the old file, which is cheaper than rebuilding everything downstream. With plain Make the step itself then reruns on every build (its output stays older than its inputs), so it must be cheap; Ninja's `restat` records the unchanged output instead | Approximates early cutoff for mtime-based tools; dependents stop rebuilding |
| A step's tool, compiler flags, or environment changed but the build reused old outputs | Make the command line, tool version or tool hash, and every environment variable the step reads part of its inputs (Ninja records each output's command line and rebuilds when it changes; Bazel puts in an action's key only the environment variables declared with `--action_env`) | The tool's identity is detected by content or version, not only by path | Changes to tools and flags rebuild exactly what they affect |
| Dependency-download or image layers rebuilt on every source change | Order steps from least to most often changing (dependency manifest and install before copying sources), since a layered cache invalidates every later step once one changes | A step that fetches from the network is cached by its command text, not by what it fetched: pin versions or hashes so a cached result means the same thing | Dependency steps reused across most builds |

## Caching across runs and machines

A cache stores a step's outputs under a key computed from its inputs, so the same step on another run, branch, or machine downloads the result instead of recomputing it. The key must include everything that can change the output: input contents, the command and flags, the tool and its version, environment variables read, and the target platform. A key that misses one of these is cache poisoning waiting to happen: two different results get the same key, and every later build that hits it ships the wrong one. Bazel's documentation gives the classic case: tools outside the workspace are not tracked, so two machines with different compilers can share wrong hits. A key that includes something irrelevant (an absolute path, a timestamp, the user name) is safe but never hits across machines.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| The same steps rebuilt on every developer machine and CI runner | Remote or shared build cache keyed by input hashes (Bazel remote cache, Gradle remote build cache, ccache with shared storage), read by all, written by trusted CI | Steps are hermetic: they read only declared inputs (sandboxing or remote execution enforces it); outputs are deterministic; the key covers toolchain, flags, and platform; only trusted builds can write entries, since anyone who can write can poison what others run; secrets never enter cached outputs | Most steps of a typical build become downloads |
| Cache configured but the hit rate is low | Compare two runs' per-step keys (Bazel execution logs, Gradle build scan comparisons) to find the input that differs: absolute paths, timestamps, environment leakage, unpinned tools | The comparison is between builds that should have matched | Hit rate raised by removing the irrelevant input |
| CI job restores a large cache archive before every run | Measure restore and save time against the time the cache saves; cache only what is expensive to recreate and stable across runs (downloaded dependencies keyed by the lockfile hash, compiler caches), and use fallback keys for partial hits | The CI cache is evicted and size-limited (GitHub Actions: 10 GB per repository by default, entries unused for 7 days removed), so plan for misses; cache contents are readable by anyone who can run a job on the repository, so no secrets | Net time saved; a cache that costs more to restore than to rebuild is removed |
| Copy-like steps (copying files, packaging small archives) cached | Do not cache steps cheaper to run than to fetch (Gradle does not cache copy tasks for this reason) | Measured both ways | Less cache traffic, no slower builds |

## Do less work

The fastest step is one that does not run. Before making a step faster, ask whether anything reads its output, whether it repeats work another step already did, and whether it can be done once instead of per run, per test, or per target.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A step copies, regenerates, or stages data that nothing downstream reads | Remove the step or the copy; read the data in place | Search every consumer first: other build targets, scripts, CI configuration, packaging, deployment, and documentation tooling (see "Removing a copy something reads" under "Behavior traps"); the removal is listed if any doubt remains (rule 5) | O(data) per run → zero |
| Test data or fixtures generated, downloaded, or loaded again for every test or every run | Generate once and reuse: a build step whose output is cached by its inputs (generator code and seed), or a fixture shared across tests (session or module scope in test frameworks) | Tests do not mutate the shared data, or each gets a cheap copy-on-write view; the generator is deterministic (fixed seed) so the reused data equals what each run would have made | Generation cost paid once per input change instead of per test |
| Whole modules or projects recompiled after a small change | The compiler's incremental mode (Rust's query-based incremental compilation, Gradle's incremental Java compilation, a compiler daemon) and splitting large modules so a change touches fewer | Incremental output equals a clean build's (compilers treat a mismatch as a bug; check it, as under "Behavior traps"); incremental caches stay out of release artifacts when they are not reproducible | Rebuild proportional to the changed module and its dependents |
| Every test runs on every change | Test selection: run the tests whose dependencies (build graph, or files and classes recorded while each test ran) include a changed file; run everything periodically and before release | Selection is safe only when it sees every dependency: a test that reads a data file, configuration, environment, or reflection target that the dependency record misses is skipped when that input changes. Changes to build files, toolchains, or shared configuration select everything. The periodic full run catches what selection missed. Selection that skips tests by predicted failure probability (machine-learned) misses some failures by design: a behavior change in what the test suite guarantees (rule 5) | Ekstazi cut end-to-end test time by 32% on average (54% for longer suites) on 32 Java projects; Facebook's predictive selection halved test cost while catching over 99.9% of faulty changes |
| Adding workers no longer speeds up the build | Find the critical path and the serial part; shorten the longest chain (split a large step, remove an unnecessary dependency edge, move work off the chain) | Amdahl's law: with a serial fraction s, speedup is at most 1/s however many workers run; parallel steps must not share outputs, temporary files, or ports | Wall time bounded by the critical path; workers beyond it only add contention |

## Data pipelines

A pipeline that recomputes all history every run costs O(all data) per run. Partition the data (by date, by source, by key range) and process only the partitions whose input changed, but only if every step is idempotent: running it twice on the same partition gives the same result as running it once, typically by overwriting the output partition rather than appending to it. Idempotence is what makes retries, backfills, and reruns after a failure safe. Record which logic version produced each partition: when the transformation changes, old partitions hold results of the old logic, and an incremental run does not fix them.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A transformation recomputes the whole table on every run while only new rows arrive | Incremental model: process rows newer than what the target already holds (dbt's `is_incremental()` filter), merged by a unique key | The unique key is truly unique and never null, or duplicates appear on each run; without a key the step appends and reruns duplicate rows; rows that arrive late or are updated after their timestamp are caught by a lookback window, or they are missed (behavior change, rule 5) | O(all rows) per run → O(new rows + lookback) |
| Queries or jobs read a whole dataset to use a slice | Partition the storage by the filtered column (date, region) so filters skip whole partitions (Hive-style directory partitioning with partition values in the path, or a table format such as Iceberg) | Filters are on the partition column with the same semantics (time zones on date partitions, nulls); partitions are not so small that per-file overhead dominates; per-block statistics are the data-skipping row of "Storage and indexing" in `techniques/data-at-scale.md` | Data read: all → matching partitions only |
| Steps append to their output, so a retry or rerun duplicates data | Make each step idempotent: overwrite the output partition atomically (write elsewhere, then swap), or merge by key | The partition boundary is deterministic from the inputs; readers never see a half-written partition | Reruns and backfills safe; incremental processing becomes possible |
| Streaming aggregation keeps state for all time, or waits forever for late events | Event-time windows with a watermark: an estimate of how far event time has progressed, after which a window is finalized and its state dropped | Data later than the watermark is dropped or handled separately (Spark guarantees not to drop data within the threshold; later data may or may not be counted): a behavior change unless the original already dropped late data | State bounded by the window and lateness threshold instead of all history |
| The transformation logic, schema, or a reference table changed | Reprocess every partition the change affects (dbt `--full-refresh` on the model and everything downstream; a backfill over the affected range) | All downstream consumers of the old results are rebuilt too; added columns are filled for old rows only by reprocessing | Results consistent with the new logic; incremental runs resume afterward |

## Behavior traps

Rewrites that look equivalent but are not; check them alongside `BEHAVIOR-TRAPS.md` ("Removed work" and "Purity and caching" there apply to every skipped or cached step).

- **Outputs must equal a clean full build's.** Byte-identical artifacts, or identical in everything consumers read (for an archive, the member contents and names, not the timestamps inside, if no consumer reads them). An incremental build that differs from a clean build is wrong, however much faster it is.
- **A hidden input ships stale output.** A step skipped because its declared inputs did not change, while an undeclared one did (a header found through an include path, a tool upgraded in place, an environment variable, a file read by a script, a remote resource), produces the old output silently. Remote caches spread the stale result to every machine.
- **Non-hermetic steps.** Steps that embed the current time, build IDs, the host name, absolute paths, network content, or random values, or iterate in an order that varies, produce different bytes on every run. That defeats early cutoff and caching and makes incremental-versus-clean comparison impossible. Fix the source (a fixed timestamp such as `SOURCE_DATE_EPOCH`, sorted file lists, fixed seeds, relative paths) before relying on caching. Nondeterministic steps combined with caches keyed only on the original inputs can also mix results from different runs into one inconsistent build.
- **Removing a copy something reads.** A staged copy, a generated file, or an intermediate output may be read by packaging, deployment, a test, a documentation step, an IDE, or another repository's CI. Search for every reader before removing it; when you cannot rule one out, report it instead of deleting (rule 5).
- **Caches keyed too narrowly.** A key that omits the toolchain version, compiler flags, target platform, or an environment variable returns another configuration's output. A key that omits an input of a data step returns results computed from other data.
- **Test selection skips the failing test.** A selected subset passing does not mean the full suite passes. Keep a full run on a schedule and before release, and select everything when build files, toolchains, or shared configuration change.
- **Pipeline reruns and late data.** A non-idempotent step duplicates rows on retry; an incremental filter on a timestamp misses rows that arrive late or are updated in place; old partitions keep results of old logic.

**Verification.** Compare the incremental result with a clean full build, byte for byte or by what consumers read, in each of these situations: a no-op rebuild; after modifying an input; after adding an input; after deleting an input (a deleted source whose output is never removed is a classic stale artifact); after changing a flag or tool version; and with the cache cold and warm. For pipelines, compare an incremental run with a full recomputation over the same data, including a rerun of the same partition and rows arriving late. Build twice from clean in different directories (or on two machines) and compare outputs to find nondeterminism before trusting a cache.
