# Databases

The shared rules and table conventions in `ADVANCED-TECHNIQUES.md` apply to every table here.

**Contents:** Find where query time goes · Query shapes · Indexes beyond the basics · Writes and transactions · Schema and data layout · Connections and round trips · Inside engines · Behavior traps

For application code that talks to a relational database, and for people building or tuning a database or query engine. The basics are elsewhere and not repeated here: reading a plan, indexing filtered and joined columns, predicates that prevent index use, keyset pagination, planner statistics, and `EXISTS` for existence checks are in "Database queries" in `CORE-TECHNIQUES.md`; N+1 queries and projection are in "Production patterns" there; storage structures (B+ trees, LSM trees, Bloom filters, MVCC, zone maps, encodings) are in "Storage and indexing" in `techniques/data-at-scale.md`.

Two things hold for every row:

- **A database's outcome is more than the rows a query returns.** It includes their order when a caller relies on it, what is stored, which errors are raised, what concurrent sessions see and when (visibility), what is locked and for how long, what commits or rolls back together (atomicity), and which triggers, constraints, and audit records fire. A change to any of these is a behavior change (rule 5) unless the developer asked for it. Schema, index, and configuration changes need approval even when results stay the same, because they change write cost, locking while they are applied, and other statements' plans.
- **Diagnose on a local or test database with representative data.** `EXPLAIN ANALYZE` executes the statement; production and shared databases are the developer's to run ("Before running a command" in `SKILL.md`). Plans depend on table sizes and statistics, so a plan taken on a small development table says little about production.

## Find where query time goes

Rank statements before tuning one. The engine's statement statistics group executions by normalized statement text and report calls and total time; total time (calls × mean) is what users pay, so a 2 ms statement run on every request often outweighs the slow report someone suspects. Then take the actual plan of each statement that matters and find the operator where estimated and actual row counts diverge, or where a step repeats per outer row (`loops` in PostgreSQL).

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| "The database is slow" with no breakdown | Rank statements by total time from the engine's statement statistics (`pg_stat_statements` in PostgreSQL, the Performance Schema digest summary or the slow query log in MySQL, Query Store in SQL Server) | The statistics come from the workload that is slow: production numbers come from the developer; locally, a replayed or generated workload of the same shape | Names the few statements that hold most of the time, often a cheap one run very often |
| One statement is slow | Actual plan with row counts and pages read (`EXPLAIN (ANALYZE, BUFFERS)` in PostgreSQL, `EXPLAIN ANALYZE` in MySQL 8.0.18 and later, the actual execution plan in SQL Server; SQLite's `EXPLAIN QUERY PLAN` shows the plan without times); look first at the lowest node whose actual rows differ from the estimate by orders of magnitude | Data of production-like size and distribution; a writing statement only inside a transaction that is rolled back | Names the cause (a misestimate, a missing index, a per-row subplan, a sort or hash spilling to disk) instead of guessing from the SQL text |
| The same statement is fast in a console but slow from the application, or slow only for some parameter values | Look for a plan built for other parameter values: a cached generic plan (PostgreSQL switches to one after five executions when it looks no costlier; `plan_cache_mode`), parameter sniffing (SQL Server), bind peeking (Oracle). Compare the plan for the slow values with the console plan, which used literals | Data is skewed: a few values match many rows. Fixes (custom plans for that statement, a recompile hint, Parameter Sensitive Plan optimization in SQL Server 2022, separate statements per class of value) are configuration or query changes (rule 5), and per-execution planning has its own cost | A plan suited to each class of value; the occasional slow call disappears |
| A statement got slower after a deploy, an upgrade, data growth, a bulk load, or a statistics refresh, with no change to its text | Plan regression: compare the current plan with an earlier one (Query Store history, `auto_explain` logs, saved plans), then fix the cause (stale statistics after a bulk load, missing statistics on correlated columns, a dropped or changed index) before forcing the old plan | A forced plan or hint freezes a choice that may be wrong at the next data size; record why it was forced | Back to the earlier plan's cost, with the cause removed |

## Query shapes

Rewrites of one statement into another. Each pays only when the plan shows the old shape doing repeated or quadratic work; each is equivalent only under conditions on NULLs, duplicates, and ties that the schema must enforce, not just the test data.

| Signal | Technique | Valid when | Behavior risk |
|---|---|---|---|
| Self-join or correlated subquery computing a running total, rank, previous or next row, or the latest row per group | Window function (`ROW_NUMBER`, `RANK`, `LAG`, `LEAD`, `SUM(...) OVER (PARTITION BY ... ORDER BY ...)`): one sort per partition instead of a probe or scan per row | The engine supports window functions (SQLite 3.25 and later, MySQL 8.0 and later); pays when the plan shows the self-join or subquery repeated per row: O(n²) pairs or n probes → one O(n log n) sort | Ties: with `ORDER BY` and no frame clause the default frame includes the current row's peers, so tied rows get the same running total where a self-join on `<` gave them different ones; `ROW_NUMBER` picks arbitrarily among ties (add a unique tiebreaker); NULL placement in the window's sort |
| Application loop that reads rows and issues one `UPDATE`, `INSERT`, or `DELETE` per row | One set-based statement (`UPDATE ... FROM` or a join, `INSERT ... SELECT`, `DELETE ... WHERE key IN (...)`), in bounded batches when the set is large | The per-row logic is expressible in SQL with identical semantics (rounding, NULLs, collation, time zones); pays with many rows: n round trips and executions → one | Atomicity (the statement fails as a whole where the loop kept earlier rows); locks on every row at once and for longer; statement-level versus row-level triggers; per-row work in the application (events, logs, cache invalidation) that no longer runs; later rows no longer see earlier rows' writes ("Read-after-write" in `BEHAVIOR-TRAPS.md`) |
| `NOT IN (subquery)` for "rows with no match" | `NOT EXISTS` (an anti-join the planner can run as a hash or merge join) | The subquery's column is `NOT NULL` by constraint, or the original filtered NULLs out | Not equivalent with NULLs: if any subquery value is NULL, `NOT IN` returns no rows at all, and `NOT EXISTS` returns the unmatched rows. Where NULLs can occur the rewrite removes a bug: report it and apply it only with approval (rule 4) |
| `JOIN` followed by `DISTINCT` (or `GROUP BY` on every column) only to filter by the existence of a match | Semi-join: `EXISTS` or `IN (subquery)`, without the `DISTINCT` | Pays when the joined side has many matches per row, which the `DISTINCT` then sorts or hashes away | `DISTINCT` also collapsed rows that were duplicates in the outer table itself; `EXISTS` keeps them. Equivalent only when the selected columns include a unique key of the outer table |
| `UNION` of branches that cannot overlap | `UNION ALL` | The branches are disjoint by construction (filters on a `NOT NULL` column that exclude each other), and no branch can return duplicate rows of its own, which `UNION` also removed; pays by dropping a sort or hash over the whole result | Duplicates appear that `UNION` removed. The order `UNION` happened to produce was never guaranteed (see "Behavior traps") |
| Correlated scalar subquery in the select list, or a large child table joined and then grouped | Aggregate the child once (`GROUP BY` its key) and left-join the result, or a lateral join | The plan runs the subquery once per outer row (`loops` equal to the outer row count) | A scalar subquery with no match gives NULL, and the joined aggregate needs the same (`COUNT` of no rows is 0 in the subquery but NULL after a left join: use `COALESCE`); a scalar subquery matching two rows raised an error, while the join returns both rows silently |
| A common table expression referenced once, filtered outside, scanned whole | Let the engine inline it (PostgreSQL 12 and later inlines a non-recursive, side-effect-free CTE referenced once; `NOT MATERIALIZED` asks for it) or move the filter inside | The plan shows the CTE materialized and the outer filter applied afterwards | None to results when the CTE has no side effects and calls no volatile function; with a volatile function (`random()`, a sequence), inlining changes how many times it runs |
| Many single-key lookups, or a very long `IN` list built in application code | One statement per batch: an `IN` list of bound parameters chunked to a fixed size, one array parameter (`= ANY($1)` in PostgreSQL), or a join against a `VALUES` list or temporary table for thousands of keys (N+1 itself: "Production patterns" in `CORE-TECHNIQUES.md`) | Under the per-statement parameter limit (65,535 in PostgreSQL's client library, 2,100 per procedure in SQL Server, 32,766 in SQLite since 3.32.0 and 999 before); fixed chunk sizes or one array keep the number of distinct statements small, so statement caches and statistics still work; values stay bound ("Query building" in `BEHAVIOR-TRAPS.md`) | One row per matching row, not per requested key: duplicate keys in the request no longer repeat results, missing keys give nothing; rows come back in no particular order; per-key errors become one failure |
| A batch job walks a whole table with `OFFSET` pages | Walk by key: `WHERE id > :last ORDER BY id LIMIT n` (the keyset row in "Database queries" in `CORE-TECHNIQUES.md`) | A unique, indexed walk key | Under concurrent writes `OFFSET` skips or repeats rows and a key walk does neither, but it sees rows inserted later with larger keys; one cursor in one transaction sees a single snapshot but holds it open (see "Long transactions" under "Writes and transactions") |

## Indexes beyond the basics

Every index is a schema change (rule 5): it costs time on every insert and delete and on every update of its columns, takes space and buffer cache, can change other statements' plans, and building it can block writes (PostgreSQL's `CREATE INDEX CONCURRENTLY`, SQL Server's `ONLINE = ON`, and MySQL's online DDL avoid most of that blocking at extra cost). Name the statements it speeds up, the writes it slows, and how it will be built.

| Signal | Technique | Valid when | Behavior risk |
|---|---|---|---|
| The plan uses an index, then fetches many table rows only to read a few columns | Covering index: the needed columns as key or `INCLUDE` columns (PostgreSQL 11 and later, SQL Server), so the index answers alone (an index-only scan) | The added columns are few and narrow. In PostgreSQL an index-only scan still visits the table for pages not marked all-visible in the visibility map, so it pays on tables that vacuum keeps up with: check "Heap Fetches" in the plan | Results unchanged; a larger index with its own write cost |
| Queries filter on a small, fixed subset (`status = 'pending'`, `deleted_at IS NULL`) | Partial or filtered index with that predicate (PostgreSQL and SQLite partial indexes, SQL Server filtered indexes) | The query's `WHERE` implies the index predicate in a form the planner can prove. A parameter in place of the constant usually prevents that (PostgreSQL's generic plans, SQL Server's parameterized queries), so check the plan the application actually gets | A unique partial index enforces uniqueness only among the rows it covers: replacing a full unique index with one accepts rows the original rejected |
| Filters or sorts on an expression (`lower(email)`, a date truncation, a JSON field) | Expression or function-based index (PostgreSQL, SQLite, MySQL 8.0.13 and later functional key parts, Oracle) | The query uses the identical expression; the function is deterministic (PostgreSQL requires `IMMUTABLE`); the expression is computed on every insert and every update of its columns | Rewriting the query to match the index (`lower(email) = lower(:x)` where the original compared exactly) changes which rows match unless the original compared that way ("Database queries" in `CORE-TECHNIQUES.md`) |
| Slow inserts and updates on a table with many indexes | Find unused and redundant indexes (`pg_stat_user_indexes.idx_scan` in PostgreSQL, `sys.schema_unused_indexes` and `sys.schema_redundant_indexes` in MySQL, `sys.dm_db_index_usage_stats` in SQL Server); an index whose columns are a leading prefix of another's is usually redundant. Hide before dropping (invisible indexes in MySQL 8.0 and Oracle) | Usage counters cover only the time since they were last reset (restart, failover, a manual reset), and each replica counts its own queries; an index can serve a monthly job, enforce a unique or primary key, or back a foreign key (deleting a referenced row scans the referencing table without it) | Dropping an index that enforces uniqueness removes a constraint (behavior change); other drops change only plans, but are schema changes (rule 5) |
| A frequently updated column is indexed (a status, a counter, `updated_at`) | Keep frequently updated columns out of indexes no important query needs | PostgreSQL updates a row in place without touching any index (a heap-only tuple update) only when no indexed column changes (summarizing indexes such as BRIN excepted) and the page has room; indexing such a column turns every update into new entries in every index | Results unchanged; a query that used the index gets a different plan |

## Writes and transactions

What commits together, what other sessions see before the commit, what is locked and for how long, and which error aborts what are all part of the outcome. Most speedups here change one of them: list it (rule 5) unless the developer asked for that technique.

| Signal | Technique | Valid when | Behavior risk |
|---|---|---|---|
| Rows inserted one statement at a time, each in its own transaction (autocommit) | Bulk load: `COPY` (PostgreSQL), `LOAD DATA` (MySQL), multi-row `INSERT ... VALUES`, or the driver's batch API (JDBC `executeBatch`, with pgjdbc's `reWriteBatchedInserts` or Connector/J's `rewriteBatchedStatements` to send multi-row inserts) inside one transaction or a few | Pays with many rows: a round trip, a parse, and a log flush per commit dominate (SQLite's FAQ: a few dozen transactions per second on a rotating disk, against tens of thousands of inserts per second in one transaction). For large initial loads, dropping indexes and foreign keys and recreating them afterwards is faster, then refresh statistics; that drop is a schema change and leaves a window without the constraints | One failing row aborts the whole batch where the loop kept earlier rows; generated keys come back differently; ORM batching can be silently off (Hibernate cannot batch inserts of entities with `IDENTITY` keys) |
| Each row or message committed separately in a long-running loop | Commit every N rows or every T milliseconds | Commit cost (a log flush) dominates; N bounded so locks and undo stay small | Visibility and atomicity: other sessions see rows appear in groups, later; a crash loses up to N rows the loop had already committed, so the producer must replay them (idempotent writes) or callers must accept it. A behavior change unless requested, and wrong wherever each commit was acknowledged to someone |
| One huge transaction (backfill, purge of old rows) blocks other sessions or bloats the table | Split into bounded batches by key range, each its own transaction, restartable from the last key | Each batch is idempotent; the job records its position | Other sessions see the half-done state between batches, and an error leaves earlier batches committed: atomicity lost (rule 5) |
| Check-then-write: `SELECT` to see whether a row exists, then `INSERT` or `UPDATE`; or read a value, compute, write it back | One statement: an upsert (`INSERT ... ON CONFLICT` in PostgreSQL and SQLite, `INSERT ... ON DUPLICATE KEY UPDATE` in MySQL, `MERGE` in SQL Server) or an in-place update (`SET n = n + 1`) | A unique constraint exists to arbitrate the conflict; pays as two round trips → one | The original's race (duplicate rows or lost updates under concurrency) is a bug: the rewrite removes it, so report it and apply with approval (rule 4). MySQL's `ON DUPLICATE KEY UPDATE` on a table with several unique indexes can update a different row than expected, and reports 1 or 2 affected rows; SQL Server's `MERGE` can still raise unique key violations under concurrency unless it runs with `HOLDLOCK` |
| **Long transactions**: a transaction held open across network calls, user think time, or long computation ("idle in transaction") | Do reads and computation outside; open the transaction only around the writes | Pays because locks and snapshots are held for less time; in MVCC engines an old snapshot keeps vacuum or purge from removing dead rows in every table, so the whole database bloats | Reads moved outside the transaction can see a different state from the one the write acts on: keep the check atomic (a version column with `UPDATE ... WHERE version = :v`, or a conditional update) or the rewrite adds a race |
| Many sessions update the same row (a global counter, a balance, a sequence table, a "last updated" row) | Spread the hot row: several counter rows summed on read, increments accumulated and applied as one update, or a database sequence instead of a counter table | Readers can afford the sum, or the delay of accumulated increments | Reading the exact current value costs more or lags; sequences are not rolled back, so numbers have gaps (a behavior change where gapless numbers are required, such as invoice numbers) |
| Deadlocks under load (two transactions lock the same rows in different orders) | Take locks in one consistent order (sort the keys of a batched update; the same table order on every path); keep transactions short; retry the whole transaction on a deadlock or serialization error | A retry re-runs the whole transaction and the transaction has no effects outside the database (emails, calls to other services) | Retries repeat outside effects; the order of writes inside the transaction changes ("Order of side effects" in `BEHAVIOR-TRAPS.md`) |
| Workers polling a queue table with `SELECT ... FOR UPDATE` block each other | `FOR UPDATE SKIP LOCKED` (PostgreSQL, MySQL 8.0), so each worker claims rows the others have not | Used only to claim work: a query with `SKIP LOCKED` sees an inconsistent view of the table by design | Strict first-in, first-out order across workers is lost |
| Isolation level lowered for speed, or raised to fix contention; snapshot reads turned on (`READ_COMMITTED_SNAPSHOT` in SQL Server) | Treat as a behavior change, never as tuning | Approved by name, with tests that run concurrent transactions | Lowering allows anomalies the original prevented (non-repeatable reads, lost updates, write skew); raising adds serialization failures callers must retry; snapshot reads return the last committed value where the original waited for the writer |

## Schema and data layout

All of these are schema changes and need approval (rule 5); a migration also has its own cost and locking on a large table.

| Signal | Technique | Valid when | Behavior risk |
|---|---|---|---|
| A large table where most queries touch a recent slice or one key's rows, or old rows are purged with large `DELETE`s | Partitioning by range, list, or hash on the filtered column, with old partitions dropped or detached instead of deleted | Pays when the table is much larger than memory and queries filter on the partition key, so the planner prunes partitions (at planning time, or at execution time for parameters). Queries without the key scan every partition; many partitions raise planning time and memory | A unique or primary key on a partitioned table must include the partition key (PostgreSQL), so uniqueness of other columns is no longer enforced across partitions; dropping a partition fires no `DELETE` triggers; updating the key moves the row |
| The same expensive join or aggregate computed on every read | Precompute: a stored generated column, a summary table maintained in the same transaction as the base writes, or a materialized view (incremental maintenance: "Change propagation" in `techniques/data-at-scale.md`) | A generated column is always current; a summary maintained by the writer is current but adds write cost and can become a hot row; a materialized view is stale until refreshed (PostgreSQL's `REFRESH MATERIALIZED VIEW CONCURRENTLY` needs a unique index, and the view is not maintained automatically) | Staleness is a behavior change unless the developer asked for that technique (then state the refresh bound); access rules on the base tables must still apply to reads of the copy |
| Random keys (UUID version 4, hashes) as the primary key of a large B-tree index or clustered table with heavy inserts | Time-ordered keys (UUID version 7, RFC 9562; or an identity column, with a random public identifier stored separately) | Pays when the index is larger than memory: random keys insert into random leaf pages, so every page of the index is in the working set; ordered keys append at one edge | Version 7 identifiers reveal creation time, which matters when identifiers are exposed; sorting by key becomes creation order, which callers may notice |
| Numbers, dates, booleans, or keys stored as text and converted in queries | Native types (integer, date or timestamp, boolean, uuid) | Every stored value converts losslessly (leading zeros, invalid dates such as `2024-02-30`, time zones, trailing spaces) | Sort order and equality change (as text `'10' < '9'`), and inputs the column used to accept are rejected: a behavior change for every reader and writer |

## Connections and round trips

When each statement is fast, time goes to connecting and waiting on the network. N+1 queries are in "Production patterns" in `CORE-TECHNIQUES.md`; the rows here are the patterns that remain after it.

| Signal | Technique | Valid when | Behavior risk |
|---|---|---|---|
| A new connection per request or per statement | A connection pool in the application, or an external pooler (PgBouncer), sized to what the database can run at once rather than to the number of clients | Connection setup (TCP, TLS, authentication, and in PostgreSQL a server process per connection) is large next to the statements; pool size stays small, since connections beyond what the cores and disks can serve only add contention | Session state leaks between borrowers (settings, temporary tables, prepared statements, advisory locks, an open transaction) unless reset on return; transaction-level pooling breaks session features; a full pool makes requests wait or time out ("Locks and pools" in `BEHAVIOR-TRAPS.md`) |
| Many small statements in sequence, each waiting for the previous result, over a high-latency link | Pipelining (libpq pipeline mode, PostgreSQL 14 and later) or the driver's batch API, so several statements share one round trip | The statements do not depend on each other's results; pays when round-trip time is large next to execution time | Error handling: in a pipeline an error skips the remaining statements up to the next synchronization point; partial failure of a batch depends on the driver (JDBC's `BatchUpdateException`) |
| ORM relations loaded lazily inside a loop | Eager loading declared for that query (`select_related` or `prefetch_related` in Django, `JOIN FETCH` or an entity graph in JPA, `includes` in Rails) | Only on the code path that uses the relation; loading a to-many relation through a join repeats parent rows (two collections at once give a Cartesian product), so a separate `IN` query per relation is often better | Objects loaded at a different moment can reflect a different state; filters and scopes on the relation (soft deletes, tenant scopes) must still apply |
| Each object saved with its own save or flush in a loop | The ORM's bulk operations (`bulk_create`, `bulk_update`, or `QuerySet.update()` in Django; `insert_all` or `update_all` in Rails; JDBC batching through `hibernate.jdbc.batch_size` in Hibernate) | Pays with many objects | Bulk methods skip per-object hooks: Django's `bulk_create` and `update()` do not call `save()` or send its signals, and Rails' `insert_all` and `update_all` skip callbacks and validations. Whatever those hooks did (validation, audit records, cache invalidation, search indexing) is kept by other means or listed (rule 5) |

## Inside engines

For people building or tuning a database, query engine, or storage layer. Storage structures (B+ trees, LSM trees and compaction, Bloom filters, MVCC, zone maps, prefix compression) are in "Storage and indexing" in `techniques/data-at-scale.md`, encodings in "Compression and encoding" there, and external sorting and spilling joins in "Streaming and external memory" there; eviction policies in general are in `techniques/specialized-structures.md`. Count pages and cache misses, and keep the engine's documented guarantees (durability, isolation, result semantics) fixed: an engine optimization that weakens one is a behavior change for every application on it.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Choosing a join algorithm | Nested loop with an index on the inner side for a small outer input; hash join for large equi-joins (build on the smaller input); merge join when both inputs are already sorted on the key or the sorted order is needed later (an "interesting order", Selinger et al.) | The choice depends on cardinality estimates: a nested loop chosen on an underestimate is the classic catastrophic plan. Hash joins need memory or partitioning to disk and work only on equality; non-index nested loops are O(n × m) | Index nested loop O(outer × log inner); hash join O(n + m) expected; merge join O(n + m) after sorting |
| Plans are bad although the cost model looks right | Improve cardinality estimates first (statistics on correlated columns, sampling), and prefer plans that degrade gracefully when estimates are uncertain (hash joins over non-index nested loops) | Leis et al. found estimation errors grow with the number of joins, are mostly underestimates, and matter more than the cost model | Avoids the plans that are orders of magnitude slower |
| Analytic scans read a few columns of wide tables in a row store | Columnar storage with compression and late materialization (C-Store) | Read-mostly, scan-heavy workloads touching few columns; point updates and whole-row reads get slower. Abadi et al. found the gain comes from column-specific execution (compression, late materialization, block iteration), not from splitting columns inside a row store | I/O proportional to the columns read, and compressed data processed directly |
| CPU-bound queries on data in memory spend their time in per-row interpretation (one `next()` call and type dispatch per row per operator) | Vectorized execution: operators process vectors of about a thousand values per call (MonetDB/X100); or compile the query into tight loops (Neumann) | Vectors sized to stay in the CPU cache; NULL handling, overflow checks, and error behavior identical to the row-at-a-time path; aggregations that regroup floating-point sums change bits ("Numbers" in `BEHAVIOR-TRAPS.md`) | Per-row interpretation overhead amortized over the vector; large constant-factor speedups on CPU-bound queries |
| Commit throughput limited by one log flush per commit | Group commit: one log write and flush covers the commit records of several transactions (`commit_delay` in PostgreSQL, `binlog_group_commit_sync_delay` in MySQL) | Many concurrent committers; each commit is still acknowledged only after its record is durable. Acknowledging before the flush (PostgreSQL `synchronous_commit = off`, MySQL `innodb_flush_log_at_trx_commit` = 0 or 2) can lose recent commits in a crash: a durability change that needs approval | Flushes per second no longer bound commits per second; latency per commit may rise slightly |
| The buffer pool's hit rate collapses while a large scan or bulk job runs | Scan-resistant replacement: LRU-K (O'Neil, O'Neil, and Weikum), 2Q (Johnson and Shasha), CLOCK with usage counts plus a small ring of buffers for bulk scans (PostgreSQL), or midpoint insertion (InnoDB) | Plain LRU lets pages read once evict the hot set; evaluate with a mixed workload of scans and point lookups | Hot pages stay resident during scans; CLOCK also avoids reordering a list on every hit |
| An in-memory index where comparisons in a B-tree or a hash table dominate, and ordered scans are still needed | Adaptive radix tree (Leis, Kemper, and Neumann): node sizes adapt to the number of children, with path compression; faster than main-memory B-trees and comparable to hash tables for point lookups | Keys transformed to a binary-comparable form (big-endian integers with the sign bit flipped; collation keys for strings), so byte order equals the original order | Lookup cost proportional to key length rather than log n; ordered iteration kept |

## Behavior traps

Rewrites that look equivalent but are not; check them alongside "I/O and databases" in `BEHAVIOR-TRAPS.md`.

- **Order without `ORDER BY`.** Rows come back in whatever order the plan produces. A new index, a different join method, a parallel plan, synchronized sequential scans, or more data reorders them, so the same order in tests on a small table proves nothing. When a caller depends on that order, the original relied on unspecified behavior: reproduce it with an explicit `ORDER BY` and a test, and log the dependence as a bug (rule 4). SQLite's `PRAGMA reverse_unordered_selects` exposes such dependence.
- **NULLs.** `NOT IN` with a NULL in the list returns nothing; `= NULL` is never true; `COUNT(column)` skips NULLs where `COUNT(*)` does not; `SUM` of no rows is NULL, not 0; engines sort NULLs differently by default (PostgreSQL as larger than every value; MySQL, SQLite, and SQL Server as smaller), so moving a sort between engines, or between the database and application code, moves them.
- **Collation and case.** Equality, `LIKE`, `ORDER BY`, `GROUP BY`, `DISTINCT`, and unique constraints follow the column's collation. MySQL 8.0's default collation (`utf8mb4_0900_ai_ci`, unless the server, database, table, or column sets another) ignores case and accents, so `'a' = 'A' = 'á'` there and not in application code. Moving a comparison between the database and the application, changing a column's collation, or adding `COLLATE` to reach an index changes which rows match and their order.
- **Isolation and visibility.** Moving a read into or out of a transaction, splitting or merging transactions, batching commits, and acknowledging commits before they are durable each change what concurrent sessions see and when. Snapshot isolation levels add serialization failures that callers must retry.
- **Triggers, constraints, and side effects.** A set-based statement fires statement-level triggers once, and row-level triggers per row in no promised order. SQL Server's DML triggers fire once per statement, so trigger code written for single-row statements breaks on a set-based rewrite. Bulk paths differ from row paths: `TRUNCATE` fires no `DELETE` triggers, and ORM bulk methods skip per-object hooks. A non-deferrable unique constraint in PostgreSQL is checked row by row, so `UPDATE t SET pos = pos + 1` can fail where per-row updates in a chosen order succeeded.
- **Timeouts and locks.** One set-based statement can exceed a statement timeout that each per-row statement met, and holds more locks for longer; SQL Server escalates many row locks in one statement to a table lock, which blocks every other session on that table. A schema change waiting for its lock also blocks the statements queued behind it: set a lock timeout for migrations.
- **Replica lag.** Moving reads to a replica (or to a cache) serves data as of the replica's last replayed change. A user who writes and then reads may not see their own write; read-your-writes needs routing to the primary after a write, or waiting until the replica has replayed it. Queries on a replica can also be cancelled when they conflict with replay.

**Verification.** Run the original and the new statement on the same representative data in a test database, including NULLs, duplicates, ties in every sort key, strings that differ only by case or accent, empty inputs, and keys missing from a batch; compare results as sequences when a caller relies on order and as multisets otherwise. For writing statements, run each version on its own copy of the same data (or in a transaction rolled back) and compare the full contents of every table it touches, including tables written by triggers. For transaction, locking, or isolation changes, run concurrent sessions that interleave the operations (two workers claiming the same rows, a reader during a batched write) and check what each sees. Compare plans at production-like sizes, since the plan on a small table is not the one production runs.
