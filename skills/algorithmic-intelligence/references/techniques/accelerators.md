# Accelerators (GPUs and Similar)

The shared rules and table conventions in `ADVANCED-TECHNIQUES.md` apply to every table here.

**Contents:** When offload pays · Data-parallel algorithms and structures (Parallel primitives, Sorting and grouping, Contention and counting, Irregular work and graphs, Spatial and geometric, Dense tiling, Data structures) · Kernel-level techniques · Measuring and verifying on a device · Behavior traps

For code that runs, or could run, on a GPU or another accelerator with its own memory and thousands of threads. Decide first whether offload pays at all, since the transfers can cost more than the kernel saves; then choose algorithms that suit lockstep thread groups; tune the kernel only after a device profiler shows where it stalls. Device results differ from CPU results in ways a single test run hides, so measure and verify them as "Measuring and verifying on a device" describes. CPU threads, SIMD, and lock contention are in `techniques/hardware-and-concurrency.md`.

## When offload pays

A GPU or other accelerator runs thousands of simple operations at once and reads its own memory far faster than a CPU reads main memory, but the data must first cross the link between host and device, which is many times slower than either memory (for example, about 16 GB/s for a PCIe x16 Gen3 link against hundreds of GB/s or more for device memory), and every kernel launch and synchronization adds a fixed cost of its own, however little work it carries. So offload pays only when the work done per byte moved (arithmetic intensity) is high enough, and the batch large enough, to repay the transfers and launches. Count the whole operation, not the kernel alone: host-to-device copy, allocation, launches, synchronization, and the copy back (rule 8). A kernel that is ten times faster can still make the operation slower.

Offload also changes behavior in ways tests on one machine miss: see "Behavior traps".

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Large, data-parallel, compute-heavy work on the CPU (dense matrix products, convolutions, FFTs, per-pixel or per-particle updates over millions of elements) | Offload to the accelerator, through the vendor's tuned library (BLAS, FFT, and deep-learning libraries for the device) before hand-written kernels | Arithmetic intensity high enough that device time plus both transfers beats the CPU, measured end to end at the real sizes; sizes below the measured crossover stay on the CPU; behavior change wherever results differ in floating point (see "Behavior traps"); a new device dependency needs the developer's approval (rule 7) | Several times faster end to end at large sizes, against optimized CPU code; slower below the crossover |
| Data copied to the device and back between consecutive steps of a pipeline (each step offloaded separately, with the host reading intermediates it does not need) | Keep data resident on the device across steps: transfer the inputs once and the final results once, even running a step on the device that is no faster there, to avoid a round trip | The working set fits in device memory at the largest size callers can pass, or is processed in chunks; the host does not need the intermediates (logging, checks, or side effects between steps keep their order) | Transfers per step → transfers per pipeline; often the largest win in an offloaded program |
| Transfers and kernels run one after another, so the device idles during copies | Page-locked (pinned) host buffers with asynchronous copies on several streams, overlapping the copy of one chunk with the computation of another | Chunks are independent; pinned memory is bounded, since locking too much host memory degrades the rest of the system; buffers are not reused before their copy completes | Transfer time hidden behind computation, up to the slower of the two |
| Many small kernel launches or device calls (one per item, row, or small matrix) | Batch into one launch (batched library routines, one kernel over all items), fuse consecutive element-wise kernels into one, or record the launch sequence once and replay it (graph capture, such as CUDA Graphs) | Items are independent; fusion keeps each element's operation order (or the change in rounding is reported); a profile shows launch overhead or idle gaps dominate | Launch overhead paid once per batch instead of once per item |
| A kernel far below the device's peak: a profiler (such as Nsight Compute or the vendor's equivalent) shows uncoalesced memory access, low occupancy, or divergent branches | Restructure for the device: adjacent threads read adjacent addresses (structure of arrays), tune block size and per-thread register and shared-memory use for occupancy, group work so threads that run together take the same branch (sort or bin items by branch) | Results identical, except where reduction order changes (report it); reordering items for branch coherence restores the original output order | Constant factor, often several times; measured, since occupancy above what hides latency gains nothing |
| Lower precision proposed for throughput (16-bit or bfloat16 storage, reduced-precision matrix units) | Mixed precision: low-precision inputs with higher-precision accumulation, loss or range scaling where values can underflow | Behavior change: report the error against a full-precision reference on representative and extreme inputs; the developer decides | Several times the throughput on hardware with low-precision units; half the memory traffic |
| An offloaded path where some deployments have no device, or the device can fail or run out of memory | Select the device or the CPU path once at startup by capability, with the CPU fallback kept and tested | Both paths pass the same differential tests with the tolerance stated (as for the runtime dispatch row in "Parallelism and vectorization" in `techniques/hardware-and-concurrency.md`); device errors surface as the original's errors would, never as silently wrong results; out-of-memory falls back or fails as the original's behavior allows | Device speed where available, with no loss of correctness elsewhere |

## Data-parallel algorithms and structures

An algorithm that is best on a CPU is often a poor fit for a GPU, and the reverse. A GPU runs thousands of threads in groups that execute in lockstep (warps or wavefronts), so:
- **Divergence costs.** Threads in one group that take different branches, or loop different numbers of times, run one after another while the rest wait.
- **Contention costs.** Thousands of threads updating one counter or one memory location serialize on it.
- **Span matters as much as work.** A sequential chain of n steps leaves the device idle, and an algorithm that does a little more total work with logarithmic span (a scan, a radix sort) usually beats one that does less work in a long chain ("Work and span" in "Parallelism and vectorization" in `techniques/hardware-and-concurrency.md`).
- **Memory access patterns decide speed.** Adjacent threads should read adjacent addresses, and data reused by a block of threads should be staged in fast on-chip shared memory.

So prefer established data-parallel libraries (for example CUB and Thrust for primitives and sorting, cuDF for tables, cuGraph for graphs, cuBLAS and CUTLASS for dense algebra, or the vendor's equivalents) over hand-written kernels: they are tuned per device generation and handle the edge cases. Write a kernel only when no library routine fits, and test it differentially against the CPU version. The behavior risks in "Behavior traps" (regrouped floating-point sums, atomics, output and tie order) run through every table below; each row names the ones it triggers.

GPU sparse-matrix formats (ELL, sliced ELL, CSR5) and when each beats CSR are in "Sparse matrices and scientific computing" in `techniques/math-and-numerics.md`.

### Parallel primitives

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A sum, minimum, maximum, or other combination over a large device array, computed by one thread, a loop of kernel launches, or every thread doing an atomic update on one result | Tree reduction: each block reduces its part in shared memory and registers (warp shuffles), then the partial results are reduced; or the library's reduction | The operation is associative (floating-point addition is not exactly: the grouping changes the result, so state the difference, or use a library mode that guarantees run-to-run or device-to-device identical results, or reproducible summation from "Numerical computation" in `techniques/math-and-numerics.md`); the identity value and the empty-input result match the original | O(n) work with O(log n) span instead of an O(n) chain or contention on one address |
| A running total, offsets for variable-length output, or any loop where each element depends on the previous one through an associative operation; or such a loop restarted per group | Parallel prefix sum (scan), and segmented scan, which restarts at segment boundaries marked by flags or offsets, in one pass (single-pass scan with decoupled look-back in current libraries) | Associative operation; inclusive or exclusive as the original computes; floating-point results differ from the sequential order (behavior change); integer overflow at the same positions as the original, or the wider type the original uses | Sequential O(n) span → O(log n) span with O(n) work; about the cost of copying the array once in a tuned library |
| Filtering, removing elements, or partitioning on the device by appending to an output through a shared atomic counter | Stream compaction by scan: compute a 0 or 1 flag per element, an exclusive scan of the flags gives each kept element its output position, then scatter (the library's select, partition, or copy-if) | Output order: the scan keeps the input order, which the atomic version did not, so callers that relied on the original sequential order get it back and callers of the atomic version see a deterministic order (state which) | One contended counter → O(n) work, O(log n) span, deterministic output |

### Sorting and grouping

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Sorting large arrays of integer, floating-point, or fixed-width keys on the device with a comparison sort, or copying them back to the host to sort | Least-significant-digit radix sort (the library's device radix sort), sorting key-value pairs where the values are payloads or indices | Keys map to unsigned bits in order (floating-point keys are bit-transformed; how NaN sorts, and whether −0.0 and +0.0 compare equal, follow the library's documentation and must match the original); radix sort is stable, so equal keys keep their input order, which matches a stable original but differs from an unstable one's tie order; sorting only the significant bit range of bounded keys saves passes | O(n log n) comparisons → O(n · b / d) work for b-bit keys and d-bit digits; usually the fastest device sort for primitive keys |
| Merging two sorted device arrays, or sorting with a comparator that radix sort cannot express (composite or custom keys) | Merge path: partition the merge into equal-size pieces by a binary search along cross-diagonals, so every thread or block merges the same number of elements regardless of the data; merge sort built on it | Same comparator; stable when ties are taken from the first input first (state the tie rule); results identical to a sequential stable merge | Balanced O(n) merge with O(log n) span per merge level; no thread gets a long run while others idle |
| Grouping, deduplicating, or joining on the device with a shared hash table updated by atomics, where output order or skewed keys matter | Sort by key (radix sort), then find group boundaries by comparing neighbors and aggregate each run with a segmented reduction; sort-merge join for joins | Output comes out in key order, unlike the hash version's order that depends on scheduling (state the order); aggregates over floating point follow the reduction rule above; hash grouping is usually faster when the distinct keys fit in fast memory, so measure both | Deterministic output and no slowdown from heavily repeated keys, at O(n) radix-sort cost |

### Contention and counting

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A histogram, count, or per-key aggregate built by every thread atomically updating a global array, with a profile showing atomic contention (few bins, skewed data) | Privatization: each block (or warp) accumulates into its own copy in shared memory, then the copies are merged into the global result at the end; for many bins, sort-then-reduce instead | The private copies fit in shared memory; integer counts give identical results, while floating-point aggregates merged in a varying order differ from run to run (merge in a fixed order to make them reproducible); the counter type cannot overflow sooner than the original's | Global atomic contention reduced by about the number of threads per block; skewed inputs no longer serialize on one bin |

### Irregular work and graphs

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| One thread per row, vertex, or item where items have very different sizes (row lengths of a sparse matrix, vertex degrees in a power-law graph), so a few long items stall their warps | Load balancing: merge-path partitioning of the combined list of item boundaries and elements, so each thread gets an equal share of elements; or binning items by size and processing small items per thread, medium per warp, large per block | Results identical where each item's elements are combined in the original order; splitting one item across threads regroups its reduction (floating-point differences, as above) | Time set by total work divided by threads instead of by the largest item |
| Breadth-first search or another level-by-level traversal on the device that scans every vertex per level, or launches one thread per vertex whether active or not | Frontier-based traversal over compressed sparse row (CSR) adjacency: expand only the current frontier, build the next frontier by scan-based compaction; direction-optimizing BFS switches to a bottom-up step (unvisited vertices look for a parent in the frontier) while the frontier is large | Distances identical; the parent chosen for each vertex, and the order vertices are discovered within a level, can differ (behavior change if a BFS tree or order is reported); bottom-up steps need incoming edges (the transpose, for directed graphs), which costs memory | O(V · levels) → O(V + E) total work; direction-optimizing skips most edge checks on low-diameter graphs |

### Spatial and geometric

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Points, particles, or objects processed in arbitrary order, so threads that run together touch distant memory | Sort by Morton (Z-order) code: interleave the bits of quantized coordinates so that items near each other in space are near each other in memory | Quantization resolution chosen so distinct items stay distinguishable where it matters; reordering changes floating-point accumulation order in later passes, and the original order is restored for output if callers see it | Better memory coalescing and cache use; a precondition for the two rows below |
| Neighbor search within a fixed radius (particle interactions, collision detection, density estimation) comparing all pairs | Uniform grid (cell list): a cell size at least the search radius, items sorted by cell index, cell start and end offsets from the sorted array; each item checks its own and adjacent cells | Search radius bounded and items fairly evenly spread (heavy clustering puts many items in one cell, back toward O(n²)); neighbor order differs from the original (sorting the neighbors, or an order-independent combination, keeps results identical) | O(n²) → about O(n · neighbors) after an O(n) sort-based build |
| Bounding-volume hierarchy built on the device top-down with sequential splits, or rebuilt on the host every frame | Linear BVH: sort objects by Morton code, then build all internal nodes in parallel from the sorted codes (each node finds its range from the common prefix length of neighboring codes) | Tree quality is lower than a surface-area-heuristic build, so queries visit more nodes (measure query time, not only build time); duplicate Morton codes are disambiguated (for example by index); query results that are sets are identical, while the order of hits and which of equidistant hits is returned can differ | O(n log n) sequential build → O(n) work after the sort, fully parallel; fast enough to rebuild every frame |

### Dense tiling

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A hand-written device kernel for matrix products, convolutions, or stencils in which each thread reads its inputs from device memory | Call the vendor library first (BLAS, convolution, FFT); write a kernel only for a fused or unusual operation, and then tile it: each block loads a tile of inputs into shared memory once, every thread reuses it, and stencils load a tile plus its halo | Summation order changes with tile shape (floating-point differences; libraries can also pick different algorithms per size and device, with different rounding, unless a deterministic mode is set); shared-memory size per block bounds the tile | Memory traffic divided by about the tile width; libraries typically reach a large fraction of the device's peak, which hand-written tiled kernels rarely match |

### Data structures

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Key lookups or inserts on the device through a sorted array with binary search per thread, or by copying keys back to a host hash map | Device hash table with open addressing (linear or bucketed probing) or cuckoo hashing, claiming slots with atomic compare-and-swap; a table built in bulk and then only queried (static) is simpler and faster than one that supports concurrent inserts and deletes (dynamic) | Load factor kept below the design limit (probe lengths and cuckoo insertion failures grow sharply near full, so a failed build is handled by rebuilding larger); iteration order depends on the hash and on thread scheduling, so it differs between runs unless sorted afterwards; which duplicate key wins a concurrent insert is unspecified; keys chosen by an attacker need a keyed hash or a bound ("Algorithmic complexity attacks" in `techniques/hostile-inputs.md`) | O(log n) dependent reads per lookup → about one or two memory transactions, expected |
| Trees with pointer-linked nodes traversed on the device (decision trees, search trees, spatial trees), each thread chasing pointers through scattered memory | Flatten into arrays: breadth-first (level-order) layout with children found by index arithmetic or stored offsets, built on the host or by a parallel build, and kept read-only during queries | The tree is static between rebuilds; traversal results identical; threads following different paths still diverge, which sorting queries by path (or by Morton code) reduces | Fewer, coalesced memory reads per level and no pointer chasing |
| Flags, sets, or small values stored as one byte, word, or object per element on the device | Packed arrays and bitmaps: one bit per flag, with population count and warp-wide ballot or vote operations to count and compact them | Value ranges fit (as for compact representations in "Memory locality" in `techniques/hardware-and-concurrency.md`); concurrent updates to bits in the same word use atomic bitwise operations, or each word has one writer | Up to 8 to 32 times less memory traffic; whole-warp counting in one instruction |

## Kernel-level techniques

Select these for a hand-written kernel that a device profiler shows is stalled on memory, barriers, atomics, or launches, after the library routines in the tables above have been ruled out. Each changes how the work is mapped onto threads, so races that one test run misses are the main risk: run the vendor's race and synchronization checker (such as `compute-sanitizer` with its racecheck and synccheck tools, or the vendor's equivalent) over the differential tests, or mark the change `NEEDS-TESTING`.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A block-wide scan, filter, or count goes through shared memory with a barrier per step, or every thread does its own atomic increment on a global counter to claim an output slot | Warp-level primitives: shuffle-based scans and reductions within a warp; vote and ballot with a population count to give each thread its offset among the active threads; warp-aggregated atomics, where one leader thread per warp does a single atomic for the whole warp and shares the base offset | Use the explicit-mask (`_sync`) forms with the mask of the threads that actually reach the call: threads of one warp can run independently on recent devices, so code that assumes they move in lockstep is a race; do not hard-code a warp width of 32 where the code can run on 64-wide wavefronts; output order across warps still depends on scheduling (as in "Behavior traps") unless the positions come from a scan | Fewer shared-memory round trips and barriers; global atomics divided by up to the warp width |
| A profiler reports shared-memory bank conflicts: threads of a warp read a tile by column (a transpose, a column pass of a stencil) or with a stride that is a multiple of the bank count | Padding (one extra element per row of the shared tile) or swizzling (XOR the column index with bits of the row) so the addresses a warp reads fall in different banks | Results identical, since only the layout changes; padding enlarges shared memory per block, which can lower occupancy; a swizzle is applied identically on every write and every read of the tile | Accesses that were serialized up to the warp width run in one pass |
| Each thread computes one output while its neighbors reload the same inputs, or many more threads are launched than the device runs at once, each repeating the same setup | Register blocking and thread coarsening: each thread computes several outputs, keeping inputs and partial results in registers and doing the shared setup once | More registers per thread can spill to slow local memory or cut occupancy, so measure; fewer threads can leave the device idle at small sizes; each output keeps its summation order, or the difference is reported | Fewer loads per output; often faster at lower occupancy |
| A tiled loop loads a tile, waits at a barrier, then computes on it, so the loads and the arithmetic never overlap (the profiler shows memory stalls) | Double buffering (software pipelining): two or more shared-memory stages, issuing the copy of the next tile (hardware asynchronous global-to-shared copies where the device has them, or loads into registers) while computing on the current one | Every stage is waited on before it is read and before it is overwritten: a missing wait reads stale data without any error, so run the race checker; shared memory grows with the number of stages; devices without asynchronous copies keep a tested fallback path | Memory latency hidden behind arithmetic, up to the slower of the two |
| Many short kernel launches, or blocks with very uneven work, leave the device idle between launches or waiting on the last few blocks | Persistent kernel: launch only as many blocks as the device can hold at once; each loops, taking the next item from a global work queue with an atomic counter, until the queue is empty | Never more blocks than can be resident at the same time when any block waits on another (otherwise the waiting block can occupy the slot the other needs, a deadlock): use the cooperative launch that guarantees co-residency for grid-wide waits; items are independent; the order items are processed depends on scheduling, so results are combined order-independently or in a fixed order afterwards | Launch overhead paid once; load balanced dynamically across blocks |
| Matrix-shaped arithmetic (dense products, convolutions, attention, batches of small matrices) on general-purpose cores of a device that has matrix units | Cast the work as small matrix multiply-accumulates on the matrix units (tensor cores and similar), through the vendor library or the warp-level matrix API | Behavior change: inputs are rounded to 16-bit, bfloat16, or TF32 formats, and the units' accumulation and rounding differ from IEEE single precision; report the error against a full-precision reference on representative and extreme inputs and let the developer decide (as for mixed precision in "When offload pays"); dimensions padded to the multiples the units need, with the padding contributing zeros | Several times the throughput of the general-purpose cores on the same device |
| Many small arrays (per block, per window, top-k candidates) sorted one per thread with an insertion sort, or one device sort launched per array | Sorting network (bitonic or odd-even merge) in registers or shared memory within a warp or block: the same compare-exchange sequence whatever the data, so no thread diverges | Not stable: equal keys can swap, so the tie order differs from a stable original unless the index is part of the key; sizes padded to a power of two with a sentinel that sorts last, with NaN placed as the original places it; O(n log² n) comparisons, so only for small arrays | Branch-free sorting of small arrays at register and shared-memory speed |
| Parallel code draws random numbers from one shared generator (serialized or atomic state), or from per-thread generators seeded by thread number, so results change when the block size, thread count, or device count changes | Counter-based generator (Philox, Threefry): each value is a keyed function of a counter built from the element's index and the draw number, so no state is shared and every value is fixed by the seed and the element | The sequence differs from the original generator's, so seed-based expected values change: a behavior change the developer approves (see "Random number consumption" in `techniques/machine-learning.md`); counters never repeat across elements or draws (reserve a counter range per element); statistical quality as the original's needs, which these generators were designed and tested for | Same results whatever the work split or launch configuration; no contention on generator state |
| Several devices combine partial results (gradients, sums) by copying them to the host or to one device and back | The communication library's collectives (all-reduce, reduce-scatter, all-gather), which use ring or tree algorithms over the fastest links, overlapped with computation where the framework allows | The reduction order depends on the algorithm, the number of devices, the topology, and the message size (libraries pick the algorithm automatically), so floating-point results differ from one device and between configurations: report it or fix the algorithm; every device calls the collectives in the same order, or the job hangs | Ring all-reduce sends about 2(p − 1)/p times the data per device, nearly independent of the device count p |
| A profile shows device allocation and release on every call or iteration (these can synchronize the device), or kernels stall on page faults of unified (managed) memory | A stream-ordered memory pool or the framework's caching allocator, allocating once and reusing; for unified memory, prefetch the data to the device before the kernel that uses it (and back before the host reads it) | Memory is reused only after the work that last used it has finished in stream order (across streams, wait on an event first); the pool keeps memory that other processes then cannot use, so set a release threshold where the device is shared; prefetching changes timing only | Allocation off the critical path; data migrated in bulk instead of page by page on faults |

## Measuring and verifying on a device

Device timings and device results both mislead by default. The general method is in `BENCHMARKING.md` and `DIFFERENTIAL-TESTING.md`; these are the device-specific parts.

- **Calls return before the work finishes.** Kernel launches and most device calls are asynchronous, so a host timer stopped right after them measures only the launch. Synchronize the device before starting and before stopping the timer, or time with device events recorded in the same stream (`torch.cuda.synchronize()`, JAX's `block_until_ready()`, CUDA events). Timing a whole operation includes the transfers ("When offload pays").
- **A device benchmark you are handed is a claim to check.** Before trusting a speedup from an existing benchmark, or from the request that cites one, read what its timer covers. Many time the kernel alone: the copies to and from the device are left out, or the timer stops before the device finishes. Such a figure can overstate the gain several times over, and the real operation can even be slower than the CPU. Fix the benchmark so it times the whole operation, as callers run it, with synchronization, or report exactly what it leaves out. Then give the corrected figure in place of the old one in the summary, since that figure is what the decision to offload rests on.
- **The first call is not representative.** It pays for just-in-time compilation, kernel loading, library autotuning, context creation, and allocator growth. Run warm-up calls first and report the first-call cost separately when callers pay it (a command-line tool runs once).
- **The device's state varies.** Clocks rise and fall with power and temperature, and other processes on the same device take its time and memory. Check the device is otherwise idle, repeat runs, and lock clocks where the platform allows when comparing two versions (profilers such as Nsight Compute lock clocks and flush caches by default, so their kernel times differ from the application's).
- **Profile with the vendor's tools.** A timeline profiler (Nsight Systems, ROCm's profilers, Intel VTune) shows transfers, launches, idle gaps, and synchronization; a kernel profiler (Nsight Compute or the equivalent) shows why one kernel is slow.
- **Hidden synchronization and copies.** Any operation that needs a device value on the host waits for all queued work and copies the value back: reading a scalar result (`.item()` in PyTorch), printing or logging a device array, converting it to a host array, a host-side `if` on a device value, and sizes that depend on data (a filter whose output length the host must know). One of these inside a loop serializes the host and device on every iteration. Some frameworks can warn on each one (`torch.cuda.set_sync_debug_mode("warn")`); otherwise the timeline profiler shows them as gaps.
- **Verify against the CPU original.** Compare device results with the original's on the same inputs, including the edge cases and the largest sizes. Exact equality is usually impossible ("Behavior traps"), so derive the tolerance from the operation instead of guessing it: for a sum of n terms in precision u, the error bound grows with about n · u · Σ|xᵢ|, so the tolerance scales with the number of terms, the precision, and the magnitudes, and a reduced-precision format sets u to that format's. State the tolerance, test every element against it, and approve it with the developer unless the request named the technique ("What to compare" in `DIFFERENTIAL-TESTING.md`). Integer, index, and ordering outputs still match exactly or the difference is reported.
- **Determinism, when results must be bit-identical** across runs or against the CPU: use fixed-order tree reductions instead of atomics, the framework's deterministic mode (which raises an error for operations without a deterministic version), the library's deterministic or reproducible setting, reduced-precision modes disabled explicitly, and fused multiply-add contraction controlled by compiler flags; or reproducible summation ("Numerical computation" in `techniques/math-and-numerics.md`). This gives run-to-run reproducibility on one device and software stack, at some cost in speed. Bit-identical to the CPU usually needs the same operation order on both sides, which only reproducible summation or exact arithmetic gives; otherwise state the tolerance and test against it.

## Behavior traps

Rewrites that look equivalent but are not; check them alongside `BEHAVIOR-TRAPS.md` ("Concurrency" there applies to every kernel).

- **Floating-point order and rounding.** Parallel reductions, scans, tiled products, and atomic additions sum in a different, often run-to-run varying order; compilers for the device contract multiply-add pairs into fused operations with a single rounding; device math libraries can round differently from the host's, and libraries can pick a different algorithm per size and device. Results then differ from the CPU version and can differ between runs, devices, driver versions, and library versions.
- **Reduced-precision defaults.** Some libraries use reduced-precision arithmetic for single-precision matrix operations by default or behind one setting (TensorFloat-32 on recent NVIDIA GPUs, where a framework's default can differ between operations and between releases), so a library upgrade or a new device can change results without a code change.
- **Atomics and scheduling vary run to run.** Anything decided by which thread arrives first (atomic accumulation, slots claimed in a shared output or hash table, the duplicate that wins a concurrent insert, the order of a work queue) gives a different result or output order on each run. Output order, tie order, and which of several valid answers is returned (a BFS parent, one of equidistant hits) often differ from the sequential version too. Each is a behavior change unless the code fixes it (rule 5).
- **Availability and fallback.** The device may be absent, busy, or out of memory where the code runs. The original's behavior on those machines is part of the contract: keep a tested CPU path ("When offload pays") and surface device errors as the original's errors would, never as silently wrong results. Device errors are also reported asynchronously, by a later call than the one that caused them.
