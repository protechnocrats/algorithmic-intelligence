# Strings and Text

The shared rules and table conventions in `ADVANCED-TECHNIQUES.md` apply.

## Strings

Before replacing a string operation, record its unit (bytes, UTF-16 code units, code points, or grapheme clusters) and its comparison (ordinal; case-insensitive with which folding, since Turkish dotted and dotless i and ß becoming "SS" differ by locale; locale collation; NFC versus NFD).
- An ASCII or byte fast path matches the original on non-ASCII input, combining marks, and right-to-left text, or falls back.
- Case conversion and normalization can change length, so an index into a lowered or normalized copy is not an index into the original.
- Some digit tests and number parsers accept non-ASCII digits (`\d` in Unicode mode, `int()`, `isdigit`); a replacement accepts exactly the same set.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Many substring or repeated-pattern queries on a static text | Suffix array + LCP array (a suffix tree answers the same queries with several times more memory) | Text does not change; enough queries to amortize the build | Build: O(n log n), or O(n) with SA-IS; O(n) memory. Query: O(m log n) for a pattern of length m, plus O(k) to report k occurrences, instead of O(n·m) per scan |
| Searching a long text for one long pattern over a large alphabet, with a hand-written search loop | Boyer-Moore or Boyer-Moore-Horspool (skip ahead by mismatch tables), or the platform's optimized search, which often already uses them or two-way matching | Same matching semantics (case, overlapping matches, Unicode units) | O(n·m) → sublinear on average, O(n/m) in the best case; the worst case stays O(n·m) for Horspool, and is O(n + m) for full Boyer-Moore with the Galil rule |
| Distinct substrings, longest repeated or common substring | Suffix automaton | Text does not change; memory O(n · alphabet) with array transitions, or O(n) with maps, counted against the largest text callers can pass; same unit of text as the original | O(n²) or worse → O(n) build |
| Longest palindromic substring, all palindromes | Manacher's algorithm | Same unit of text as the original: bytes, code units, code points, or user-visible characters give different palindromes | O(n²) → O(n) |
| Border and period detection | Prefix function (KMP failure function) | Same unit of text as the original; which border or period is reported (shortest, longest, all) matches | O(n²) → O(n) |
| Edit distance when only small distances matter | Banded (Ukkonen) edit distance | A threshold k is known | O(n·m) → O(n·k) |
| Regular expression with nested or overlapping quantifiers (`(a+)+`, `(a\|a)*`, `.*.*x`), run by a backtracking engine on long or untrusted input | Rewrite the pattern to remove the ambiguity (atomic groups or possessive quantifiers where supported), or switch to a linear-time engine (Thompson NFA or lazy DFA, such as RE2, Rust's `regex`, Go's `regexp`) | Linear-time engines lack backreferences and lookaround; compare leftmost-first versus leftmost-longest, capture contents, Unicode classes, anchors, and line modes. A new engine is usually a dependency (rule 7). Keep existing match timeouts and input length limits; patterns built from input: `techniques/hostile-inputs.md` | Exponential worst case for nested quantifiers such as `(a+)+`, polynomial (cubic for an unanchored search) for patterns such as `.*.*x` → O(n·m) for text length n and pattern size m |
| Many regular expressions tried one after another on the same input | One combined alternation, or a regex set that reports every pattern that matched in one pass | Which pattern wins, and in which priority order, matches the original | k passes over the input → one pass |
| Keyword or term search across many documents by scanning each | Inverted index: each term maps to a sorted list of the documents (and positions) containing it; ranking such as BM25 computed over those lists only; multi-term queries intersect lists | Tokenization, normalization, matching rules, and result order reproduce the original; documents the caller may not see (other tenants, deleted or restricted records) are excluded as in the original and before the top k is taken, or results and counts leak or change | O(total text) per query → O(length of the posting lists for the query terms) |
| Multi-term ranked search that scores every document in the union of the posting lists, then sorts | Dynamic pruning for top-k retrieval: MaxScore, WAND, or Block-Max WAND, using per-term (and per-block) upper bounds on score contributions to skip documents that cannot enter the current top k | The scoring function is a sum of per-term contributions with known maxima; ties at the k-th score are broken as in the original | Most postings skipped; same top k as exhaustive scoring |
| Intersecting posting lists or sorted ID sets of very different lengths | Galloping (exponential) search from the shorter list into the longer one, or skip pointers stored in the lists | Lists sorted by the same order; duplicates handled as the original does | O(m + n) → O(m · (1 + log(n / m))) for lists of lengths m ≤ n |
| Sorting many strings that share long prefixes (paths, URLs, composite keys), where each comparison rescans the shared prefix | Multikey (three-way radix) quicksort: partition on one character at a time, recursing into the "equal" part on the next character | The order equals the original comparator's: plain code-unit or byte order, not locale collation or case-insensitive comparison | O(n log n) full-string comparisons → O(n log n + D) character comparisons expected, where D is the total length of the distinguishing prefixes |
| Prefix search, autocomplete, or near-neighbor search over a large string set, where a trie with one child slot per alphabet symbol uses too much memory | Ternary search trie: each node holds one character and three children (less, equal, greater) | Same matching rules (case, normalization) and result order as the original | O(k + log n) per lookup for a key of length k in a balanced tree, with memory proportional to the stored characters |
| Diffing two sequences (lines, tokens, characters, list items) with the full O(N·M) longest-common-subsequence table | Myers' O((N + M) · D) algorithm, where D is the edit distance, with its linear-space variant; Hunt-Szymanski when matches are rare | Same edit script: Myers returns a shortest script but may pick a different one among several, and patience or histogram diff pick different (often more readable) ones: a behavior change where the script is shown or stored | O(N·M) time and memory → O((N + M) · D) time and O(N + M) memory; fast when the inputs are similar, but O((N + M)²) when they differ entirely, which an attacker can choose: keep any cost limit the original had |
| Editing a large text buffer by copying the whole string on each insert or delete (editors, collaborative documents, logs edited in place) | Gap buffer (edits near one cursor), piece table (original plus append-only buffer, with a list or tree of pieces), or rope (balanced tree of string chunks) | Index semantics preserved (code units versus code points versus graphemes); line and offset lookups maintained | O(n) per edit → O(1) amortized near the cursor (gap buffer) or O(log n) anywhere (rope, piece tree) |
| Breaking paragraphs into lines by trying combinations of break points | Knuth-Plass total-fit line breaking: DP over feasible break points, keeping only active break points within one line's width | The cost function matches the original's; replacing greedy first-fit with total-fit changes the output (behavior change) | Exponential search → O(n · w) for n break points and at most w per line; first-fit greedy stays O(n) but is not optimal |
| Regular expression used only to find a fixed string or a fixed prefix | Plain substring search or prefix check | Same case sensitivity, escaping, and Unicode handling | Constant factor; no engine setup |

## Automata, lexers, and parsers

A rewrite reproduces accept and reject decisions, match priorities, error positions, and error messages on malformed, truncated, and hostile input as well as valid input. A parser that accepts what the original rejected, or reads it differently (duplicate keys, trailing data, invalid UTF-8, out-of-range numbers), creates a parser differential when another component reads the same input: a security behavior change (`techniques/hostile-inputs.md`). Keep nesting, size, and length limits. On untrusted input, a recursive rewrite uses an explicit stack or keeps the original's depth limit. A limit the original lacked rejects input it accepted: in existing code it is a behavior change listed for approval, and new code takes its limits from the requirements or sets and states them ("Algorithmic complexity attacks" in `techniques/hostile-inputs.md`).

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| A lexer that tries each token pattern in turn at every position | One combined deterministic finite automaton (DFA) over all token patterns, generated or hand-built | Longest-match and pattern-priority rules match the original. Longest match makes the DFA back up after overshooting, which is O(n²) in the worst case for some token sets (tokens `a` and `a*b` on `aaaa…`); Reps' memoized tokenizer restores O(n) | O(n · patterns) → O(n) for typical token sets |
| Large DFA tables (many states, poor cache fit) | DFA minimization (Hopcroft's algorithm), equivalence classes of input bytes to shrink the alphabet | Minimization preserves the recognized language; for a lexer, start the partition with accepting states split by the token they report, or different tokens merge | Build O(s · σ log s) for s states and alphabet σ; fewer states and smaller tables |
| A protocol or format parser that rescans the buffer, or restarts when input arrives in pieces (network packets, streamed files) | Explicit state machine that consumes each byte once and keeps its state across buffer boundaries | Same results for every way the input can be split into chunks; limits on header and field sizes kept | O(n · chunks) when each chunk restarts the scan → O(n) |
| A backtracking parser (recursive descent with backtracking, parsing expression grammars) that is slow or exponential on some inputs | Packrat parsing: memoize each (rule, position) result | Rules are pure; ordered-choice semantics kept; memory O(n · rules) is acceptable for the largest input callers can pass, or memoize only the rules that backtrack | Exponential worst case → O(n · rules) |
| Arithmetic or filter expressions evaluated by repeatedly scanning for the highest-precedence operator and rewriting the string | Dijkstra's shunting-yard algorithm: one pass with an operator stack produces postfix order (or a tree), then one evaluation pass | Same precedence, associativity, unary-operator handling, and errors for malformed input | O(n²) → O(n) |
| General context-free parsing by exhaustive backtracking or the CYK algorithm | Earley, GLR, or GLL parsing; or a deterministic LL or LR parser when the grammar allows | Same parse result, including which parse is chosen for ambiguous input | Exponential or O(n³) → O(n³) worst case (Earley; GLR only in its binarized variants, since plain Tomita GLR is O(n^(k+1)) for rules of length k), O(n²) for unambiguous grammars with Earley, and O(n) for deterministic LL or LR parsers, or Earley with Leo's modification on LR(k) grammars |

## Biological sequences

DNA, RNA, and protein sequences are strings over tiny alphabets, at sizes that make quadratic work impossible: a human genome is about 3.1 billion bases, and one sequencing run yields hundreds of millions of reads. Exact alignment (Needleman-Wunsch for global, Smith-Waterman for local alignment) is dynamic programming in O(n·m) time, which is fine for two genes and hopeless for a read against a genome. Read mappers and search tools therefore index the reference and align only candidate regions, and most of those shortcuts are heuristics: they can miss an alignment, or report a different score, position, or choice among equally good hits. Treat a move from exact to heuristic alignment as a behavior change, and give its measured sensitivity (alignments found against the exact method) on representative data.

Before replacing sequence code, record how it treats:
- characters other than A, C, G, T: N and the other ambiguity codes, U in RNA, gaps, and lowercase letters, which many formats use to mark repeats ("soft-masking");
- the reverse complement: whether a match on the opposite strand counts;
- scoring and coordinates: the substitution matrix, gap penalties, and 0-based or 1-based, inclusive or exclusive positions.

| Signal | Technique | Valid when | Typical result |
|---|---|---|---|
| Nucleotide sequences stored one character (or object) per base, with memory or bandwidth the limit | 2-bit encoding: four bases per byte, 32 per 64-bit word; comparison and hashing on whole words | The alphabet is exactly A, C, G, T, or the other symbols (N runs, ambiguity codes, lowercase masking) are kept in a side structure, as the UCSC 2bit format keeps N and masked blocks; otherwise they are lost or turned into a real base (behavior change) | 4 times less memory than one byte per base; k-mers of up to 32 bases fit one integer |
| k-mers counted or looked up by building a substring per position and hashing it | Rolling k-mer integers: shift in 2 bits per base and mask to 2k bits; for strand-independent work, the canonical k-mer is the smaller of the k-mer and its reverse complement (also updated per base); counts kept in a hash table, or sorted and run-length counted | k ≤ 32 for a 64-bit integer (wider types or two words beyond that); a k-mer containing N is skipped or handled as the original does; canonical form only if the original treats both strands as equal; memory for the distinct k-mers of the largest input is counted (billions at genome scale), with disk-based partitioned counting when it does not fit | O(n·k) → O(n) to extract all k-mers; constant-factor gains in hashing and memory |
| An index over every k-mer position of a large reference or read set, too large for memory | Minimizers: in each window of w consecutive k-mers, keep only the smallest under a hash order, and index those | Any two sequences sharing an exact match of at least w + k − 1 bases share a minimizer, so such matches are still found; shorter shared matches can be missed (behavior change against indexing every k-mer); the order is a hash, not lexicographic order, which selects low-complexity k-mers such as AAAA… far too often; the most frequent minimizers (repeats) are capped or skipped as a stated policy | Index holds about 2/(w + 1) of the positions under a random order: several times smaller and faster to query |
| Exact-match or few-mismatch search of many short patterns (sequencing reads) against a large static reference with a suffix array or hash table that does not fit memory | FM-index: the Burrows-Wheeler transform of the reference with rank (occurrence) tables and a sampled suffix array; backward search counts occurrences of a pattern of length m in O(m) rank queries | The reference does not change (building costs about a suffix-array construction, done once); locating each occurrence costs time inversely proportional to the suffix-array sampling rate, a memory-for-time choice to state; mismatches are searched by backtracking, which grows exponentially with the number allowed, so cap it | Index of a few bits per base instead of 4 to 8 bytes per base for a suffix array; count in O(m), independent of the reference length |
| Each read aligned against the whole reference by full dynamic programming | Seed and extend: find exact seeds (k-mers, minimizers, or maximal exact matches from an FM-index), chain colinear seeds, then align only the regions around the best chains with banded dynamic programming | Behavior change: reads whose true alignment has no exact seed are missed, and positions, scores, and the choice among equally good hits (multi-mapping reads) can differ; report sensitivity measured against exact alignment on representative data; repeat-rich references cap the number of seed hits per read | O(n·m) per read against the reference → roughly proportional to the read length plus the candidate regions, in practice |
| Pairwise alignment of two long, similar sequences by the full O(n·m) table | Banded alignment, restricted to a diagonal band of width w; or X-drop extension, which stops a path once its score falls a set amount below the best seen | Banded: exact only if the optimal alignment stays inside the band, which holds when the band covers the largest distance the optimal path can stray from the diagonal (at most the total gap length it can contain, and never less than the difference in lengths) (the banded edit-distance row in "Strings" is the case with unit costs); otherwise, and always for X-drop, a heuristic (behavior change) | O(n·m) → O(n·w) for banded; X-drop work proportional to the region explored |
| Exact Smith-Waterman or Needleman-Wunsch scores required, but too slow; or affine gap penalties computed by trying every gap length at each cell | Gotoh's three-table recurrence for affine gaps; SIMD vectorization of the same recurrence (Farrar's striped method), or GPU kernels; Hirschberg's divide and conquer when the traceback must fit in linear memory | Same scores as the original by construction; narrow (8- or 16-bit) vector lanes saturate on high scores, so overflow is detected and the cell recomputed at a wider width; ties between equally scoring alignments are broken as the original breaks them, or the chosen alignment can differ (behavior change where it is reported) | Affine gaps: O(n·m·(n + m)) → O(n·m); SIMD: several times faster at the same complexity; Hirschberg: O(n·m) memory → O(n + m) at about twice the time |
