Round 7's pattern held with five times the data. **Haiku without the skill broke a user-visible contract in 4 of 5 sessions; Haiku with the skill never did.** The aliasing trap fooled it every time: the cache returns its own string, and `CodeSummary` appends " (discontinued)" to it in place.

**Opus without the skill made no behavior errors.** On this fixture it was as safe as Opus with the skill, cut more round trips, and cost 40% less. The skill's safety advantage is a small-model effect here. Opus needed no help with aliasing or error order.

## Why the skill held back RB1 and RB2 on Haiku

Every Haiku skill session found both items and listed them under "Behavior changes for review". The reasons:
- **Labels:** "an edit made during a page render is seen on the next page".
- **Billing:** "a price change published mid-run is not seen".

The decline turn then declined them, and the sessions kept the original code. **None of them looked for an equivalent variant afterward.** One said outright there was none.

Equivalent variants exist for both items, and the Opus skill sessions found them:
- **Labels** (opus-2, opus-3): read the file on every call, but parse it only when its text changes, and return a copy. Each edit is visible on the next call, exactly as before, and the parsing cost is gone.
- **Billing** (opus-1, opus-3): verified "against a fake that implements the documented contract", the round-7 change in rule 5 at work. opus-2 read `DIFFERENTIAL-TESTING.md`, the only skill session other than haiku-2 to read anything beyond `SKILL.md` and `REPORTING.md`.

On billing, the Haiku sessions' concern is technically real: a price change in the middle of one statement call would be seen by later lines in the original. The answer key treats caching for the duration of one call as within the contract, so these sessions were overcautious on billing. On labels they missed an equivalent variant that does exist.

**What this suggests for the skill (not yet changed):**
1. **Before filing a speedup as a behavior change, look for a variant that keeps the behavior.** Examples: recompute only when the input actually changed, keep the call but drop the repeated work, cache only within one call. File it as a behavior change only if no such variant exists, and say why.
2. **When a behavior change is declined, offer or apply the variant that keeps the behavior,** as opus-2 did ("applied as an equivalent variant after BC-3 was declined").
3. **The skill's routing is mostly not followed.** 6 of 8 with-skill sessions read only `SKILL.md` and `REPORTING.md`, never `WORKFLOW.md` or `DIFFERENTIAL-TESTING.md`. Instructions that matter on every run need to be in `SKILL.md` or in the report format, or the routing step needs to be enforced.

## Cost

The skill cost 4 times more on Haiku ($0.45 against $0.11) and 1.7 times more on Opus ($3.13 against $1.87). One Opus pair costs about as much as 6 Haiku pairs.

## Limits

- One fixture, and the decline turn declines everything. A developer who approved B1 or B2 would have received the Haiku skill sessions' speedups.
- The probe checks behavior and a few timings, not report quality. The report claims above come from reading the reports and `APPLY-RESULTS.md`.
- "Read only `SKILL.md` and `REPORTING.md`" counts tool calls that name the file. A session could have learned the content another way, but none quoted it.
